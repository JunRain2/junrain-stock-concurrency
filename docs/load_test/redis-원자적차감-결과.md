## 1. 측정 대상

재고 감소는 `RedisStockWriterImpl.decrease`가 실행하는 Lua 스크립트(`redis/decrease_stock.lua`) 한 번으로 수행된다. Redis는 단일 스레드로 명령을 처리하므로 스크립트 실행 자체가 원자 단위이며, 애플리케이션이 별도로 락을 걸지 않는다.

```lua
-- 전부 검사한 뒤에 차감하므로 부분 차감이 생기지 않는다
for i = 2, #KEYS do
    local current = redis.call('GET', KEYS[i])
    if tonumber(current) < tonumber(ARGV[i]) then
        return {2, i - 1}
    end
end
for i = 2, #KEYS do
    redis.call('DECRBY', KEYS[i], ARGV[i])
end
```

호출 전후로 `StockOpLogger`가 `stock-op` 로그에 pending/done을 남긴다(Redis 타임아웃 시 적용 여부를 알 수 없는 요청을 나중에 식별하기 위한 WAL). 예약 자체(`Reservation` 저장)는 이전과 동일하게 MySQL에 JPA로 쓰인다 — 이 측정에서 MySQL은 재고 경합과는 무관하게 매 요청 1건씩 계속 쓰인다.

`RedisStockWriterImpl`이 `@Primary`라 이 저장소가 실제 예약 경로에서 사용된다. `increase`(보상 경로)는 미구현(`TODO`)이며 예약 성공 경로에서는 호출되지 않는다.

이 구현은 아직 커밋되지 않은 작업 중 코드다(git sha `c2f314d` 기준 워킹 트리 변경분).

## 3. 시나리오 A 단일 행 경합

| 도착률 | run1 p95 | run2 p95 | run3 p95 | 중앙값 | 판정(중앙값 기준) |
|---|---|---|---|---|---|
| 500 | 17ms | 6ms | 10ms | **10ms** | PASS |
| 600 | 17ms | 11ms | 6ms | **11ms** | PASS |
| 700 | 7ms | 6ms | 1,130ms (FAIL) | **7ms** | PASS |

요청 수는 500/600 RPS 구간에서 3회 모두 기대치(rate×40s)에 사실상 일치한다(20,000~20,001건, 24,000~24,001건). 700 RPS는 run1·run2가 28,001건(100%)이고, run3만 27,138건(96.9%)로 5.6절 완결성 기준(95%)은 겨우 넘는다.

각 실행에서 나온 `dropped_iterations` 경고(run1 6,236 / run2 1,473 / run3 2,127)는 사다리 최고 rate(700)로 60초 도는 워밍업 구간에서 커넥션을 새로 여는 비용 때문으로 보인다 — 측정 구간(500/600/700) 요청 수 자체는 위처럼 기대치에 도달했으므로, 5.6절 "워밍업 구간 드롭은 유효성 판정에서 제외"에 해당한다.

**3회 사다리 전 구간이 중앙값 기준 PASS다.** 유일한 예외는 run3의 700 RPS에서 나온 1,130ms 단발 저하로, 다른 두 실행(6~7ms)과 두 자릿수 이상 차이 난다. **사다리(500~700 RPS) 안에서 A의 처리 한계를 찾지 못했다** — MySQL 재측정에서는 정확히 이 구간(약 645 RPS)이 한계였던 것과 대조적이다.

## 4. 시나리오 B 기준선

| 도착률 | run1 p95 | run2 p95 | run3 p95 | 중앙값 | 판정(중앙값 기준) |
|---|---|---|---|---|---|
| 500 | 6ms | 1,464ms (FAIL) | 252ms (FAIL) | **252ms** | FAIL |
| 600 | 286ms (FAIL) | 10ms | 10ms | **10ms** | PASS |
| 700 | 42ms | 6ms | 52ms | **42ms** | PASS |
| 1000 | 13ms | 8ms | 204ms (FAIL) | **13ms** | PASS |

**500 RPS(사다리의 첫 측정 구간, 워밍업 직후)에서 3회 중 2회가 큰 폭으로 튀었다.** run2는 1,464ms, run3는 252ms로 SLO(200ms)를 넘겼고, 중앙값도 252ms로 FAIL이다. 나머지 구간(600/700/1,000)은 매번 다른 회차에서 한 번씩만 튀는, 지금까지와 같은 일회성 패턴이다.

500 RPS의 저하가 유독 3회 중 2회 반복된다는 점은 다른 구간의 "무작위한 1회성"과 결이 다르다. 워밍업(최고 rate인 1,000 RPS로 60초)이 끝난 직후 곧바로 시작되는 첫 측정 구간이라, 워밍업 종료 시점의 VU 정리·재할당 비용이 500 RPS 구간 초반에 걸쳐 들어갈 가능성이 있다 — 검증하지 않은 가설이다(9절).

600 RPS부터는 안정적으로 PASS다. **B의 처리 한계는 최소 700 RPS까지 확인되고, 1,000 RPS는 중앙값(13ms)은 PASS지만 3회 중 1회(run3, 204ms)가 SLO 경계에 걸려 완전히 확정하기는 이르다.**

## 5. 경합 비용

공통 도착률 600 RPS를 기준으로 삼는다(양쪽 다 3회 중 다수가 안정적으로 통과).

| 기준 | A 중앙값 | B 중앙값 | 배수 |
|---|---|---|---|
| p95 @ 600 RPS | 11ms | 10ms | **약 1.1배** |
| p95 @ 500 RPS | 10ms | 252ms | 0.04배 (A가 더 빠름 — B의 500 구간 이상치 때문, 6절) |

**단일 행에 요청이 몰려도(A) 상품 100개에 분산돼도(B) 지연에 유의미한 차이가 없다.** MySQL에서 관측된 15~18배의 경합 비용이 Redis 구현에서는 사실상 사라졌다. 500 RPS의 역전(B가 A보다 20배 이상 느림)은 경합 때문이 아니라 4절에서 다룬 B 고유의 워밍업 직후 저하 때문이며, 이 수치를 경합 비용으로 해석하면 안 된다.

## 6. MySQL 대비 관찰

MySQL 구현(mysql-비관적락-결과.md 6절)의 병목은 행 락 보유 시간(~1.5ms, 커밋 시 fsync 포함)이었고, 이 값이 A의 처리 한계(~645 RPS)를 그대로 결정했다. Redis 구현은 이 병목의 원인 자체가 없다 — Lua 스크립트는 단일 스레드로 마이크로초 단위에 끝나고, 트랜잭션 커밋에 걸리는 fsync도 재고 변경 경로에는 없다(재고는 인메모리 키 변경이지 디스크 커밋이 아니다). 그 결과가 3절의 관찰이다: 같은 사다리(500~700 RPS) 안에서 A가 한 번도 한계에 부딪히지 않았다.

다만 예약 자체는 여전히 MySQL에 `Reservation` 행을 커밋한다. 이 쓰기는 상품별 경합이 없는 단순 INSERT라 행 락 문제는 없지만, HikariCP 풀(기본값 10)을 A와 B가 공유한다. 1,000 RPS 부근에서 나타나는 B의 불안정(4절)이 이 공유 풀 때문인지, 아니면 아래 7절의 호스트 잡음 때문인지는 이번 측정만으로 구분할 수 없다.

## 7. 미해결 관측

MySQL 재측정(mysql-비관적락-결과.md 7절)에서 관측한 "부하 크기와 무관하게 매 실행 정확히 한 구간에서만 나타나는 일회성 저하"가 Redis 구현에서도 그대로 재현됐다: A run3의 700 RPS(1,130ms), B run1의 600 RPS(286ms), B run2의 500 RPS(1,464ms), B run3의 500·1,000 RPS.

**구현을 MySQL 행 락에서 Redis 단일 스레드 연산으로 완전히 바꿨는데도 같은 패턴이 재현됐다는 것은, 이 저하가 재고 경합 로직과 무관하다는 강한 증거다.** 두 구현이 공유하는 것은 호스트/Docker VM, k6, 그리고 MySQL에 남아 있는 Reservation INSERT뿐이다. 원 문서(재고점유.md) 7절의 호스트/VM 스케줄 지연 가설이 이번 결과로 더 힘을 얻는다.

B의 500 RPS에서만 3회 중 2회 반복된 것(4절)은 이 일회성 패턴과 별개로 다뤄야 한다 — 워밍업 종료 직후 첫 구간이라는 위치가 고정돼 있어, 무작위 호스트 잡음보다는 워밍업-측정 전환 시점의 구조적 비용일 가능성이 있다.

## 10. 처리 한계 탐색 (풀 크기 진단)

3절·4절의 사다리(500~1,000 RPS)로는 Redis 구현의 실제 한계를 찾지 못해(3회 모두 사다리 위에서 한계 미도달), 사다리를 올려 한계를 직접 찾았다. 아래는 모두 **단발 실행**(반복 없음)이라 탐색 목적으로만 쓴다 — 8.6절 반복 기준 대상이 아니다.

### 10.1 1차 시도: 크래시

사다리를 A/B 모두 `[700, 1000, 1500, 2000, 3000]`으로, k6 `maxVUs` 상한을 기존 1,500 → 8,000으로 올려 재실행했다. 결과: **앱 컨테이너가 `OutOfMemoryError: Java heap space`로 죽었다.** 힙 사용량이 컨테이너 메모리 상한(1,465MiB)의 98%까지 찬 뒤 각 스레드에서 연쇄적으로 OOM이 터졌고, `http_req_failed`가 99.82%(대부분 10초 타임아웃)에 달했다.

원인은 백프레셔 부재다. HikariCP 풀(기본 10)이 감당 못 하는 속도로 요청이 들어오면, MySQL 락 대기 타임아웃(2초)으로 빠르게 튕기는 MySQL 구현과 달리 이 구현은 커넥션을 그냥 기다린다 — 대기가 쌓일수록 Tomcat 스레드·Virtual Thread·버퍼가 힙에 계속 누적된다. k6 쪽 `maxVUs`를 넉넉히 열어주면 그 누적을 막을 벽이 없어져 힙이 터진다. **한계를 넘겼을 때 "느려짐"이 아니라 "죽음"으로 나타난다는 것 자체가 관찰 결과다.**

컨테이너를 재기동하고 `maxVUs` 상한을 2,500으로, 사다리를 `[1000, 1300, 1600, 1900]`으로 낮춰 재시도했다(아래 10.2). 시드 재고도 이 사다리의 워밍업 소비량에 맞춰 500,000 → 3,000,000으로 올렸다(`seed.sql`).

### 10.2 풀 기본값(10)에서의 한계

| 도착률 | A p95 | A 판정 | B p95 | B 판정 |
|---|---|---|---|---|
| 1000 | 941ms | FAIL | 101ms | PASS |
| 1300 | 80ms | PASS | 4,657ms | FAIL |
| 1600 | 732ms | FAIL | 3,313ms | FAIL |
| 1900 | 2,367ms | FAIL | 2,761ms | FAIL |

판정이 뒤죽박죽인 것(A는 1000에서 FAIL, 1300에서 PASS) 자체가 신호다 — 1,000~1,300 RPS 부근이 한계 바로 옆이라 튀는 것이지, 사다리를 더 올린 1,600·1,900은 명확히 넘어섰다. **풀 10 기준 실제 처리 한계는 대략 1,000~1,300 RPS**로, 6절에서 "행 락 병목이 없다"고 결론 낸 것과 모순되지 않는다 — 이번에 새로 찾은 벽은 재고 경합이 아니라 **Reservation INSERT가 공유하는 HikariCP 풀**이라는 게 아래 10.3에서 확인된다.

### 10.3 풀을 50으로 올렸을 때

같은 사다리로, `docker-compose.bench.yml`에 `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=50`을 임시로 얹어 재실행했다(측정 후 원복 — 이후 baseline과 섞이지 않게).

| 도착률 | A p95 | A 판정 | B p95 | B 판정 |
|---|---|---|---|---|
| 1000 | 19ms | PASS | 328ms | FAIL (이상치) |
| 1300 | 16ms | PASS | 60ms | PASS |
| 1600 | 543ms | FAIL | 17ms | PASS |
| 1900 | 410ms | FAIL | 90ms | PASS |

**B의 처리 한계가 1,000 → 1,900 RPS 이상으로 밀렸다.** A도 1,000 RPS가 941ms(FAIL)에서 19ms(PASS)로 확 좋아졌다. 풀을 5배 늘렸더니 한계가 그만큼 밀린다는 것은, **6절의 결론에 이어 시스템 전체의 상한이 Redis 재고 로직이 아니라 Reservation을 쓰는 MySQL 커넥션 풀(기본값 10)이라는 뜻이다.** B의 1000 RPS FAIL(328ms)은 다른 구간이 다 PASS인 채로 하나만 튄 것이라 7절의 일회성 저하 패턴과 같은 종류로 보인다.

**결론: 지금 기본 설정(풀 10)에서 Redis 구현의 실질 처리 한계는 약 1,000~1,300 RPS다.** 이 한계는 Redis도 MySQL 행 락도 아닌 커넥션 풀 크기가 만든 것이므로, 재고 로직과 무관하게 `application.yml`에 풀 크기를 명시하고 늘리는 것만으로 쉽게 올릴 수 있는 여지가 있다(9절 4번).
