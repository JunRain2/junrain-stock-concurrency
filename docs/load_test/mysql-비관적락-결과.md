## 1. 측정 대상

재고 감소는 `JdbcProductRepository.applyStockDeltas`의 단일 UPDATE 한 건으로 수행된다.

```sql
UPDATE products SET stock = stock + CASE id WHEN ? THEN ? END
WHERE id IN (?) AND stock + CASE id WHEN ? THEN ? END >= 0
```

이 UPDATE는 대상 행에 배타 락을 걸고, 락은 트랜잭션 커밋까지 유지된다. 같은 행을 겨냥한 다른 트랜잭션은 락 해제까지 MySQL 안에서 대기한다. 애플리케이션 코드에 별도의 락 획득 단계는 없으나, 동시성 제어의 실체는 DB 행 락에 의한 직렬화이므로 비관적 락으로 분류한다.

낙관적 락 재시도 경로는 없다. 락 획득에 실패하면 `StockUnstableException`으로 409를 반환하고 종료한다.

실행 시각은 KST 01:26–01:35이며, 이 구간은 모니터링 스택(Prometheus, mysqld-exporter)이 함께 동작했다. 6.5절의 유효성 조건 중 호스트 자원 전용 사용 항목에서 벗어나므로, 절대 처리량보다 A와 B의 상대 비교에 무게를 둔다.

## 3. 시나리오 A 단일 행 경합

| 도착률 | 표본 | 중앙값 | p95 | p99 | 최대 | 실효 처리량 | 판정 |
|---|---|---|---|---|---|---|---|
| 500 | 20,001 / 20,000 (100%) | 4.8ms | 233ms | 310ms | 608ms | 500/s | FAIL |
| 600 | 24,001 / 24,000 (100%) | 35ms | 293ms | 342ms | 674ms | 600/s | FAIL |
| 700 | 25,181 / 28,000 (89.9%) | 2,184ms | 2,563ms | 4,825ms | 7,516ms | 630/s | 무효 |

응답 상태는 200이 94,926건, 400과 409는 0건이다. 락 대기 만료가 빠른 실패로 빠져나가 p95를 낮추는 왜곡은 없다.

500 구간이 p95 233ms로 임계값을 넘었으므로 **A의 처리 한계는 500 RPS 미만**이며, 현재 부하 단계로는 값을 확정할 수 없다.

700 구간은 표본 완결성 89.9%로 무효다. 지연이 늘면서 k6가 `maxVUs` 상한에 도달해 이터레이션을 버렸다.

구간별 거동이 대기행렬 모형과 일치한다. 700 구간의 실효 처리량 630/s는 직렬 구간의 서비스 시간 1.59ms에 해당하고, 이 값을 용량으로 보면 이용률은 500 RPS에서 79%, 600 RPS에서 95%, 700 RPS에서 111%다.

| 이용률 | 관측 | 해석 |
|---|---|---|
| 79% | 중앙값 4.8ms, p95 233ms | 꼬리만 대기에 걸린다 |
| 95% | 중앙값 35ms, p95 293ms | 대기가 중앙값까지 올라온다 |
| 111% | 중앙값 2,184ms | 큐가 발산한다 |

1.59ms 안에는 `innodb_flush_log_at_trx_commit=1`이 강제하는 커밋 시점 fsync가 포함된다. 락을 쥔 채 fsync를 기다리므로, 이 설정이 곧 직렬 구간의 길이를 결정한다.

## 4. 시나리오 B 기준선

| 도착률 | 표본 | 중앙값 | p95 | p99 | 최대 | 판정 |
|---|---|---|---|---|---|---|
| 500 | 20,001 / 20,000 (100%) | 2.4ms | 54ms | 329ms | 498ms | PASS |
| 600 | 24,000 / 24,000 (100%) | 2.4ms | 5.8ms | 23ms | 95ms | PASS |
| 700 | 27,575 / 28,000 (98.5%) | 3.3ms | 566ms | 1,450ms | 2,227ms | FAIL |
| 1000 | 40,001 / 40,000 (100%) | 3.7ms | 90ms | 202ms | 446ms | PASS |

응답 상태는 200이 171,578건, 400과 409는 0건이다.

중앙값이 1,000 RPS까지 2.4–3.7ms로 유지되고 최고 단계가 통과했다. **B의 처리 한계는 1,000 RPS를 넘으며 이번 측정으로는 찾지 못했다.** 700 구간의 실패는 부하 증가에 따른 저하가 아니다(6절, 7절 참조).

## 5. 경합 비용

경합 비용은 동일 도착률에서의 `p95(A) ÷ p95(B)`로 정의한다. 500 구간은 B의 p95가 54ms로 인접 구간(5.8ms) 대비 이상값이므로 사용하지 않고, 양쪽 모두 표본이 완결된 600 구간을 기준으로 한다.

| 기준 | A | B | 배수 |
|---|---|---|---|
| p95 @ 600 RPS | 293ms | 5.8ms | **50배** |
| 중앙값 @ 600 RPS | 35ms | 2.4ms | 15배 |

같은 도착률, 같은 코드 경로에서 대상 행이 하나로 모이는 것만으로 p95가 50배가 된다.

## 6. 병목 확인

측정 구간을 Prometheus가 덮었으므로 서버 지표로 원인을 확정할 수 있다.

| 지표 | A 구간 | B 구간 |
|---|---|---|
| `innodb_row_lock_time` | 4,500–8,600 ms/s | 1–60 ms/s |
| `innodb_row_lock_current_waits` | 8–9 | 0 |
| `hikaricp_connections_pending` | 최대 1,491 | 0 |
| `hikaricp_connections_active` | 10 고정 | 10 미만 |
| `mysql_global_status_threads_running` | 11–13 | 2–11 |
| `innodb_log_waits` | 0 | 0 |

A에서는 커넥션 10개 중 9개가 항상 행 락을 기다리고, 나머지 요청 1,491건은 커넥션 풀 큐에서 대기한다. DB 안에서 실제로 진행 중인 트랜잭션은 언제나 1건이다. 즉 A의 처리량 상한은 커넥션 수도 CPU도 아닌 **행 락 보유 시간의 역수**다.

B에서는 풀 대기가 전 구간 0이고 행 락 대기가 무시할 수준이다. 1,000 RPS에서 MySQL은 약 5,000 QPS를 처리했고 평균 사용 커넥션은 4개 미만이다. 기준선으로서 자격을 만족한다.

부수 확인 사항으로, 커넥션 풀 크기가 `application.yml`에 설정되어 있지 않아 HikariCP 기본값 10으로 동작한다. Virtual Thread가 켜져 있어 웹 계층에는 동시성 상한이 없으므로 부하는 전부 이 10개에 모인다. A에서는 행 락이 직렬 자원이라 풀을 키워도 처리량이 오르지 않고 대기 위치만 옮겨가지만, B의 부하 단계를 더 올리면 이 값이 먼저 상한으로 걸린다.

## 7. 미해결 관측

B의 700 구간만 p95 566ms, 최대 2,227ms, 폐기 이터레이션 425건을 기록했다. 바로 다음 1,000 구간은 완결 표본에 p95 90ms로 통과했다. 부하가 원인이라면 더 높은 도착률에서 더 나빠야 하므로 부하 의존적 저하가 아니다.

해당 시각의 서버 지표에는 근거가 없다. 행 락 대기 25–60 ms/s, GC 점유율 0.9%, 풀 대기 0이다. 앱과 DB 어느 쪽도 포화 징후를 보이지 않았다. 남은 후보는 호스트 또는 Docker VM의 순간적 스케줄 지연이며, 서버 측 지표로는 더 좁힐 수 없다.

## 8. 이 결과의 유효 범위

| 항목 | 상태 |
|---|---|
| 반복 횟수 | 1회. 8.6절이 요구하는 3회 미달 |
| 실행 간 편차 | A의 500 구간이 실행에 따라 43ms / 233ms / 2,084ms로 관측되었다 |
| 호스트 전용 사용 | 미충족. 모니터링 스택이 같은 VM에서 동작 |
| 표본 완결성 | A 700 구간, B 700 구간 미달 |

따라서 이 문서의 절대 수치는 확정값이 아니다. 반면 A와 B의 차이는 같은 실행 안에서 나온 값이고 서버 지표로 기전이 확인되었으므로, 경합 비용 50배와 6절의 병목 위치는 이 실행만으로도 유지된다.
