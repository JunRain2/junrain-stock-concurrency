## 1. 측정 목표와 범위

### 1.1 목표

이 테스트는 다음 한 가지 질문에 답한다.

> 재고 행 경합이 처리량을 얼마나 깎는가.

동시성 제어 구현을 바꿔가며 이 값을 비교하는 것이 목적이다. 따라서 시나리오는 경합 정도라는 변수 하나만 조작하고 나머지 조건은 모두 고정한다. 여러 변수가 함께 변하면 결과가 나빠져도 원인을 특정할 수 없다.

### 1.2 범위 밖

정합성 검증은 이 테스트가 담당하지 않는다.

| 항목 | 검증 위치 |
|---|---|
| 오버셀 없음 (lost update) | `ReserveProductsConcurrencyTest` |
| 다중 상품 역순 요청 시 데드락 없음 | 같은 테스트 |
| 재고 부족 시 롤백 | `ReserveProductsIntegrationTest` |

부하테스트는 확률적이므로 "이번 실행에서는 문제가 발생하지 않았다"까지만 말할 수 있다. 반면 통합 테스트는 "재고 수량만큼만 성공했다"를 단정한다. 검증은 결정적인 쪽에 맡긴다.

## 2. 용어

| 용어 | 정의 |
|---|---|
| **도착률(rate)** | 초당 요청 수. 이 테스트에서 조작하는 부하 단위 |
| **부하 단계** | 하나의 고정 도착률로 40초간 유지하는 구간 |
| **처리 한계** | p95 < 200ms를 만족하는 최대 도착률. 시나리오별 결론값 |
| **기준선** | 경합이 없는 조건에서의 처리 한계. 시나리오 B가 담당 |
| **경합 비용** | 동일 도착률에서 p95(A) ÷ p95(B) |

## 3. 부하 모델

### 3.1 도착률 고정 방식

가상 사용자(VU) 수가 아니라 초당 요청 수를 고정한다. k6의 `constant-arrival-rate` 실행자를 사용한다.

VU 수를 고정하는 방식은 각 VU가 응답을 받은 뒤에 다음 요청을 보내므로, 응답 지연이 늘어나면 실제 유입량이 함께 줄어든다. 서버가 느려질수록 부하도 낮아지는 구조이며, 그 결과 포화 지점이 측정 결과에서 사라진다. 이를 coordinated omission이라 한다.

도착률을 고정하면 다음과 같이 유입량과 지연을 분리해 기술할 수 있다.

> 300 RPS에서 p95 180ms, 600 RPS에서 p95 2,400ms.

### 3.2 단계 분리

각 부하 단계는 독립 시나리오로 정의하고 `rate` 태그를 부여해 순차 실행한다.

```
rate_500  [0s   ~ 40s ]  tags: { rate: "500" }
rate_600  [55s  ~ 95s ]  tags: { rate: "600" }
rate_700  [110s ~ 150s]  tags: { rate: "700" }
```

하나의 시나리오 안에서 부하를 점증시키면 요약 통계의 p95가 저부하 구간과 고부하 구간의 평균이 되어 해석할 수 없다.

`thresholds`에 태그 셀렉터(`http_req_duration{rate:300}`)를 지정하면 k6가 구간별 서브메트릭을 요약에 포함시킨다. 별도 집계 코드가 필요하지 않다.

### 3.3 단계 간 간격

각 단계 사이에 15초의 간격을 둔다. 포화 구간에서 누적된 커넥션 대기와 accept 큐가 다음 단계 초반을 오염시키기 때문이다.

### 3.4 워밍업

전체 실행 앞에 60초간 워밍업을 두고 그 결과는 집계에서 제외한다. JIT 컴파일 이전 구간과 InnoDB 버퍼 풀이 비어 있는 구간은 실제보다 나쁜 값을 내며, 그 정도가 실행마다 달라 재현성을 해친다.

**워밍업은 부하 단계의 최고 도착률로 실행한다.** 낮은 도착률로 워밍업하면 커넥션이 그만큼만 열린 상태로 끝나고, 첫 측정 구간이 나머지 연결을 한꺼번에 여는 비용을 혼자 부담한다. 실제로 50 RPS로 워밍업했을 때 300 구간만 p95 390ms로 실패하고 400·500 구간은 각각 14ms, 120ms로 통과하는 결과가 나왔다. 부하가 올라갔는데 지연이 줄어드는 순서는 부하로 설명되지 않으며, 측정 구조가 첫 구간에만 불리했던 것이다.

## 4. 시나리오

| | 이름 | 요청 대상 | 부하 단계 (RPS) | 역할 |
|---|---|---|---|---|
| **A** | `single-row` | 상품 1개 고정 (ID=1) | 500 / 600 / 700 | 경합 최악 조건. 결론값 |
| **B** | `spread` | 상품 100개 랜덤 | 500 / 600 / 700 / 1000 | 기준선. 경합이 없는 조건의 상한 |

각 단계는 40초이며 간격이 15초다. 워밍업을 포함해 시나리오당 약 5분이 소요된다.

### 4.1 시나리오 B의 역할

B는 독립적인 측정 대상이 아니라 A를 해석하기 위한 통제 변수다.

A만 측정하면 결과가 개선되었을 때 경합이 줄어든 것인지 측정 당시 장비 상태가 좋았던 것인지 구분할 수 없다. B가 그 구분을 제공한다.

```
경합 비용 = p95(A, R) ÷ p95(B, R)      # R은 양쪽에 공통인 도착률
```

처리 한계로 나누지 않는 이유는 해상도 때문이다. 처리 한계는 부하 단계 간격만큼의 해상도밖에 없어 두 시나리오가 같은 값으로 나오기 쉽다. 실제로 첫 측정에서 A와 B가 모두 600 RPS로 같게 나왔으나, 같은 600 RPS에서의 p95는 153ms 대 5ms로 30배 차이였다. 비율 쪽이 훨씬 민감하다.

| 결과 예 | 해석 |
|---|---|
| 비율 1배 부근 | 경합 비용이 없다. 최적화 대상이 이 지점이 아니다 |
| 비율 30배 | 같은 유입량에서 경합 때문에 30배 느리다 |

A와 B가 함께 개선되었다면 경합 자체는 변하지 않은 것이다.

### 4.2 부하 단계 공유

500 / 600 / 700은 두 시나리오에 모두 포함된다. 단계가 어긋나면 동일 유입량에서의 비교가 불가능한데, 그 비교가 이 테스트의 결론이다.

B에만 1000이 있는 것은 A가 해당 지점에서 이미 SLO를 초과할 것으로 예상되기 때문이다. 기준선은 더 높은 지점까지 확인해야 한다.

### 4.3 시나리오 B의 상품 수

상품 10개에 600 RPS를 분산하면 행당 60 RPS가 되어 경합이 남는다. 이 경우 측정 대상은 "경합 없음"이 아니라 "경합 1/10"이 되고, A와의 격차가 실제보다 작게 나온다.

상품 100개면 행당 6 RPS이므로 동일 행에 요청이 겹칠 확률이 무시할 수준이며, 경합을 제외한 순수 처리 비용을 얻을 수 있다.

### 4.4 시드 데이터

상품 100개, 상품당 재고 500,000. 재고 부족이 측정에 섞이지 않는 것이 시드 수량의 유일한 요구사항이다.

워밍업이 최고 도착률로 실행되므로 1회 소비량은 `최고 rate × 60 + Σ(각 단계 rate × 40)`이다. 현재 사다리에서 시나리오 A는 상품 1개에서 78,000건을 소비한다. 여유를 크게 두어 사다리를 조정할 때마다 재계산하지 않아도 되게 한다.

## 5. 판정 기준

```js
thresholds: {
  'http_req_duration{rate:300}': ['p(95)<200'],   // SLO
  http_req_failed: ['rate<0.01'],
}
```

### 5.1 임계값

p95 < 200ms는 이 서비스의 API 응답 SLO다. threshold는 SLO와 일치해야 통과·실패가 신호로 기능한다. SLO보다 느슨한 값을 설정하면 threshold가 실패하지 않으므로 정보를 제공하지 못한다.

이 기준을 통과하는 최대 도착률이 해당 시나리오의 처리 한계이며, 시나리오별로 이 값 하나가 결론이다.

### 5.2 실패율 집계

`http_req_failed`는 5xx와 타임아웃만 집계한다. 재고 부족(400)과 락 획득 실패(409)는 정상 응답이므로 `http.setResponseCallback(http.expectedStatuses(200, 400, 409))`으로 제외한다.

제외하지 않으면 시나리오 A의 고부하 구간에서 409가 실패율을 채워 threshold가 의도와 무관한 이유로 실패한다.

### 5.3 p99 인용 조건

구간별 표본 수는 `도착률 × 40초`다. 150 RPS 구간은 6,000건이며 이 경우 p99는 상위 60건이 결정하므로 노이즈에 가깝다.

p99는 표본 10,000건 이상인 구간, 즉 300 RPS 이상에서만 인용한다. 그 미만 구간은 p95까지만 사용한다.

### 5.4 부하 단계 배치

모든 단계가 통과하면 한계가 최고 단계보다 위에 있다는 사실만 알 수 있고, 모두 실패해도 마찬가지다. 최소 한 단계는 통과하고 한 단계는 실패해야 처리 한계를 특정할 수 있다.

결과가 한쪽으로 쏠리면 도착률 값을 조정해 다시 측정한다. 현재 값은 측정에서 A가 500 RPS에서 p95 145ms로 SLO에 근접하는 것이 확인되어 그 위를 겨냥한 것이며, 구현이 바뀌면 다시 옮겨야 한다.

### 5.5 응답 상태 분해

`http_req_duration{status:409}` 등 상태코드별 건수를 요약에 남긴다. 락 획득 실패(409)와 재고 부족(400)은 정상 응답이라 실패율에서 제외되지만, **이 경로는 정상 경로보다 빨리 끝난다.** 비중이 커지면 느린 요청이 실패로 빠져나가면서 p95가 실제보다 좋게 나온다.

`innodb_lock_wait_timeout=2` 설정 때문에 고부하 구간에서 409가 늘어날 수 있으므로 함께 확인한다. 리포트는 409 비중이 1%를 넘으면 경고한다.

### 5.6 구간별 표본 완결성

각 구간의 기대 표본 수는 `도착률 × 40초`다. 실제 표본이 기대치의 95%에 못 미치면 k6가 목표 유입량을 생성하지 못한 것이므로 해당 구간은 무효로 처리하고 값을 읽지 않는다.

워밍업 구간에서만 발생한 폐기는 무효 사유가 아니다. 워밍업은 집계에서 제외되므로, 측정 구간이 모두 완결이면 실행은 유효하다.

이 상황은 도착률을 지나치게 높게 잡았을 때 발생한다. 지연이 늘면 k6가 더 많은 VU를 필요로 하는데 `maxVUs`에 도달하면 이터레이션을 버린다. 이때 기록되는 지연은 서버 응답 시간이 아니라 부하 생성기가 스케줄되지 못한 시간을 포함한다. 실제로 요청 타임아웃을 10초로 설정했음에도 p99가 243초로 기록된 사례가 있었다.

대응은 `maxVUs`를 올리는 것이 아니라 **부하 단계를 임계 구간 주변으로 좁히는 것**이다. VU를 늘리면 부하 생성기가 호스트 자원을 더 소모해 측정 대상이 노트북으로 바뀐다.

## 6. 측정 환경

측정값은 코드가 변경될 때마다 다시 산출한다. 그 시점에 환경 조건이 달라져 있으면 이전 값과 비교할 수 없으므로, 환경 고정이 측정에 선행한다.

### 6.1 통제 범위

호스트는 M1 Pro 8코어 / 16GB이며, Docker Desktop VM은 6 vCPU / 8GB로 설정한다. 기본값인 4 vCPU로는 앱 컨테이너까지 수용할 수 없다.

**통제 불가** — macOS에는 컨테이너를 호스트 코어에 고정하는 수단이 없다. `cpuset`은 VM 내부 vCPU에만 적용되며, 해당 vCPU는 macOS 스케줄러가 일반 프로세스와 동일하게 스케줄링한다.

**통제 가능** — 컨테이너별 CPU·메모리 상한, JVM이 인식하는 코어 수, 부하 생성기 비용.

따라서 목표는 운영 하드웨어 재현이 아니라 실행 간 조건을 일치시키는 것이며, 산출물은 절대 처리량이 아니라 비율이다.

### 6.2 자원 배분

앱도 컨테이너에서 실행한다. 호스트에서 `bootRun`으로 기동하면 자원 상한을 걸 수단이 없고, Gradle 데몬이 코어를 함께 사용하는데 그 사용량이 실행마다 다르다.

| 프로세스 | 위치 | 상한 |
|---|---|---|
| MySQL | VM | `cpus: 2.0` |
| 앱 | VM | `cpus: 2.0` |
| Redis | VM | `cpus: 1.0` (유휴) |
| k6 | 호스트 | 약 1코어 (실측 필요) |

VM 6코어(여유 1 포함)와 호스트 2코어로 합계 8코어를 넘지 않는다. 실제 상한값은 `docker-compose.bench.yml`에 정의한다.

JDK 21은 컨테이너 인식이 기본 활성화되어 있어 `availableProcessors()`가 `cpus` 값을 반환한다. Virtual Thread 캐리어 풀과 GC 스레드 수가 이에 맞춰 결정되므로 `-XX:ActiveProcessorCount`를 별도로 지정할 필요가 없다.

힙은 `-XX:InitialRAMPercentage`와 `-XX:MaxRAMPercentage`를 동일하게 설정해 측정 중 리사이즈를 방지하고, `-XX:+AlwaysPreTouch`로 기동 시점에 페이지를 미리 확보한다.

앱을 컨테이너에 두면 VM 경계 통과 횟수도 줄어든다. 호스트에서 기동하면 요청당 DB 왕복 2~3회가 모두 경계를 넘지만, 컨테이너에 두면 경계를 넘는 것은 k6에서 앱으로 가는 1회뿐이고 DB 왕복은 VM 내부에서 처리된다.

사용하지 않는 컨테이너도 함께 기동한다. 실행마다 컨테이너 구성이 달라지면 그 차이가 결과에 반영되기 때문이며, 유휴 상태의 비용은 무시할 수준이다.

### 6.3 `innodb_flush_log_at_trx_commit`

이 설정은 커밋마다 fsync 수행 여부를 결정한다. Docker Desktop의 VM 디스크에서 fsync 지연은 밀리초 단위로 변동하므로, 기본값 `1`에서는 행 경합이 아니라 fsync를 측정하게 될 수 있다.

첫 측정 시 `1`과 `2`로 각각 실행해 격차를 확인한다.

- 격차가 작으면 병목은 경합이다. `1`을 유지한다.
- 격차가 크면 현재 측정 대상은 디스크다. 리포트에 이를 명시한다.

어느 값을 선택하든 이후 모든 실행에서 동일하게 사용한다.

### 6.4 환경 스탬프

결과 파일과 함께 다음 정보를 기록한다. 이 기록이 없으면 해당 측정값은 이후 비교에 사용할 수 없다.

```
date                     2026-08-23
git sha                  387e45e
host                     M1 Pro 8core / 16GB / macOS 15.5
docker vm                6 vCPU / 8GB
mysql cpus               2.0
app cpus                 2.0
jvm                      Java 21, MaxRAMPercentage=70, G1GC
flush_log_at_trx_commit  1
lock_wait_timeout        2
connection pool max      20
k6                       v0.5x, 호스트 실행
result A                 340 RPS @ p95<200ms  (3회 중앙값, 편차 4%)
result B                 2,900 RPS @ p95<200ms
경합 비용                 8.5배
```

`date`와 `git sha` 외의 항목이 변경되었다면 이전 값을 사용하지 않고, 이전 커밋을 체크아웃해 다시 측정한다.

### 6.5 유효성 조건

다음 중 하나라도 충족하지 못하면 해당 실행 결과는 폐기한다.

| 조건 | 확인 방법 | 위배 시 의미 |
|---|---|---|
| `dropped_iterations == 0` | k6 요약 | k6가 목표 부하를 생성하지 못했다. 측정 대상이 k6였다 |
| 구간별 표본 ≥ 기대치의 95% | 리포트의 `무효` 표시 | 같은 원인. 5.5절 참조 |
| 호스트 CPU idle > 15% | 실행 중 `top` | 장비가 포화 상태다. 측정 대상이 노트북의 한계였다 |
| k6 CPU < 1코어 | 실행 중 `top` | 부하 생성기가 앱과 코어를 경합한다 |
| `http_req_failed` ≈ 0 | k6 요약 | 5xx가 섞였다. 에러 경로는 정상 경로보다 저렴하므로 지연이 실제보다 좋게 나온다 |
| 3회 편차 < 15% | 직접 계산 | 배경 잡음이 측정하려는 차이보다 크다 |

### 6.6 이 환경의 한계

앱, DB, 부하 생성기가 노트북 한 대에서 동작하며 앱과 DB는 동일한 VM 안에 있다. 따라서 여기서 산출된 절대 처리량은 외부에 인용할 수 없다.

이 환경에서 정당한 진술은 다음 형태뿐이다.

> 동일 조건에서 이번 측정이 이전 측정보다 k배 더 견뎠다.

절대 수치가 필요해지면 리눅스 단독 장비로 이전하고 k6를 별도 장비에서 실행한다.

## 7. 서버 설정 제약

시나리오 A는 재고 행 하나에서 병목이 발생해야 하고, 시나리오 B는 어느 지점에서도 병목이 없어야 한다. 아래 설정이 그 두 조건을 만든다.

| 설정 | 값 | 대상 | 근거 |
|---|---|---|---|
| `innodb_lock_wait_timeout` | `2` | A | 기본값 50초에서는 직렬화된 행에 고부하가 유입될 때 대기 큐가 수십 초로 늘어 p95를 해석할 수 없다. 빠르게 실패해야 포화가 드러난다 |
| Hikari `connection-timeout` | `3000ms` | A | 풀 고갈이 긴 stall로 나타나면 k6의 VU가 모두 묶여 도착률이 유지되지 않는다 |
| k6 `timeout` | `10s` | A | 동일한 이유. 응답하지 않는 요청 하나가 VU를 계속 점유한다 |
| `ulimit -n` | `10240` | B | macOS 기본값이 256인 셸이 있다. 1200 RPS에서 파일 디스크립터가 고갈된다 |
| `max_connections` | 풀 크기 × 2 이상 | B | 풀보다 작으면 연결 거부가 먼저 발생한다 |
| 시드 리셋 | 실행마다 | A | 시나리오 A 1회가 상품 1개에서 78,000건을 소비한다. 반복 시 재고가 소진된다 |

### 7.1 동시성 상한의 위치

`spring.threads.virtual.enabled=true` 설정으로 인해 웹 계층에는 실질적인 동시성 상한이 없다. 요청은 모두 수용되며 부하는 커넥션 풀에 누적된다. 즉 이 시스템의 동시성 상한은 커넥션 풀 크기다.

따라서 풀 크기는 임의로 정하지 않고 아래 절차로 측정한 뒤 고정한다.

### 7.2 시나리오 B의 기준선 자격 검증

B는 경합이 없는 조건의 처리 한계여야 한다. 자원 상한에 먼저 도달하면 기준선으로 사용할 수 없다. 최초 1회 다음을 확인한다.

1. 커넥션 풀 크기를 10 → 20 → 40으로 올리며 B를 측정한다.
2. 처리 한계가 계속 상승하면 현재 병목은 풀이다. 계속 올린다.
3. 처리 한계가 더 이상 변하지 않는 지점에서 멈추고 그 값을 고정한다.
4. MySQL `cpus`를 2.0 → 4.0으로 올려 동일하게 확인한다.

4단계에서 처리 한계가 상승하면 자원 상한을 올려 B가 제약 없이 동작하게 한다. 호스트 코어 예산상 올릴 수 없다면 리포트에 "B는 자원 상한에서의 처리 한계"임을 명시한다. 이 경우 경합 비용이 실제보다 작게 산출된다.

### 7.3 시나리오 A의 측정 대상 검증

역방향 확인이다. A의 처리 한계는 커넥션 풀 크기나 CPU 상한에 반응하지 않아야 한다.

풀 크기를 10에서 40으로 올렸을 때 A의 처리 한계가 함께 상승한다면, A가 측정하던 것은 행 경합이 아니라 풀이다. 이 경우 설정을 조정하고 처음부터 다시 측정한다.

행 하나가 직렬화되므로 풀 크기를 늘려도 A의 처리량은 변하지 않는 것이 정상이다.

### 7.4 확인 불필요 항목

- **MySQL 코어 수 (시나리오 A 한정)** — 단일 행 직렬화이므로 코어를 사용하지 않는다
- **Tomcat 스레드 수** — Virtual Thread 사용으로 의미가 없다
- **버퍼 풀 적중률** — 상품 100행과 예약 테이블뿐이므로 워밍업 후 전량 메모리에 상주한다

## 8. 실행 방법

### 8.1 사전 준비

1. Docker Desktop → Settings → Resources를 CPU 6 / Memory 8GB 이상으로 설정한다. 기본값 4 vCPU로는 앱 컨테이너를 수용할 수 없다.
2. k6를 설치한다. `brew install k6`
3. `ulimit -n 10240`을 설정한다. k6는 호스트에서 실행되며, macOS 기본값 256으로는 1200 RPS 구간에서 파일 디스크립터가 고갈된다. `run.sh`가 확인 후 자동으로 상향한다.

컨테이너 기동은 사전 준비에 포함되지 않는다. `run.sh`가 직접 수행한다.

### 8.2 전체 실행

```bash
bash k6-tests/reserve/run.sh
```

이미지 빌드부터 리포트 생성까지 이 명령 하나로 수행된다. 약 12분이 소요된다.

`run.sh`의 처리 순서는 다음과 같다.

| 순서 | 내용 |
|---|---|
| 1 | `up -d --build --wait` — 앱 이미지 재빌드 후 헬스체크 통과까지 대기 |
| 2 | `ulimit -n` 확인 및 상향 |
| 3 | `reset.sh` — 헬스체크 → 시드 100개 적재 → Redis FLUSHALL → 검증 |
| 4 | 시나리오 A 실행 (워밍업 60초 포함, 집계에서 제외) |
| 5 | `reset.sh` 재실행 |
| 6 | 시나리오 B 실행 |
| 7 | `report.py` — 두 결과를 병합해 HTML 리포트 생성 |

### 8.3 이미지 빌드 정책

앱 이미지는 매 실행마다 다시 빌드한다. 이미지가 갱신되지 않으면 이전 코드를 측정하게 되며, 빌드 여부를 기억에 의존하면 언젠가 어긋난다.

Dockerfile의 `COPY src`가 레이어 캐시를 무효화하므로 코드가 변경되면 콜드 Gradle 빌드 1~2분이 추가된다. 전체 12분 대비 감수할 수 있는 비용이다.

호스트에서 빌드한 jar를 재사용하면 이 시간을 절약할 수 있으나, 해당 jar가 어느 시점의 어떤 코드로 생성되었는지 보장할 수 없다. 반복 주기가 문제가 되면 런타임 전용 Dockerfile로 전환한다.

### 8.4 기동 순서 제약

앱 기동이 시드 적재보다 먼저다. `ddl-auto=create` 설정으로 앱 기동 시 테이블이 재생성되므로, 시드를 먼저 적재하면 기동과 함께 삭제된다. `reset.sh`가 헬스체크로 이 순서를 강제한다.

### 8.5 단일 시나리오 실행

```bash
docker compose -f docker-compose.yml -f docker-compose.bench.yml up -d --build --wait
bash k6-tests/reserve/reset.sh
k6 run k6-tests/reserve/scenario-a-single-row.js
python3 k6-tests/reserve/report.py
```

`reset.sh`를 반드시 함께 실행한다. 시나리오 1회가 상품 1개에서 78,000건을 소비하므로, 리셋 없이 반복하면 뒤쪽 회차는 재고 부족 상태를 측정하게 된다.

버퍼 풀과 연결 상태까지 초기화하려면 실행 사이에 `docker compose restart app mysql redis`를 수행한다.

### 8.6 반복 규칙

3회 이상 실행하고 중앙값과 편차를 함께 기록한다. 3회 값이 340 / 355 / 620과 같이 분산되면 해당 실험은 실패한 것이며, 최댓값 620을 결과로 사용하지 않는다.

두 버전을 같은 날 비교할 때는 교대로 실행한다. 한 버전을 연속으로 실행하면 온도 상승과 백그라운드 프로세스 변화가 뒤쪽 버전에 집중된다.

## 9. 결과 해석

### 9.1 산출물

| 산출물 | 내용 |
|---|---|
| 터미널 출력 | 시나리오별 구간 표, 처리 한계, 유효성 경고 |
| `results/reserve/report.html` | A/B 비교 리포트. 로그 스케일 그래프, 경합 비용, 구간별 표 |
| `results/reserve/*.json` | k6 원본 요약 |

### 9.2 터미널 출력

```
=== A: 단일 행 경합 ===

  rate     요청수      p95        p99     판정
   150       6000     142ms   표본부족     PASS
   300      12000     198ms      410ms    PASS
   600      24000    2410ms     5200ms    FAIL

  처리 한계: 300 RPS  @ p95 < 200ms
```

처리 한계는 p95 < 200ms를 통과하는 최대 도착률이며, 시나리오별로 이 값 하나가 결론이다.

`표본부족`은 해당 구간의 표본이 10,000건 미만이라는 표시다. p99를 상위 소수 건이 결정하므로 인용하지 않는다.

### 9.3 HTML 리포트

`run.sh`가 마지막 단계에서 자동 생성한다. 개별 실행도 가능하다.

```bash
python3 k6-tests/reserve/report.py
open k6-tests/results/reserve/report.html
```

구성은 다음과 같다.

- **상단 카드** — 시나리오별 처리 한계와 경합 비용
- **같은 유입량에서의 경합 비용** — 공통 도착률별 p95 비교. 표본이 모자란 구간은 제외된다
- **그래프** — 도착률 대비 p95. y축이 로그 스케일이므로 100ms와 5,000ms가 한 화면에 표시된다. 초록 점선이 SLO 200ms이며, 속이 빈 점은 SLO를 초과한 구간이다
- **구간별 표** — 중앙값, p95, p99, 최댓값, 판정
- **유효성 경고** — 6.5절의 조건에 위배된 항목

한쪽 시나리오만 실행한 경우 해당 시나리오만 표시된다. 경합 비용은 양쪽 처리 한계가 모두 산출되어야 계산된다.

### 9.4 해석 순서

1. **유효성 경고를 먼저 확인한다.** 경고가 있으면 수치를 읽지 않고 다시 측정한다.
2. **부하 단계가 임계 구간을 포함하는지 확인한다.** 전 구간 통과 또는 전 구간 실패이면 처리 한계를 특정할 수 없다. 도착률을 조정해 다시 측정한다.
3. **시나리오 A의 처리 한계를 읽는다.** 이 값이 최악 조건 성능이다.
4. **경합 비용을 읽는다.** 공통 도착률 표의 최고 구간 비율이다. 1배에 가까우면 경합은 병목이 아니다.
5. **환경 스탬프를 결과와 함께 기록한다.** 기록이 없으면 이후 측정과 비교할 수 없다.
