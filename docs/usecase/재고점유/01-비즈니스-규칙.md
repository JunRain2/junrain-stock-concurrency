## 1. 정의

재고 점유는 사용자의 구매 요청 시점에 상품 재고를 즉시, 확정적으로 차감하는 것이다. "장바구니에 담았다"가 아니라 "그 순간 그 수량만큼 다른 사람이 살 수 없게 만들었다"를 뜻한다. 별도의 예약 만료나 해제 절차는 없다 — 점유는 곧 확정이다.

한 번의 점유가 성공하면 두 가지가 함께 일어난다.

1. `Product.stock`이 요청 수량만큼 감소한다
2. `Reservation`이 생성된다 — 무엇을 얼마나 점유했는지의 기록

## 2. 처리 흐름

`ReserveProducts` 유스케이스가 한 트랜잭션 안에서 순서대로 실행한다.

```
1. 트랜잭션 ID(trxId) 발급        — 구매의 진입점이므로 여기서 발급한다
2. 재고 감소 (StockWriter.decrease)
3. Reservation 저장               — 감소가 성공한 경우에만 실행된다
4. trxId 반환
```

2번이 실패하면 예외가 트랜잭션을 롤백시키므로 3번은 실행되지 않는다. `Reservation`이 존재한다는 것은 곧 해당 재고가 실제로 감소했다는 것과 같다.

반대 방향은 보장하지 않는다. **재고는 감소했는데 `Reservation`이 없는 상태는 존재할 수 있다** — 2번의 응답을 잃었거나 3번이 실패해 롤백된 경우다. 그 재고는 아무도 사지 않았지만 팔 수도 없는 상태로 남는다. 이걸 허용하는 이유와 되돌리는 방법은 [6. 재고 정합](#6-재고-정합)에 있다.

trxId는 재고 감소 이전, 유스케이스 진입 시점에 발급한다. 감소가 실패해도 trxId 자체는 이미 생성된 값이지만 `Reservation`에 저장되지 않으므로 외부로 노출되지 않는다.

## 3. 입력 규칙

한 번의 요청은 여러 상품을 동시에 담을 수 있다. `ReserveProducts.Command` 생성 시점에 검증한다.

| 규칙 | 위반 시 |
|---|---|
| 점유할 상품이 1개 이상 | `IllegalArgumentException` |
| 같은 상품을 중복해서 담을 수 없음 | `IllegalArgumentException` |
| 상품별 수량은 1 이상 | `IllegalArgumentException` (`StockChange` 생성 시점) |

중복 상품을 허용하지 않는 이유는 인프라 구현([MySQL 단일 UPDATE](전략/mysql-case-update-설계.md) 참고)이 상품 ID별로 정확히 한 번씩만 증감을 적용하는 구조이기 때문이다. 중복을 애플리케이션에서 먼저 걸러야 인프라가 "합산해서 적용했는지 마지막 값만 적용했는지" 애매한 상태를 만들지 않는다.

## 4. 원자성

한 요청에 상품이 여러 개 담기면 전부 성공하거나 전부 실패한다 — 일부만 감소하고 나머지는 실패하는 상태는 없다.

재고 부족 판정은 상품별로 독립적이다. 요청한 상품 중 단 하나라도 "현재 재고 − 요청 수량 < 0"이면 그 상품 하나 때문에 전체 요청이 실패로 처리되고, 이미 조건을 만족했던 다른 상품의 재고도 감소하지 않는다.

## 5. 실패 분류

실패는 재시도해서 결과가 달라지는지로 나눈다. 이 기준이 HTTP 상태 코드와 클라이언트의 재시도 여부를 결정한다.

| 원인 | 예외 | 코드 | 상태 | 재시도 |
|---|---|---|---|---|
| 재고 부족 또는 없는 상품 | `StockUnavailableException` | `PRO003` | 400 | 불가 — 재고 상태 자체가 문제이므로 같은 요청을 다시 보내도 같은 결과 |
| 락 획득 실패 (데드락 희생, 락 대기 만료) | `StockUnstableException` | `PRO006` | 409 | 가능 — 재고 상태는 멀쩡한 인프라 일시 장애 |

"재고 부족"과 "상품 없음"은 사용자 응답에서 구분하지 않는다. 둘 다 `PRO003`으로 한데 묶인다. 실패 상세 원인(어떤 상품이 얼마나 모자랐는지)은 로그에만 남고 응답 본문에는 실리지 않는다.

## 6. 재고 정합

### 오버셀과 언더셀은 대칭이 아니다

| | 뜻 | 취급 |
|---|---|---|
| 오버셀 | 있지도 않은 재고를 팔았다 | **금지.** 매 순간 성립해야 하는 불변식 |
| 언더셀 | 팔 수 있는 재고를 못 팔았다 | **허용.** 결국 되돌아오면 된다 |

오버셀은 이미 판 물건을 못 주는 것이라 사후에 되돌릴 방법이 없다. 언더셀은 판매 기회를 늦게 잡는 것뿐이라 나중에 되돌리면 된다. 그래서 확실치 않을 때는 항상 언더셀 쪽으로 틀린다.

이걸 한 줄로 쓰면 이렇다.

```
확정 재고  ≤  초기 재고 − 지금까지 점유된 수량
```

**단방향 오차 불변식이다.** 저장된 재고 값은 진짜 팔 수 있는 양의 하한이지 정확한 값이 아니다.

이 규칙이 있어서 "응답을 못 받았는데 적용됐나?"를 판정할 필요가 없어진다. 적용됐으면 언더셀로 남고, 적용 안 됐으면 아무 일도 없다. 어느 쪽도 오버셀이 아니므로 판정하지 않고 실패로 끝낸다.

### 방향은 한쪽으로만 열려 있다

재고를 다시 늘리는 경로(`StockWriter.increase`)도 존재한다. 취소·환불, 그리고 새어나간 재고를 되돌릴 때 쓴다.

- 증가는 재고 조건(0 미만 방지)에 걸릴 일이 없다 — 늘리는 동작이므로 상한이 없다
- 없는 상품이 섞이면 전부 취소된다 → `ProductNotFoundException`. 부분 증가는 되돌릴 방법이 없다
- 인프라 일시 장애는 감소와 동일하게 `StockUnstableException`(재시도 가능)

| 실패한 연산 | 사후 처리 |
|---|---|
| 감소 | **아무것도 하지 않는다.** 적용됐다면 언더셀로 남고 정합 배치가 되돌린다 |
| 증가 | **성공할 때까지 증가를 반복한다.** 감소로 되돌리지 않는다 |

증가를 감소로 보상하지 않는 이유는 그 사이에 들어온 점유 때문이다. 보상 감소가 실행될 시점에 재고가 이미 0이면 0 미만으로 깎이고, 정합성이 깨진 그 상태가 그대로 오버셀이 된다. **되돌리려다 남의 정상 점유를 밟는 셈이다.**

그래서 증가가 실패하면 사용자에게 실패가 아니라 **지연**으로 알린다. 사용자가 보는 "재고가 아직 안 늘어난" 상태는 누군가 사려다 말았거나 판매자가 재고를 채워 넣는 중인 것과 구분되지 않는다. 재고는 원래 그렇게 움직인다.

### 새어나간 재고는 총량으로 되돌린다

응답 타임아웃, 트랜잭션 롤백, 프로세스 크래시 — 원인이 무엇이든 결과는 하나다. **차감은 됐는데 그에 대응하는 `Reservation`이 없다.** 그래서 어느 연산이 샜는지 판정하지 않고 상품별 총량만 다시 계산한다.

```
기대치 = 초기 재고 − SUM(Reservation의 점유 수량)
delta  = 기대치 − 확정 재고
delta > 0 이면 그만큼 증가. delta ≤ 0 이면 아무것도 하지 않는다
```

`Reservation`이 원장이고 확정 재고는 거기서 파생된 집계값이다. 복제본 두 벌이 수렴하는 관계가 아니라서 충돌 해소도 병합 규칙도 필요 없다 — 복구 방향이 위로만 열려 있기 때문이다.

되돌리는 주체는 **하나여야 한다.** 인라인 보상과 정합 배치를 같이 두면 같은 누수를 둘이 되돌려 이중 증가, 곧 오버셀이 된다. 그래서 트랜잭션 롤백도 인라인으로 보상하지 않고 배치에 맡긴다.

전략별 구현은 다르다 — Redis 전략은 [정합 배치](전략/redis-lua-설계.md#7-정합-배치--총량으로-되돌린다)로 푼다. MySQL 전략은 차감과 `Reservation` 저장이 한 트랜잭션이라 누수 자체가 생기지 않는다.

### 감시할 것

수렴 여부(불리언)가 아니라 **하한 간격의 크기**(연속값)를 본다.

| 지표 | 뜻 |
|---|---|
| `stock.decrease.unknown` | 적용 여부를 모른 채 끝난 차감 횟수. 누수 발생률의 상한 |
| `stock.reconcile.repaired` | 정합 배치가 되돌린 수량의 누계 |
| `stock.reconcile.gap` | 마지막 배치가 관측한 누수 총합 |
