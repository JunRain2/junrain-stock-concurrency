## 1. 측정 대상

재고를 `products.stock`이라는 카운터 한 칸이 아니라 `stock_items` 테이블의 낱개 행으로 물리적으로 쪼갠다. 차감은 상품별로 두 단계다(`SkipLockedStockWriterImpl`).

```sql
SELECT id FROM stock_items
WHERE product_id = ? AND status = 'AVAILABLE'
ORDER BY id
LIMIT ?
FOR UPDATE SKIP LOCKED
```

```sql
UPDATE stock_items SET status = 'SOLD' WHERE id IN (...)
```

핵심은 `SKIP LOCKED`가 **절대 대기하지 않는다**는 것이다. 다른 트랜잭션이 이미 잠근 행은 건너뛰고 그다음 가용 행을 잡는다. 단일 UPDATE 방식(mysql-비관적락-결과.md 1절)에서는 모든 요청이 같은 행 하나를 놓고 줄을 섰지만, 여기서는 각 요청이 서로 다른 행을 잡으므로 **경합 자체가 줄어든다**. 락 순서로 인한 데드락도 구조상 없다.

확보한 행 수가 요청 수량보다 적으면 재고 부족(`StockUnavailableException`, 재시도 불가)이고, 락 획득 자체가 실패하면 `StockUnstableException`(재시도 가능)이다.

측정 당시 `@Primary`가 이 구현에 붙어 있어 예약 경로가 실제로 이 전략을 썼다(현재는 `stock.strategy=skip-locked`로 고른다). 예약 자체(`Reservation` 저장)는 이전 측정들과 동일하게 MySQL에 JPA로 쓰인다.

## 2. 환경 스탬프

앞선 두 측정과 동일한 환경·같은 실행 스크립트로 3회 연속 실행했다. 사다리와 시드 재고는 Redis 3회 측정(redis-원자적차감-결과.md 3·4절)과 같은 값으로 되돌려 비교 가능하게 했다 — 그 문서 10절의 탐색용 상향값이 아니다.

```
date                     2026-08-24
git sha                  e30cf48 (+ 미커밋 SKIP LOCKED 구현)
host                     M1 Pro 8core / 16GB / macOS 26.5.2
docker vm                6 vCPU / 7.75GB
mysql cpus               2.0
app cpus                 2.0
redis cpus               1.0 (이 구현에서는 미사용)
flush_log_at_trx_commit  1
lock_wait_timeout        2
connection pool max      10 (미설정, HikariCP 기본값)
k6                       v0.51.0, 호스트 실행
monitoring               해제
사다리                    A 500/600/700, B 500/600/700/1000
stock_items 시드          상품1 500,000행 / 나머지 99개 각 20,000행 (총 2,480,000행)
반복 횟수                 3회 (22:08–22:39 KST, 연속 실행)
result A                 700 RPS까지 중앙값 기준 전 구간 PASS. 한계 미도달 (3절)
result B                 1,000 RPS까지 중앙값 기준 전 구간 PASS. 한계 미도달 (4절)
경합 비용                 약 1.1배 (600 RPS, 중앙값 기준)
```

`stock_items` 시드가 비대칭인 이유: 낱개 행이라 상품 100개를 전부 500,000행으로 채우면 5천만 행이 되어 시드 자체가 측정 시간을 잡아먹는다. 시나리오 A는 항상 상품 1만 때리므로 상품 1만 500,000행을 채우고, 나머지는 시나리오 B가 쓸 만큼(상품당 20,000행)만 채웠다.

## 3. 시나리오 A 단일 행 경합

| 도착률 | run1 p95 | run2 p95 | run3 p95 | 중앙값 | 판정(중앙값 기준) |
|---|---|---|---|---|---|
| 500 | 291ms (FAIL) | 9ms | 21ms | **21ms** | PASS |
| 600 | 14ms | 288ms (FAIL) | 11ms | **14ms** | PASS |
| 700 | 8ms | 14ms | 9ms | **9ms** | PASS |

표본은 3회 모두 완결(20,000~20,001 / 24,000~24,001 / 28,001건)이라 5.6절 기준을 충족한다. `dropped_iterations`(run1 3,627 / run2 2,959 / run3 1,494)는 사다리 최고 rate로 도는 워밍업 구간의 커넥션 개설 비용으로 보이며, 측정 구간 요청 수가 기대치에 도달했으므로 유효성 판정에서 제외한다.

**3회 사다리 전 구간이 중앙값 기준 PASS다.** FAIL은 두 건뿐인데(run1의 500, run2의 600) 각각 다른 회차·다른 구간에서 한 번씩만 나타났고 인접한 더 높은 부하 구간은 정상이었다 — 7절의 일회성 패턴과 같은 성격이다.

**단일 UPDATE 방식이 정확히 이 구간에서 막혔다는 점이 대비된다.** 그 방식은 처리 한계가 약 645 RPS였고 600 RPS에서 판정이 실행마다 뒤집혔다(mysql-비관적락-결과.md 3절). 같은 사다리에서 SKIP LOCKED는 700 RPS를 9ms로 통과한다. **행 락 병목이 사라졌다** — 재고를 낱개 행으로 쪼개 요청들이 서로 다른 행을 잡게 만든 결과다.

**A의 처리 한계는 이 사다리(≤700 RPS) 안에서 찾지 못했다.**

## 4. 시나리오 B 기준선

| 도착률 | run1 p95 | run2 p95 | run3 p95 | 중앙값 | 판정(중앙값 기준) |
|---|---|---|---|---|---|
| 500 | 28ms | 60ms | 7ms | **28ms** | PASS |
| 600 | 94ms | 62ms | 10ms | **62ms** | PASS |
| 700 | 12ms | 32ms | 11ms | **12ms** | PASS |
| 1000 | 265ms (FAIL) | 22ms | 34ms | **34ms** | PASS |

표본은 3회 모두 완결이다. run2·run3은 사다리 전 구간을 통과해 "한계가 이 위에 있다" 경고가 떴다.

1,000 RPS의 FAIL은 run1 한 번뿐(265ms)이고 run2·run3은 22ms·34ms다. **B의 처리 한계도 이 사다리(≤1,000 RPS) 안에서 찾지 못했다.**

Redis 구현의 같은 사다리 측정(redis-원자적차감-결과.md 4절)에서는 500 RPS가 3회 중 2회 크게 튀어 중앙값이 FAIL이었는데, 이번엔 그 구간이 3회 모두 안정적이다(28/60/7ms). 워밍업 직후 첫 구간이라는 위치는 같으므로, 그 저하가 워밍업-측정 전환 구조 때문이라는 가설(그 문서 9절 3번)은 이번 결과로 약해진다 — 구조 때문이면 여기서도 같이 나타났어야 한다.

## 5. 경합 비용

공통 도착률 중 3회 모두 표본이 완결된 600 RPS를 기준으로 삼는다.

| 기준 | A 중앙값 | B 중앙값 | 배수 |
|---|---|---|---|
| p95 @ 600 RPS | 14ms | 62ms | **0.23배** (A가 더 빠름) |
| p95 @ 500 RPS | 21ms | 28ms | 0.75배 |
| p95 @ 700 RPS | 9ms | 12ms | 0.75배 |

**경합 비용이 사실상 없다.** 단일 행에 요청이 몰려도(A) 100개 상품에 분산돼도(B) 지연 차이가 유의미하지 않고, 600 RPS에서는 오히려 A가 더 빠르게 나왔다. 이 역전은 A가 경합에 강해서가 아니라 B의 600 구간 값(62ms)이 3회 중 한 번 크게 튄 것(94ms)에 끌려 올라간 결과로 보이며, 두 값 다 SLO(200ms) 대비 여유가 커서 배수 해석에 큰 의미를 두기 어렵다.

핵심은 **MySQL에서 관측된 15~18배의 경합 비용(mysql-비관적락-결과.md 5절)이 같은 MySQL 위에서 저장 구조만 바꿔 사라졌다**는 것이다. Redis로 저장소를 옮기지 않고도 같은 효과를 얻었다.

## 6. 세 전략 비교

같은 사다리·같은 SLO에서 세 구현의 시나리오 A(단일 행 경합, 최악 조건) 중앙값이다.

| 도착률 | 단일 UPDATE(행 락) | Redis Lua | SKIP LOCKED |
|---|---|---|---|
| 500 | 72ms | 10ms | 21ms |
| 600 | 143ms | 11ms | 14ms |
| 700 | 무효(포화) | 7ms | 9ms |
| 처리 한계 | 약 645 RPS | ≥700 (미도달) | ≥700 (미도달) |
| 경합 비용 | 15~18배 | 약 1.1배 | 약 1배 이하 |

**SKIP LOCKED는 MySQL을 그대로 쓰면서 Redis와 비슷한 수준에 도달했다.** 단일 UPDATE 대비 600 RPS에서 약 10배 빠르고(143ms → 14ms), 그 방식이 포화됐던 700 RPS도 여유롭게 통과한다.

이 비교는 두 가지를 뜻한다.

1. **병목의 정체가 확정된다.** 단일 UPDATE의 한계는 MySQL이나 fsync 자체가 아니라 **모든 요청이 같은 행 하나를 직렬로 통과해야 한다는 접근 구조**였다. 같은 DB·같은 커밋 비용에서 접근 구조만 바꾸니 한계가 사라졌다.
2. **Redis가 유일한 선택지가 아니다.** 재고 경합 해소만 놓고 보면 저장소를 하나 더 늘리지 않고 MySQL 안에서 해결 가능하다 — 이중 저장소의 정합성·운영 부담(redis-원자적차감-결과.md 6절)을 지지 않아도 된다.

다만 SKIP LOCKED에는 이 측정이 다루지 않은 비용이 있다. 재고 1개당 행 1개라 저장 공간과 시드/재입고 비용이 수량에 비례하고(이번 시드만 248만 행), 재고가 큰 상품일수록 인덱스도 커진다. `products.stock` 한 칸으로 끝나던 것과는 다른 트레이드오프다.

## 7. 미해결 관측

앞선 두 측정에서 반복된 "부하 크기와 무관하게 매 실행 정확히 한 구간에서만 나타나는 일회성 저하"가 여기서도 재현됐다: A run1의 500 RPS(291ms), A run2의 600 RPS(288ms), B run1의 1,000 RPS(265ms). 셋 다 다른 회차·다른 구간이고, 인접한 더 높은 부하 구간은 정상이었다.

**이제 세 가지 서로 다른 구현(단일 UPDATE 행 락 / Redis Lua / SKIP LOCKED)에서 모두 같은 패턴이 재현됐다.** 재고 차감 방식도, 저장소도 전부 다른데 패턴이 같다는 것은 이 저하가 재고 로직과 무관하다는 강한 증거다. 공통 요소는 호스트/Docker VM, k6, 그리고 MySQL Reservation INSERT뿐이다. 원 문서(재고점유.md) 7절의 호스트/VM 스케줄 지연 가설이 가장 유력하다.

## 8. 이 결과의 유효 범위

| 항목 | 상태 |
|---|---|
| 반복 횟수 | 3회. 8.6절 충족 |
| 호스트 전용 사용 | 충족. 모니터링 스택 내리고 측정 |
| 실행 간 편차 | **미충족.** A 500(32배)·600(26배), B 1,000(12배)이 15% 기준을 초과 |
| 표본 완결성 | 전 구간 3회 모두 충족 |
| 처리 한계 | **미확정.** A·B 모두 사다리 위에서 한계에 도달하지 못했다 |

편차가 기준을 넘지만 전부 7절의 일회성 저하에서 나온 것이고, 그 저하를 뺀 나머지 값들은 서로 한 자릿수 ms 안에서 일치한다(예: A 700은 8/14/9ms). 값을 폐기하지 않고 중앙값과 함께 이 한계를 명시하는 쪽을 앞선 두 측정과 동일하게 택했다.

**"처리 한계 미확정"이 이 측정의 가장 큰 공백이다.** 3절·4절의 결론은 "한계가 최소 700(A)·1,000(B) RPS보다 위에 있다"까지이며, 그 값이 얼마인지는 이 측정으로 알 수 없다.

## 9. 다음 측정

1. **완료** — stock_items 시드 추가 후 3회 반복 측정.
2. 사다리를 올려 SKIP LOCKED의 실제 처리 한계를 찾는다. Redis 탐색(redis-원자적차감-결과.md 10절)에서 이미 확인했듯, 이 지점에서는 재고 로직이 아니라 Reservation INSERT가 공유하는 HikariCP 풀(기본값 10, 약 1,000~1,300 RPS)이 먼저 막힐 가능성이 높다 — 풀을 함께 올려가며 재야 재고 전략의 한계가 드러난다. 사다리를 크게 올릴 때는 k6 `maxVUs`도 같이 올리면 앱이 OOM으로 죽으므로(그 문서 10.1절) 단계적으로 올린다.
3. 재고 수량이 큰 상품에서 `SELECT ... LIMIT n FOR UPDATE SKIP LOCKED`의 비용이 어떻게 변하는지 잰다. 이번 시드는 상품 1이 500,000행인데, 잠긴 행을 건너뛰는 비용이 동시 요청 수에 따라 커지는지는 측정하지 않았다.
4. 재입고(`increase`) 경로의 비용을 잰다. 이번 측정은 차감 경로만 다뤘고, 재입고는 수량만큼 INSERT를 도는 구조라 대량 재입고에서 다르게 움직일 수 있다.
