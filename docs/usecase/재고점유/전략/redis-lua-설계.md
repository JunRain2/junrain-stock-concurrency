## 1. 범위

n개 상품의 재고를 한 요청 안에서 원자적으로 차감하는 것, 그리고 그 호출이 타임아웃 났을 때 오버셀 없이 넘어가고 새어나간 재고를 나중에 되돌리는 것까지가 이 문서의 범위다.

전략 간 공통 계약(재시도 가능 여부, 실패 시 사용자 응답, 오버셀/언더셀 취급)은 [비즈니스 규칙](../01-비즈니스-규칙.md)이 정의한다. 이 문서는 그 계약을 Redis에서 "어떻게" 지키는지만 다룬다.

## 2. 문제의 시작점 — 애매한 상태

Redis는 트랜잭션을 지원하지 않는다. 더 큰 문제는 타임아웃이다. 타임아웃이 나면 애플리케이션은 실패로 인식하지만, 실제로는 연산이 이미 적용되어 있을 수 있다.

즉 **"적용 안 됨"과 "적용됐는데 응답만 못 받음"을 구분할 수 없는 애매한 상태**가 생긴다.

| 실제 상태 | 아무것도 안 하면 | 무조건 재시도하면 |
|---|---|---|
| 적용 안 됨 | 재고가 안 줄어든 채 사용자만 실패 | 정상 회복 |
| 적용됨 | 재고가 사라진다 (언더셀) | **이중 차감 = 오버셀** |

## 3. 판정을 포기한다

위 표를 다시 보면, "아무것도 안 하면" 열에 오버셀이 없다. 최악이 언더셀이다.

[비즈니스 규칙 6번](../01-비즈니스-규칙.md#6-재고-정합)이 오버셀은 금지하고 언더셀은 허용하므로, **애매한 상태를 애매한 채로 끝내도 된다.** 판정할 필요가 없다.

이게 이 설계의 전부다. 판정을 포기하는 순간 판정에 필요했던 장치가 통째로 사라진다.

| 장치 | 무엇을 위해 있었나 | 판정을 포기하면 |
|---|---|---|
| op_id + `stock:op:{opId}` 키 | 재적용이 이중 차감되지 않게 | 재적용하는 주체가 없다 → 불필요 |
| WAL(`pending`/`done`) | 판정할 대상을 남기려고 | 판정하지 않는다 → 불필요 |
| 봉인(tombstone) | 판정 뒤 도착한 원본을 막으려고 | 판정 시점이 없다 → 불필요 |
| 유예 창, 회전/압축, 회수 스케줄러 | 위 셋을 굴리려고 | 통째로 불필요 |

남는 것은 **핫패스의 `EVALSHA` 한 번**뿐이다. 요청당 디스크 I/O도, 부가 키도 없다.

대신 새어나간 재고를 되돌릴 방법이 필요하다. 그건 [7번](#7-정합-배치--총량으로-되돌린다)이 총량으로 푼다.

## 4. 폐기한 설계 — op 로그(WAL)

이전 판은 판정을 끝까지 밀어붙였다. 남겨 둘 가치가 있어서 요약해 둔다.

```
1. op_id 발급 (서버에서)
2. pending 기록          ← 로컬 디스크에 append, 연산을 시도하기 전에 먼저
3. Redis 호출 (Lua)      ← 스크립트가 op_id를 기록해 재적용을 멱등으로 만든다
4. done 기록             ← 응답을 받은 뒤에
```

pending인 채 남은 op를 1분마다 도는 회수 배치가 집어, `SET NX`로 적용 여부를 판정하고 미적용이면 그 자리에서 봉인했다. 감소는 되돌리고 증가는 밀어붙였다.

동작은 했다. 문제는 **비용이 트래픽에 비례한다**는 것이었다.

| | 비용 | 어디에 |
|---|---|---|
| `pending` / `done` append 2회 | 디스크 I/O | **사용자 응답 경로 안** |
| `stock:op:{opId}` 키 1개 × TTL 1일 | Redis 메모리 | 요청마다 |
| 봉인·유예·회전·압축·스케줄러 | 코드 300줄 | 유지보수 |

Redis를 고른 이유가 지연시간인데, 그 지연시간을 되사는 구조였다. 게다가 판정 자체가 완전하지도 않았다 — op 키 TTL(1일)이 지난 pending은 "만료됐다"와 "적용된 적 없다"를 구분할 수 없어 손도 못 댔다.

**판정의 정확도를 사려고 핫패스를 판 것이 잘못이었다.** 언더셀을 허용하면 그 정확도가 애초에 필요 없다.

## 5. Lua 스크립트 설계

`src/main/resources/redis/decrease_stock.lua`

```
KEYS[i] = product_stock:{productId}
ARGV[i] = 차감 수량 (KEYS와 같은 순서)
```

```lua
for i = 1, #KEYS do                                            -- 전부 검사
    local current = redis.call('GET', KEYS[i])
    if current == false then return {3, i} end
    if tonumber(current) < tonumber(ARGV[i]) then return {2, i} end
end

for i = 1, #KEYS do                                            -- 통과했을 때만 차감
    redis.call('DECRBY', KEYS[i], ARGV[i])
end
return {0, 0}
```

반환은 항상 `{status, index}` 두 칸이다.

| status | 의미 | 재고 변화 |
|---|---|---|
| 0 | 성공 | 전부 차감 |
| 2 | 재고 부족 | **없음** |
| 3 | 재고 키 없음(상품 없음) | **없음** |

`index`는 실패한 상품의 순번(1-based)이며 실패가 아니면 0이다. status 1은 "이미 처리된 op_id"였다가 멱등키와 함께 사라졌다. 감소·증가 규약을 맞추려고 번호만 비워 둔다.

설계상 짚을 점 셋.

1. **검사 루프를 전부 돈 뒤에 차감 루프를 돈다.** 부분 차감이 아예 생기지 않으므로 보상 로직이 필요 없다.
2. 스크립트 실행 전체가 원자적이라 검사와 차감 사이에 경합이 없다. **오버셀을 막는 것이 이 원자성이고, 이건 매 순간 성립한다.**
3. **같은 명령이 두 번 도착하면 두 번 차감된다.** 멱등키가 없으므로 커넥션 계층 재시도를 반드시 꺼야 한다([8번](#8-재시도를-끈-이유)).

같은 이유로 **n개 상품 전체가 하나의 스크립트 단위**여야 한다. 상품별로 쪼개면 일부만 차감된 상태가 생긴다.

전제: 재고 키가 평문 정수 문자열이라 `GET`/`DECRBY`가 통한다. Redisson 호출 시 `StringCodec`을 쓰지 않으면 키·인자가 직렬화돼 스크립트가 읽지 못한다.

`ponytail:` 단일 노드 전제다. Cluster로 가면 `product_stock` 키에 hash tag가 필요하다.

### 증가 스크립트

`src/main/resources/redis/increase_stock.lua`는 감소의 거울이다. 상한이 없으니 수량 검사 루프가 없고, 없는 상품이 섞였는지만 먼저 전부 확인한 뒤 `INCRBY`를 돈다. 반환 규약은 같다(0 성공 / 3 상품없음).

증가에 멱등키가 없어도 되는 이유는 **부르는 주체가 정합 배치 하나뿐이기 때문이다.** 배치는 매 회차 delta를 다시 계산하므로, 증가가 유실되면 다음 회차가 같은 몫을 다시 집는다. 반복 적용이 아니라 재계산으로 수렴한다.

## 6. 예외 변환

| 결과 | 던지는 예외 | HTTP |
|---|---|---|
| status 0 | 없음 | 200 |
| status 2 / 3 (감소) | `StockUnavailableException` | 400 (재시도 불가) |
| status 3 (증가) | `ProductNotFoundException` | 404 |
| `RedisTimeoutException` | `StockUnstableException` | 409 (재시도 가능) |
| `RedisConnectionException` | `StockUnstableException` | 409 (재시도 가능) |

타임아웃과 연결 실패는 `stock.decrease.unknown` 카운터를 올리고 그대로 끝낸다. **적용됐는지 확인하지 않는다.** 적용됐다면 언더셀로 남고, 그 몫은 배치가 되돌린다.

사용자가 409를 보고 재시도하면 새 요청이다. 그건 새로운 점유 의사이므로 다시 차감하는 것이 옳다 — 앞 요청이 적용됐든 아니든 오버셀이 되지 않는다. 앞 요청이 적용됐다면 그 수량만큼이 언더셀로 남을 뿐이다.

인프라 장애를 500이 아니라 409로 변환하는 이유는 [비즈니스 규칙](../01-비즈니스-규칙.md)의 실패 분류를 따르기 때문이다.

## 7. 정합 배치 — 총량으로 되돌린다

`StockReconciler`가 하루 한 번 돈다(`stock.reconcile.cron`). 사용자 응답 경로 밖이라 자주 돌 이유가 없다.

응답 타임아웃, 트랜잭션 롤백, 프로세스 크래시 — 원인이 무엇이든 결과는 하나다. **차감은 됐는데 그에 대응하는 `Reservation`이 없다.** 그래서 어느 연산이 샜는지 판정하지 않고 상품별 총량만 다시 계산한다.

```
1. actual   = GET product_stock:{id}                    ← Redis를 먼저 읽는다
2. (유예)
3. reserved = SUM(reservations.items[].quantity)        ← MySQL을 나중에
4. delta    = (products.stock − reserved) − actual
5. delta > 0 이면 INCRBY. delta ≤ 0 이면 아무것도 하지 않는다
```

`reservations`가 원장이고 Redis 값은 거기서 파생된 집계값이다.

### 계산이 서 있는 두 전제

1. **`products.stock`은 움직이지 않는다.** Redis 전략에서는 아무도 쓰지 않는다 — `products.stock`을 UPDATE하는 유일한 코드(`JdbcProductRepository.applyStockDeltas`)를 부르는 건 `single-update` 전략의 구현체뿐이고, 그건 redis 전략에서 빈으로 등록되지 않는다.
2. **팔 수 있는 양을 올리는 주체는 배치 하나뿐이다.**

둘 다 코드가 강제하지 않는다. 지금 안 깨지는 이유는 구매 확정·재입고·취소가 아직 없기 때문이다. 깨지는 지점과 지켜야 할 것은 [9절](#9-범위-밖)에 있다.

### 상품이 중간에 추가되는 경우

신규 등록은 id 오름차순 페이징이라 이미 지나간 구간에 끼어들지 않는다. 다만 `ProductRepositoryImpl.save`는 JPA insert 뒤 `SETNX`가 별도 단계라 **재고 키가 아직 없는 창**이 있다. 그 창에 걸린 상품은 건너뛰고 warn만 남긴다 — 0에서 채워 넣으면 존재한 적 없는 재고를 만든다.

### 읽기 순서가 안전성의 전부다

예약 합계를 먼저 읽으면, 그 뒤에 들어온 정상 차감이 delta에 통째로 누수로 잡혀 되돌려진다. **그게 오버셀이다.**

Redis를 먼저 읽으면 반대로 작동한다. 스냅샷 이후 커밋된 예약은 `reserved`를 늘려 기대치를 낮추고, 그만큼 **delta를 과소평가**한다. 덜 되돌리는 것은 언더셀이므로 허용된다. 남은 몫은 다음 회차가 집는다.

`SET`이 아니라 `INCRBY`인 것도 같은 이유다. `SET`은 계산과 반영 사이에 들어온 차감을 지워버린다.

규칙을 일반화하면 이렇다. `delta = products.stock − reserved − actual`에서 **늦게 읽은 값일수록 delta를 낮추는 쪽으로 틀리게** 순서를 잡는다. `actual`을 가장 먼저 읽는 것도, 구매 확정이 붙었을 때 `products.stock`을 가장 나중에 읽어야 하는 것도([9절](#9-범위-밖)) 같은 규칙의 적용이다.

### 유예가 필요한 이유

차감은 `Reservation` 커밋보다 **먼저** 일어난다. 스냅샷 시점에 트랜잭션이 진행 중이면, 그 차감은 `actual`에 이미 반영됐는데 `reserved`에는 아직 안 보인다. 그 상태로 계산하면 정상 점유가 누수로 오인돼 되돌려지고, 뒤이어 커밋되는 순간 오버셀이다.

그래서 스냅샷 뒤 `stock.reconcile.grace-seconds`(기본 60초)만큼 기다렸다가 예약 합계를 읽는다. **이 값은 최대 트랜잭션 수행 시간보다 커야 한다.**

### 되돌리는 주체는 하나여야 한다

인라인 보상과 배치를 같이 두면 같은 누수를 둘이 되돌려 이중 증가, 곧 오버셀이 된다. 그래서 트랜잭션 롤백도 인라인으로 보상하지 않는다.

Redis 차감은 `ReserveProducts`의 `@Transactional` **밖**이라 롤백이 재고를 되돌려주지 않는다. 그 재고는 언더셀로 남고 배치가 집는다. `RedisStockWriterImplTest`가 이걸 명시적으로 단언한다 — 잊고 인라인 보상을 되살리면 테스트가 깨진다.

### 비용

| | |
|---|---|
| 핫패스 | 0. 배치는 사용자 응답 경로 밖이다 |
| Redis | 상품 수 / 청크 크기 만큼의 `MGET` |
| MySQL | `reservations` 전량 스캔 1회 + 상품 페이징 |

`ponytail:` `reservations.items`가 JSON이라 `JSON_TABLE`로 펼쳐 집계한다. 인덱스를 못 타므로 테이블이 커지면 reservation id 워터마크로 상품별 누계를 증분 유지하는 쪽으로 바꾼다.

`ponytail:` 스냅샷을 전량 메모리에 올린다. 상품 수가 문제가 되면 id 구간별로 1·2단계를 쌍으로 돌린다(유예도 구간마다 필요하다).

> 측정 중 확인한 것: Redisson은 스크립트를 EVALSHA로 보낸다. 스크립트가 Redis 캐시에 없는 상태에서 타임아웃이 나면 서버는 NOSCRIPT만 돌려주므로 **아무것도 적용되지 않는다.** 즉 콜드 스타트 직후의 타임아웃은 "미적용"쪽으로 기운다. 판정하지 않는 설계라 어느 쪽이든 결과는 같다.

## 8. 재시도를 끈 이유

`RedissonConfig`에서 `retryAttempts(0)`으로 커넥션 계층의 재시도를 껐다(기본 3회).

**이 설정이 오버셀을 막는 유일한 장치다.** 차감 스크립트에 멱등키가 없으므로, 응답 타임아웃 뒤 커넥션 계층이 같은 명령을 다시 보내면 그대로 두 번 차감된다. 그 순간 재고 값은 실제보다 적어지는 게 아니라 **팔린 양이 부풀어** 오버셀이 된다.

`RedissonConfigTest`가 이 값을 단언한다. 올려야 한다면 멱등키부터 되살려야 한다.

대가도 있다. 장애 중 상처 난 커넥션이 재시도로 가려지지 않고 다음 명령을 그대로 실패시킨다. 그 실패는 409로 나가고 사용자가 다시 시도한다 — 실패 분류가 이미 그렇게 정의돼 있다.

## 9. 범위 밖

현재 미구현이거나 이 문서가 다루지 않는 것들. 첫 항목은 붙을 것이 이미 정해져 있어 따로 뗀다.

### 구매 확정 — `products.stock`이 움직이기 시작하는 시점

확정 시 `products.stock -= q`를 하기로 정했다. 그 순간 [7절](#7-정합-배치--총량으로-되돌린다)의 전제 1이 깨지므로, 붙일 때 아래 셋을 **함께** 지켜야 한다. 하나만 빠져도 오버셀이거나 배치가 죽는다.

**(1) 배치의 예약 집계에서 확정분을 제외한다.**

같은 수량이 `products.stock` 차감과 예약 행에 둘 다 남으면 두 번 빠진다.

```
초기 100, 예약 10, 누수 0  →  actual = 90
확정 3

예약 행 그대로:  expected = 97 − 10 = 87   delta = −3   ← 같은 3을 두 번 뺌
예약 행 제외:    expected = 97 −  7 = 90   delta =  0   ← 정확
```

위쪽이면 **배치가 죽는다.** delta가 확정 누적량만큼 음수로 깔려서, 그보다 작은 진짜 누수는 영영 잡히지 않는다.

**(2) 확정의 두 쓰기는 한 트랜잭션이어야 한다.**

`products.stock -= q`와 예약 제외가 갈라지면, "예약은 확정 처리됐는데 `stock`은 아직 안 깎인" 중간 상태가 읽힌다. 그 상태의 기대치는 q만큼 부풀어 있다.

**(3) 배치가 `products.stock`을 예약 집계보다 뒤에 읽어야 한다.**

지금은 상품 읽기가 1단계(Redis 스냅샷과 함께), 예약 집계가 2단계라 순서가 반대다. 확정이 그 사이에 커밋되면 이렇게 된다.

```
t1  products 읽음        stock = 100          ← 확정 전 값(큼)
t2  확정 커밋            stock = 97, 예약 10 → 7
t3  reserved 읽음        7                    ← 확정 후 값(작음)
    expected = 100 − 7 = 93,  actual = 90  →  INCRBY 3
    실제 팔 수 있는 양 = 90                    →  오버셀 3
```

두 값이 **각각 delta를 키우는 쪽**으로 어긋났다. 순서를 뒤집으면 반대가 된다 — 예약 집계가 확정 전(10), `products.stock`이 확정 후(97)라 `expected = 87`로 과소평가되고, 남은 몫은 다음 회차가 집는다.

즉 이 절에서 지켜야 할 읽기 순서는 이렇게 된다.

```
Redis actual  →  (유예)  →  예약 집계  →  products.stock
        늦게 읽을수록 delta가 작아지는 순서
```

> 한 트랜잭션(REPEATABLE READ)으로 두 읽기를 묶어도 닫힌다. 그쪽은 delta가 정확해지는 대신 긴 읽기 트랜잭션과 격리수준 의존이 붙는다. 어차피 못 집은 몫은 다음 회차가 가져가므로 순서 쪽을 쓴다.

> 확정 트랜잭션은 유예(`grace-seconds`)와 무관하다. 유예는 "차감은 Redis에 반영됐는데 예약은 아직 커밋 전"인 창을 비우는 장치이고, 확정은 Redis를 건드리지 않는다. 진행 중인 확정은 단일 스냅샷 읽기에 아예 보이지 않으므로 (3)만으로 닫힌다.

### 그 밖의 범위 밖

- **사용자향 재고 증가 유스케이스.** 증가 호출자는 정합 배치뿐이다. 취소·환불 API를 붙일 때 "지연됨" 응답을 어떻게 낼지 함께 설계한다.
- **MySQL 재고와의 동기화.** 조회 경로(`GetProductDetail`, `GetProductPage`)는 MySQL을 읽는데, 점유는 Redis만 줄인다. `products.stock`은 구매 확정이 붙기 전까지 초기값 그대로이므로 화면이 stale이다. 확정이 붙어도 확정된 몫만 반영되고 점유 중인 몫은 여전히 안 보인다.
- **재입고·취소·환불.** 팔 수 있는 양을 올리는 두 번째 주체가 생기는 순간 전제 2가 깨진다. `products.stock`만 올리고 Redis는 배치가 따라오게 하면 유지된다(대신 배치 주기만큼 늦다). Redis를 같이 올리면 증가 주체가 둘이 되어 오버셀이다.
- **배치의 다중 인스턴스 실행.** `@Scheduled`가 인스턴스마다 돈다. 둘이 동시에 돌면 각자 delta를 계산해 둘 다 `INCRBY`하므로 이중 증가가 난다. 지금은 단일 인스턴스 전제이고, 붙일 땐 리더 선출이나 분산락이 필요하다.
- **회수 지연의 상한.** 배치 주기가 곧 언더셀이 유지되는 시간이다. `stock.reconcile.gap`이 커지면 주기를 줄이는 것이 첫 대응이다.
