## 1. 범위

n개 상품의 재고를 한 요청 안에서 원자적으로 차감하는 것, 그리고 그 호출이 타임아웃 났을 때 최종적 일관성을 회복할 수 있게 기록을 남기는 것까지가 이 문서의 범위다.

전략 간 공통 계약(재시도 가능 여부, 실패 시 사용자 응답)은 [비즈니스 규칙](../01-비즈니스-규칙.md)이 정의한다. 이 문서는 그 계약을 Redis에서 "어떻게" 지키는지만 다룬다.

**현재 미구현**: 보상(`increase`), pending 회수 스케줄러. [9번](#9-범위-밖) 참고.

## 2. 문제의 시작점 — 애매한 상태

Redis는 트랜잭션을 지원하지 않는다. 더 큰 문제는 타임아웃이다. 타임아웃이 나면 애플리케이션은 실패로 인식하지만, 실제로는 연산이 이미 적용되어 있을 수 있다.

즉 **"적용 안 됨"과 "적용됐는데 응답만 못 받음"을 구분할 수 없는 애매한 상태**가 생긴다. 이 둘은 사후 처리가 정반대다.

| 실제 상태 | 아무것도 안 하면 | 무조건 재시도하면 |
|---|---|---|
| 적용 안 됨 | 재고가 안 줄어든 채 사용자만 실패 | 정상 회복 |
| 적용됨 | 정상 (사용자만 손해) | **이중 차감** |

구분할 수 없으므로, 최종적 일관성을 위해서는 이 실패를 기록해 두고 나중에 정합성을 맞추는 절차가 필요하다.

## 3. 기록 순서 — Write-Ahead로 전환

최초 접근은 "타임아웃이 발생하면 그때 기록한다"였다. 이건 구멍이 있다 — **기록을 시도하는 도중 서버가 죽으면 실패 사실 자체가 증발한다.** 회수할 근거가 남지 않는다.

해법은 순서를 뒤집는 것이다.

```
1. op_id 발급 (서버에서)
2. pending 기록          ← 연산을 시도하기 전에 먼저
3. Redis 호출 (Lua)
4. done 기록             ← 응답을 받은 뒤에
```

크래시든 타임아웃이든, 4번에 도달하지 못하면 pending인 채로 남는다. 그 pending이 곧 회수 대상이다.

`RedisStockWriterImpl.decrease`가 이 순서 그대로다.

## 4. 기록 위치 — 왜 로컬 디스크인가

**DB에 매번 기록하면 원래 Redis를 쓴 목적(DB 왕복 최소화)이 사라진다.** 요청마다 DB INSERT 한 번과 UPDATE 한 번이 붙으면, Redis로 얻은 지연시간 이득을 그대로 반납한다.

**로컬 디스크에 append하는 방식은 네트워크 홉이 없어** 지연시간이 매우 낮고, Redis 호출 응답 속도에 거의 영향을 주지 않는다.

여기서 우려한 "서버가 죽는 경우"는 **프로세스(애플리케이션) crash**를 의미했다. 이 경우:

- `write()`로 커널의 페이지 캐시에 데이터가 넘어간 순간부터는, 애플리케이션 프로세스가 죽어도 **OS가 살아있는 한 그 데이터는 유지된다.**
- 즉 `fsync()`까지 강제하지 않아도, 프로세스 crash 시나리오에서는 로컬 디스크 로그만으로 기록 유실을 막을 수 있다.

> 서버/커널/전원 자체가 죽는 경우는 별개의 리스크다. 더 드문 사건으로 간주하고 이번 설계 범위에서는 감수한다.

### 로그 포맷

`logback-spring.xml`의 `stock-op` 로거가 `logs/stock-op.log`로 뺀다. 탭 구분 2종.

```
2026-08-24T16:44:00,163	pending	{opId}	[{"productId":1,"quantity":2}]
2026-08-24T16:44:00,171	done	{opId}
```

pending은 있는데 done이 없는 op_id = 회수 대상.

## 5. 재적용의 멱등성

타임아웃은 실패가 아니라 응답 유실을 의미한다. 따라서 재시도는 **실제 적용 여부와 무관하게 안전해야** 한다.

| 연산 종류 | 예 | 재적용 |
|---|---|---|
| 멱등 | `SET`, `DEL` | 그대로 재실행 |
| **비멱등** | `INCR`, `DECRBY` | 그대로 재실행하면 이중 차감 |

재고 차감은 비멱등이다. 그래서 **서버에서 생성한 op_id**를 Redis에 기록하고, Lua 스크립트가 "이미 처리된 op_id면 skip"을 판정해 멱등 연산으로 바꾼다.

핵심은 **op_id 체크와 차감이 같은 Lua 실행 안에 있어야 한다**는 것이다. 체크와 차감이 분리되면 그 틈에서 재시도가 겹쳐 이중 차감이 난다.

같은 이유로 **N개 상품 전체가 하나의 스크립트 단위**여야 한다. 상품별로 쪼개면 일부만 재적용되는 상태가 생긴다.

> 구현 노트: 처리 기록을 `processed_ops` SET + `SISMEMBER`로 두는 대신, op_id마다 `stock:op:{opId}` 키를 만들고 `EXISTS`로 판정한다. 판정 비용은 같고, TTL을 op 단위로 걸 수 있어 만료 관리가 단순하다. TTL은 재시도 윈도우보다 넉넉하게 1일(`OP_KEY_TTL_SECONDS`) — 메모리 무한 증가를 막는다.

## 6. Lua 스크립트 설계

`src/main/resources/redis/decrease_stock.lua`

```
KEYS[1]      = stock:op:{opId}
KEYS[2..n+1] = product_stock:{productId}
ARGV[1]      = op 키 TTL(초)
ARGV[2..n+1] = 차감 수량 (KEYS와 같은 순서)
```

```lua
if redis.call('EXISTS', KEYS[1]) == 1 then return {1, 0} end   -- 이미 처리됨

for i = 2, #KEYS do                                            -- 전부 검사
    local current = redis.call('GET', KEYS[i])
    if current == false then return {3, i - 1} end
    if tonumber(current) < tonumber(ARGV[i]) then return {2, i - 1} end
end

for i = 2, #KEYS do                                            -- 통과했을 때만 차감
    redis.call('DECRBY', KEYS[i], ARGV[i])
end
redis.call('SET', KEYS[1], '1', 'EX', ARGV[1])
return {0, 0}
```

반환은 항상 `{status, index}` 두 칸이다.

| status | 의미 | 재고 변화 | op 키 |
|---|---|---|---|
| 0 | 성공 | 전부 차감 | 기록됨 |
| 1 | 이미 처리된 op_id | 없음 | 이미 있음 |
| 2 | 재고 부족 | **없음** | 없음 |
| 3 | 재고 키 없음(상품 없음) | **없음** | 없음 |

`index`는 실패한 상품의 순번(1-based)이며 실패가 아니면 0이다.

설계상 짚을 점 세 가지.

1. **검사 루프를 전부 돈 뒤에 차감 루프를 돈다.** 부분 차감이 아예 생기지 않으므로 보상 로직이 필요 없다.
2. 스크립트 실행 전체가 원자적이라 `EXISTS` 후 `SET` 사이에 경합이 없다.
3. 실패 경로(2, 3)에서는 op 키를 쓰지 않는다. 재시도가 막히지 않는다.

전제: 재고 키가 `RAtomicLong`의 평문 정수 문자열이라 `GET`/`DECRBY`가 통한다. Redisson 호출 시 `StringCodec`을 쓰지 않으면 키·인자가 직렬화돼 스크립트가 읽지 못한다.

`ponytail:` 단일 노드 전제다. Cluster로 가면 `product_stock` 키에 hash tag가 필요하다.

## 7. 예외 변환과 로그 상태 전이

**응답을 받았다는 것 자체가 적용 여부가 확정됐다는 뜻이다.** 그래서 비즈니스 실패도 done으로 닫는다 — 재고가 모자랐다면 스크립트가 아무것도 건드리지 않았으므로 회수할 것이 없다.

pending으로 남는 것은 **적용 여부를 모르는 경우뿐**이다.

| 결과 | 로그 | 던지는 예외 | HTTP |
|---|---|---|---|
| status 0 / 1 | **done** | 없음 | 200 |
| status 2 / 3 | **done** | `StockUnavailableException` | 400 (재시도 불가) |
| `RedisTimeoutException` | **pending인 채** | `StockUnstableException` | 409 (재시도 가능) |
| `RedisConnectionException` | **pending인 채** | `StockUnstableException` | 409 (재시도 가능) |

`InfraException`(→500)이 아니라 `StockUnstableException`(→409)으로 변환하는 이유는 [비즈니스 규칙](../01-비즈니스-규칙.md)의 실패 분류를 따르기 때문이다. 인프라 일시 장애는 사용자가 다시 시도할 수 있는 실패다.

## 8. 재적용 대상의 범위와 비용

Reconciliation job은 **일정 시간 이상 pending으로 남아있는 것만** 스캔 대상으로 삼는다. 정상적으로 done 처리된 케이스는 대상에서 빠진다.

따라서 **재적용 비용은 전체 트래픽이 아니라 실패율에 비례한다.**

이미 처리된 op_id는 스크립트 진입 직후 `EXISTS` 한 번으로 즉시 skip되고 실제 `DECRBY`는 재실행되지 않는다. 즉 "적용됐는데 응답만 못 받은" 케이스를 재시도해도 이중 차감이 나지 않는다.

`stock:op:{opId}` 키의 TTL은 재시도 윈도우보다 조금 긴 시간만 유지해 메모리가 무한히 늘지 않게 한다.

## 9. 범위 밖

현재 미구현이거나 이 문서가 다루지 않는 것들.

- **pending 회수 스케줄러.** 로그는 쌓이지만 아직 아무도 읽지 않는다. 회수 주체·주기·파싱은 다음 단계에서 설계한다.
- **보상(`increase`).** `RedisStockWriterImpl.increase`는 `TODO`다. 현재 호출자가 없다.
- **`ReserveProducts`의 트랜잭션 경계.** 유스케이스는 `@Transactional`이지만 Redis는 그 밖이다. 차감 성공 후 `reservationRepository.save`가 실패하면 재고가 유실된다. 보상을 붙일 때 함께 처리해야 한다.
- **MySQL 재고와의 동기화.** Redis가 진실 원천이 되면서 `products.stock`은 더 이상 줄지 않는다. 조회 경로(`GetProductDetail`, `GetProductPage`)가 MySQL을 읽으므로 화면이 stale이다.
- **로그의 물리적 위치.** 인스턴스별 로컬 디스크이므로 멀티 인스턴스에서는 회수 주체가 각 인스턴스의 로그에 접근할 수 있어야 한다. 컨테이너 재생성 시 유실되지 않도록 볼륨 설계가 필요하다.
