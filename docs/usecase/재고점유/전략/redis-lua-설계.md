# 요구사항

## 1. 요구사항과 제약

### 지켜야 하는 것

- **오버셀 금지** — 있지도 않은 재고를 파는 상태가 **매 순간** 없어야 한다. 사후에 되돌릴 방법이 없다
- **언더셀 허용** — 팔 수 있는 재고를 못 파는 상태는 허용한다. 단 **회복될 때까지**이지 영원히가 아니다
- 부분 차감 없음 — n개 중 하나라도 모자라면 전부 차감되지 않는다
- 되돌릴 근거 — 새어나간 재고를 나중에 정확히 한 번 되돌릴 수 있어야 한다
- 점유에는 기한 — 결제하지 않으면 재고가 돌아와야 한다

앞의 두 줄이 **비대칭**이라는 것이 설계 전체를 결정한다. 확실치 않으면 항상 언더셀 쪽으로 튼다.

### 주어진 제약

- 저장소가 둘 — 재고는 Redis, 예약은 MySQL. 한 트랜잭션으로 못 묶는다. XA도 없다
- **응답 미수신은 판별 불가** — 타임아웃이 지연 때문인지 서버 사망 때문인지 구분할 수 없다
- 단일 노드 Redis — Cluster가 아니라 여러 키를 한 스크립트에서 다룰 수 있다

### 애매한 상태

두 번째 제약이 만드는 문제다. Lua는 원자적이라 부분 적용이 없다 — 적용됐거나 안 됐거나 둘 중 하나다. 문제는 **그 결과를 응답으로 받지 못하는 경우**이고, 비동기 네트워크에서 "지연"과 "사망"은 원리적으로 구분 불가능하다.

| 실제 상태 | 아무것도 안 하면 | 무조건 재시도하면 | 무조건 보상하면 |
|---|---|---|---|
| 적용 안 됨 | 사용자만 실패 | 정상 회복 | **없던 재고가 생김 = 오버셀** |
| 적용됨 | 재고가 사라진다 (언더셀) | **이중 차감 = 오버셀** | 정상 회복 |

오버셀이 없는 열은 첫 번째뿐이다. **모호한 상태에서 낙관하지 않는다**가 첫 번째 원칙이 된다.

# 결정된 설계

## 2. 처리 흐름

```
1. trxId 발급
2. 만료 시각 계산            expireAt = now + hold-minutes
3. Redis (Lua 1회, 원자)     검사 → 차감 → 본문 기록 → 만료 인덱스 등재
4. MySQL                     Reservation 저장               ← 커밋 1회
5. trxId 반환
```

- DB 커밋 **요청당 1회**, Redis 왕복 1회
- `@Transactional` 없음 — 커밋할 쓰기가 하나뿐이다
- 중간 상태 없음 — `Reservation`에 상태 컬럼이 없다. **행이 있으면 차감이 확정된 것**
- 실패 시 정리 없음 — 유스케이스가 예외를 잡지 않는다

3번이 4번보다 **먼저**이고, 만료 시각은 2번에서 한 번만 계산해 두 저장소에 같은 값이 들어간다.

## 3. 저장 구조

**Redis**

| 키 | 타입 | 역할 |
|---|---|---|
| `available_stock:{productId}` | STRING | **예약 가능한 재고.** 남은 값이 곧 아직 점유할 수 있는 양 |
| `reservation:{trxId}` | HASH | 되돌릴 수량(재고키 → 수량). 동시에 멱등 가드 |
| `reservation_expire` | ZSET | member=`trxId`, score=만료 시각(ms) |

**MySQL** — `reservations` 한 행. `trx_id`(unique), `items`(JSON), `expire_at`.

`reservation_expire`가 두 역할을 겸한다. **회수 대상 목록**(`ZRANGE ... BYSCORE LIMIT`이 만기된 것만, O(log N + M))이면서 **"차감이 적용됐다"의 증거**다. 차감과 같은 원자 단위에서 등재되므로 "차감은 됐는데 등재가 안 된" 상태가 존재하지 않는다.

## 4. Lua 스크립트

`src/main/resources/redis/reserve_stock.lua`

```
KEYS[1]   = reservation:{trxId}       예약 본문 + 멱등 가드
KEYS[2]   = reservation_expire        만료 인덱스(ZSET)
KEYS[i+2] = available_stock:{productId}
ARGV[1]   = trxId
ARGV[2]   = 만료 시각(epoch ms). 호출자가 계산해서 넘긴다
ARGV[i+2] = 차감 수량 (KEYS와 같은 순서)
```

```lua
if redis.call('EXISTS', KEYS[1]) == 1 then return {1, 0} end   -- 멱등 가드

local n = #KEYS - 2

for i = 1, n do                                                -- 전부 검사
    local current = redis.call('GET', KEYS[i + 2])
    if current == false then return {3, i} end
    if tonumber(current) < tonumber(ARGV[i + 2]) then return {2, i} end
end

local body = {}                                                -- 통과했을 때만 차감
for i = 1, n do
    redis.call('DECRBY', KEYS[i + 2], ARGV[i + 2])
    body[#body + 1] = KEYS[i + 2]
    body[#body + 1] = ARGV[i + 2]
end
redis.call('HSET', KEYS[1], unpack(body))
redis.call('ZADD', KEYS[2], ARGV[2], ARGV[1])                  -- 만료 시각은 받은 값 그대로

return {0, 0}
```

반환은 항상 `{status, index}`. `index`는 실패한 상품의 순번(1-based)이고 실패가 아니면 0이다.

| status | 의미 | 재고 | 기록 |
|---|---|---|---|
| 0 | 성공 | 전부 차감 | 본문 + 만료 등재 |
| 1 | 같은 `trxId`가 이미 처리됨 | **없음** | 이미 있음 |
| 2 | 재고 부족 | **없음** | **없음** |
| 3 | 상품 없음 | **없음** | **없음** |

전제: 재고 키가 평문 정수 문자열이라 `GET`/`DECRBY`가 통한다. Redisson 호출 시 `StringCodec`을 안 쓰면 키·인자가 직렬화돼 스크립트가 못 읽는다.

단일 노드 전제. Cluster로 가면 세 종류의 키가 같은 슬롯에 있어야 해서 hash tag가 필요하다.

## 5. 실패와 응답

| 결과 | 예외 | HTTP | 예약 행 | Redis |
|---|---|---|---|---|
| status 0 / 1 | 없음 | 200 | 저장된다 | 차감 + 등재 |
| status 2 / 3 | `StockUnavailableException` | 400 (재시도 불가) | 없음 | 아무것도 안 남는다 |
| 타임아웃 / 연결 실패 | `StockUnstableException` | 409 (재시도 가능) | 없음 | **적용됐다면 등재돼 있다** |

**어느 실패에서도 MySQL에 남는 게 없다.** Redis를 먼저 부르고 성공했을 때만 저장하기 때문이다. 그래서 `ReserveProducts`는 예외를 잡지 않는다 — 정리할 것이 없다.

응답 미수신은 `stock.decrease.unknown` 카운터만 올리고 끝낸다. **적용 여부를 확인하지 않는다** — 확인해도 처리가 같다([7절](#7-판정을-없앤-이유)).

사용자가 409를 보고 재시도하면 새 `trxId`의 새 요청이다. 새로운 점유 의사이므로 다시 차감하는 것이 옳고, 앞 요청이 적용됐다면 그 수량은 만료까지 언더셀로 남는다.

## 6. 회수

만기된 등재를 뽑아 **조건 없이** 되돌린다. 판정하지 않는다. 시각이 유일한 트리거인 이유는 [7절](#7-판정을-없앤-이유)에 있다 — 복구 대상 중에는 `trxId`가 Redis에만 남아 아무도 물어봐 주지 않는 건이 섞여 있다.

```
ZRANGE reservation_expire -inf {now} BYSCORE LIMIT 0 100
  → trxId마다 보상 스크립트 1회
```

```lua
-- 회수. KEYS[1] = reservation:{trxId}, KEYS[2] = reservation_expire
if redis.call('ZREM', KEYS[2], ARGV[1]) == 0 then return 0 end   -- 실제로 지운 하나만 통과
local body = redis.call('HGETALL', KEYS[1])
for i = 1, #body, 2 do redis.call('INCRBY', body[i], body[i + 1]) end
redis.call('DEL', KEYS[1])
return 1
```

**구매가 확정되면 그 차감은 영구다.** 되돌릴 일이 없으니 되돌릴 근거도 남길 이유가 없다. 재고는 그대로 두고 회수 대상과 기록을 지운다.

```lua
-- 확정. 재고는 되돌리지 않는다
if redis.call('ZREM', KEYS[2], ARGV[1]) == 0 then return 0 end
redis.call('DEL', KEYS[1])
return 1
```

두 경로가 하는 일은 다르지만 **끝나는 방식은 같다** — `ZREM`으로 청구권을 잡고, 할 일을 하고, 기록을 지운다. 예약의 수명은 점유 기간까지이고 그 뒤에는 Redis에 아무것도 남지 않는다.

이 두 스크립트의 형태가 [3절](#3-저장-구조)의 인덱스와 기록 구조를 결정했다. 되돌릴 수량이 Redis 안에 자기완결적으로 있어야 하고, 가드로 쓸 원자적 제거 연산이 있어야 한다.

# 왜 이렇게 설계했나

## 7. 판정을 없앤 이유

이전 판은 [1절](#1-요구사항과-제약)의 애매함을 **판정으로** 풀었다. 예약을 PENDING으로 먼저 커밋해 사후 확인의 진입점을 만들고, 차감이 성공하면 완료 마커를 남기고, 예약을 HELD로 갱신했다. 스케줄러가 만료된 PENDING을 찾아 마커 유무로 "적용됐는가"를 판정했다.

그 대가가 요청당 커밋 2회다. 그리고 [측정 결과 부록 B](redis-lua-결과.md#부록-b-완료-마커-설계의-병목-진단)이 MySQL이 쓴 시간의 **92%가 `COMMIT`**임을 보였다(문장 자체는 5%). 비싼 것은 무엇을 쓰느냐가 아니라 **몇 번 커밋하느냐**였고, 두 번째 커밋의 존재 이유는 단 하나 — **"이 요청은 정상 종료했다"는 판별자**였다.

그래서 질문을 뒤집었다. **판정 결과가 처리를 바꾸는가?**

바꾸지 않는다. 점유에는 만료가 있고, **만료되면 어차피 되돌린다.** 정상 종료한 예약이든 응답을 못 받고 죽은 요청이든 만료 시점의 처리가 같다. 구분할 이유가 없으니 판별자도 필요 없다.

| 실패 지점 | 만료 인덱스 | 스케줄러 |
|---|---|---|
| Redis 호출 전 | 없음 | — |
| Redis 타임아웃, 실제로 적용됨 | **있음** | 만료 시각에 회수 |
| Redis 타임아웃, 적용 안 됨 | 없음 | — |
| 차감 성공 후 앱 사망 | **있음** | 만료 시각에 회수 (`trxId`가 Redis에만 남는다, 아래) |
| `Reservation` 저장 실패 | **있음** | 만료 시각에 회수 |
| 정상 종료 + 사용자 미결제 | **있음** | 만료 시각에 회수 |

애매함이 사라진 게 아니다. **모르든 알든 처리가 같아져서 물어볼 필요가 없어진 것**이다.

이 결정 하나로 사라진 것들이다.

| | 왜 필요 없어졌나 |
|---|---|
| PENDING 선기록 | 판정 대상이 없다 |
| 완료 마커 `stock_op:{trxId}` | 만료 인덱스 등재가 같은 역할을 하고, 이미 회수에도 쓰인다 |
| HELD 갱신 (두 번째 커밋) | 판별자였다 |
| `ReservationStatus` | 중간 상태를 표현할 이유가 없다 |
| 마커 TTL과 그 부등식 | 판정 가능 기간이라는 개념 자체가 없다 |
| 트랜잭션 경계 논증 | 커밋할 쓰기가 하나로 줄었다 |

마지막 줄이 부수 효과다. 이전 판은 PENDING을 먼저 커밋시키려고 메서드를 감싸면 안 됐고, 왜 그게 "트랜잭션을 쪼개는 것"이 아닌지를 따로 논증해야 했다. 지금 `@Transactional`을 안 붙이는 이유는 단순하다 — **붙일 이유가 없고, 붙이면 Redis 왕복 내내 DB 커넥션을 붙잡는다.**

### 잃어버린 `trxId`는 아무도 물어봐 주지 않는다

회수가 **시각으로 시작되는** 이유다.

`trxId`는 요청이 들어온 뒤 앱 메모리에서 만들어진다. 그리고 [2절](#2-처리-흐름)의 순서대로 **Redis에 먼저** 들어가고 MySQL에는 나중에 들어간다. 그 사이에서 앱이 죽거나 응답이 유실되면 이렇게 된다.

| | |
|---|---|
| 사용자 | `trxId`를 못 받았다. 무엇을 예약했는지 지목할 수 없다 |
| MySQL | 행이 없다. 어떤 조회로도 안 나온다 |
| 로그 | 남아 있을 수는 있지만 일관성 복구의 근거로 쓸 것이 못 된다 |
| **Redis** | **여기에만 있다** |

즉 그 예약을 **물어봐 줄 주체가 없다.** 사용자도, 다른 저장소도, 재시도도 그 `trxId`를 다시 들고 오지 못한다. 요청 기반이나 조회 기반의 복구는 전부 "누군가 언젠가 물어본다"를 전제하는데 그 전제가 여기서는 성립하지 않는다.

그래서 회수가 두 가지를 만족해야 한다.

1. **아무도 부르지 않아도 스스로 시작돼야 한다.** 트리거가 될 수 있는 것은 시간뿐이고, 만료 인덱스가 그 타이머다
2. **Redis 안의 기록만으로 되돌릴 수 있어야 한다.** MySQL에 물어볼 수 없으므로 되돌릴 수량이 `reservation:{trxId}`에 같이 들어 있다([8절 3번](#8-기록이-이-형태인-이유))

이 둘이 [3절](#3-저장-구조)의 저장 구조를 그대로 규정한다. 만료 인덱스가 **언제 시작할지**를, 예약 본문이 **무엇을 되돌릴지**를 담고, 둘 다 차감과 같은 원자 단위 안에서 쓰인다.

**이전 판은 같은 문제를 다르게 풀었다.** PENDING을 Redis 호출 **전에** 커밋해 `trxId`를 MySQL에 심어 뒀다. 그러면 유실되지 않고 스케줄러가 MySQL을 훑어 찾을 수 있다 — **사후 확인의 진입점을 커밋 하나로 산 것**이다.

지금은 그 진입점을 사지 않는다. Redis에 남긴 기록이 스스로 진입점 노릇을 한다. 만료 시각이 되면 인덱스가 그 `trxId`를 뱉으므로 MySQL에 복사본을 둘 이유가 없다. **커밋 하나가 사라진 자리가 정확히 여기다.**

### 왜 재고가 먼저인가

| 순서 | 사이에서 죽으면 | 결과 |
|---|---|---|
| **Redis → MySQL** | 재고는 잡혔는데 예약 행이 없다 | **언더셀.** 만료 시각에 회수 |
| MySQL → Redis | 예약 행은 있는데 재고가 안 줄었다 | **오버셀.** 같은 재고를 두 번 판다 |

되돌릴 수 없는 실패를 한쪽으로 몰아 두는 것이다. **언더셀은 시간이 지나면 낫고 오버셀은 낫지 않는다.** [1절](#1-요구사항과-제약)의 비대칭이 그대로 순서가 됐다.

## 8. 기록이 이 형태인 이유

### 스크립트

1. **검사 루프를 전부 돈 뒤에 쓰기 루프를 돈다.** Lua는 원자적이지만 **롤백이 없다.** 첫 쓰기 뒤에 실패할 수 있는 연산이 남으면 되돌릴 수 없는 "반쯤 적용된 상태"가 생긴다. 검사를 앞에, 쓰기를 뒤에 두면 그 상황이 구조적으로 불가능해진다.
2. **오버셀을 막는 것은 이 원자성이고 매 순간 성립한다.** 같은 이유로 **n개 전체가 하나의 스크립트 단위**여야 한다 — 상품별로 쪼개면 일부만 차감된 상태가 생긴다.
3. **본문 필드를 재고 키 자체로 둔다.** 보상이 productId를 파싱하거나 MySQL을 다시 읽지 않고 `HGETALL` 결과를 그대로 `INCRBY`에 넘긴다. 복구 근거가 Redis 안에서 자기완결적이 된다.
4. **만료 시각은 호출자가 계산해 넘긴다.** 스크립트 안에서 `redis.call('TIME')`으로 찍는 안도 검토했다. 클럭이 하나로 통일되지만 **같은 예약의 만료 시각이 두 개가 된다** — MySQL은 앱 시계, ZSET score는 Redis 시계. 회수 시점과 화면에 보이는 시각이 어긋난다. 앱 인스턴스 간 클럭 편차는 점유 시간이 10분 ± 드리프트가 되는 것뿐이라 정확성에 영향이 없다.
5. **`EXISTS` 가드로 스크립트가 멱등이다.** 같은 `trxId`가 두 번 도착해도 두 번 차감되지 않는다.

### 재시도를 끈 이유가 바뀌었다

`RedissonConfig`가 `retryAttempts(0)`으로 커넥션 계층 재시도를 껐다(기본 3회). **이유가 이전 판과 다르다.**

이전엔 이 설정이 오버셀을 막는 **유일한** 장치였다. 스크립트에 멱등키가 없어 재시도가 그대로 이중 차감이었고, 안전성이 설정값 하나에 걸려 있었다. 지금은 5번 가드가 그 책임을 진다 — **설정에서 스크립트 안으로 옮겨 갔다.** 켜도 안전하다.

그래도 꺼 두는 이유는 부하 쪽이다. Redis가 느려진 상황에서 재시도는 이미 밀린 단일 스레드에 같은 부하를 배로 얹는다. `RedissonConfigTest`가 이 값을 단언하고, 올릴 때 볼 것은 멱등성이 아니라 그 추가 부하다.

### `ZREM` 성공이 회수 가드다

같은 누수를 둘이 되돌리면 이중 증가, 곧 오버셀이다. 실행자 수를 세는 방식으로는 지킬 수 없다 — 재시도와 중복 실행이 늘 가능하다.

"조회한 뒤 복구한다"로 나누면 사이에 원자성이 없어 같은 건을 두 번 복구한다. 그래서 한 Lua로 합치고 `ZREM` 성공을 가드로 쓴다. Redis가 단일 스레드라 전체가 원자적이고, 실제로 제거한 하나만 복구한다. **되돌리는 주체가 하나여야 한다는 규칙을 스케줄러 개수가 아니라 스크립트가 보장한다.**

확정과 만료가 동시에 와도 `ZREM`이 하나만 1을 돌려주므로 자동으로 갈린다. **저장소가 하나면 이 경합이 공짜로 해결된다** — MySQL 쪽 상태로 하려면 행 잠금이 필요하다.

### TTL을 안 걸고, 끝나면 지운다

`reservation:{trxId}`에 TTL을 걸면 회수 스케줄러보다 먼저 사라져 되돌릴 수량을 잃는다. 그 재고는 아무도 복구하지 못하는 고아가 된다. 그래서 만료로 사라지지 않게 두고, **지우는 주체를 회수·확정 스크립트 하나로 고정한다.**

지울 때는 `DEL`이다. 남겨 두면 `EXISTS` 멱등 가드가 더 오래 살긴 한다 — 확정 뒤에 도착한 원래 요청의 늦은 중복도 막힌다. 그 안(tombstone TTL)도 검토했지만 채택하지 않았다. **그 TTL을 정하려면 "재시도 창보다 길다"를 가정해야 하고, 그건 [9절](#9-폐기한-설계들)에서 걷어낸 것과 같은 종류의 시간 전제다.**

가드가 점유 기간까지만 사는 것은 한계가 아니라 맞는 수명이다. 막으려는 것은 **처리 중인 같은 요청의 중복 도착**이고, 그건 점유가 살아 있는 동안 벌어진다. 확정이 끝난 뒤에도 같은 `trxId`가 유효한 새 점유로 살아나는 상황은 커넥션 재시도를 켜지 않는 한 만들어지지 않는다([8절 재시도](#8-기록이-이-형태인-이유)).

### 비용

- 핫패스 성공 — `EXISTS` + `HSET` + `ZADD`. 차감과 같은 스크립트라 왕복은 안 늘어난다
- 핫패스 거절 — `EXISTS` 1회. 검사에서 반환하므로 아무것도 안 쓴다
- Redis 메모리 — **활성 예약당** 해시 1 + ZSET member 1. 확정·회수가 끝난 예약은 남지 않는다
- MySQL — INSERT = **커밋 1회**

> Redisson은 스크립트를 EVALSHA로 보낸다. 캐시에 없는 상태에서 타임아웃이 나면 서버는 NOSCRIPT만 돌려주므로 **아무것도 적용되지 않는다.** 등재도 없으니 회수 대상이 되지 않는다 — 그게 맞는 결과다.

## 9. 폐기한 설계들

### op 로그(WAL)

Redis 호출 **전에** 애플리케이션이 시도를 기록하고 완료 후 지우는 방식(`pending` append → Lua → `done` append).

비용이 트래픽에 비례했다. 응답 경로 안에서 디스크 I/O 2회, 요청마다 Redis 키 1개, 봉인·유예·회전·압축 코드 300줄.

WAL도 Outbox도 아니었다. WAL은 자기 상태를 재생하는 게 목적이고, Outbox의 핵심은 도메인 쓰기와 발행 의도가 **같은 커밋에** 묶이는 것인데 여기선 기록·호출·삭제가 전부 별개 트랜잭션이라 묶일 짝이 없었다.

살아남은 원칙 하나: **애플리케이션이 밖에서 쓰는 기록으로는 "차감과 기록이 같이 일어난다"를 보장할 수 없다.** 그래서 지금은 스크립트 안에서 Redis가 스스로 쓰게 한다.

### 총량 대조 배치

```
기대치 = products.stock − SUM(reservations.items[].quantity)
delta > 0 이면 INCRBY
```

핫패스 비용이 0이지만 **코드가 강제하지 않는 전제 셋** 위에 서 있었다.

| 전제 | 왜 깨지나 |
|---|---|
| `products.stock`은 안 움직인다 | 구매 확정·재입고·취소가 붙는 순간 깨진다 |
| 재고를 올리는 주체는 배치 하나뿐 | 취소·환불 API가 두 번째 주체가 된다 |
| 유예가 점유 트랜잭션 상한보다 길다 | **그 상한이 어디에도 적용돼 있지 않았다** |

셋째가 결정적이다. 느린 요청 하나가 유예 창을 넘기면 진행 중인 정상 점유가 누수로 오인돼 되돌려지고, 그 뒤 커밋되는 순간 오버셀이다. **안전성이 코드가 아니라 주석에 걸려 있었다.**

식 자체는 버리지 않았다. **상시 배치가 아니라 복구 절차로 자리를 옮겼다**([10절](#10-값어치를-하는-조건)).

### 완료 마커 + PENDING 판정

바로 이전 판. 폐기 이유는 [7절](#7-판정을-없앤-이유) 전체다. 측정은 [결과 문서 부록 B](redis-lua-결과.md#부록-b-완료-마커-설계의-병목-진단), 코드는 `backup/marker-design` 브랜치.

### 주문 원장까지 Redis로 (Streams)

예약을 `XADD`로 스트림에 append하고 MySQL이 배치로 소비하는 구조. 커밋이 **0회**가 된다 — 500건이 커밋 1회로 상각된다. 검토했고 채택하지 않았다.

1. **유실 창이 소비자 랙이 된다.** AOF `everysec`은 프로세스 크래시만 덮는다. 데이터셋 자체를 잃으면 아직 MySQL에 안 내려간 주문이 전부 사라진다. 랙을 줄이려면 배치를 작게 해야 하는데 그게 곧 이득 반납이다 — **배치 크기가 유실 창이자 이득이라 다이얼이 하나뿐이다.**
2. **결제·쿠폰·포인트와 한 트랜잭션에 못 묶는다.** 그것들은 MySQL이고 재고 확정은 Redis다. 이 문서가 없앤 경계가 그대로 되살아나고, 함께 장치도 되살아난다.

## 10. 값어치를 하는 조건

### 남은 것은 둘

- **만료 인덱스(ZSET)** — 저장소가 둘이라 MySQL 트랜잭션이 재고를 되돌려 줄 수 없다. 되돌릴 근거를 Redis 안에 따로 들고 있어야 한다
- **회수 스케줄러** — 그 근거를 걷어가는 주체

둘 다 **경계가 있어서** 존재한다. 경계가 없으면 만료된 점유는 그냥 그 트랜잭션 안에서 정리된다.

### 대가가 커밋에서 언더셀 창으로 옮겨 갔다

이전 판의 대가는 커밋 2회, 지금은 1회다. 대신 **죽은 요청의 재고가 점유 시간 전체(10분) 잠긴다.** 이전 판은 판정만 되면 즉시 회수했다.

정확성 문제가 아니라 회수 지연이고, 필요하면 실패를 확실히 아는 경로에서만 보상을 즉시 부르면 좁힐 수 있다. 안 해도 결과는 같다.

### 다른 전략과 나란히

| | 저장소 | 커밋/요청 | 경합 | 일관성 장치 | 원장 |
|---|---|---|---|---|---|
| [MySQL 단일 UPDATE](mysql-case-update-설계.md) | MySQL | 1 | **15~18배** | 없음 | MySQL |
| [MySQL SKIP LOCKED](mysql-skip-locked-설계.md) | MySQL | 1 | 소멸 | 없음 | MySQL |
| **이 문서** | Redis + MySQL | **1** | 소멸 | 만료 인덱스 + 스케줄러 | MySQL |
| 전부 Redis (Streams) | Redis | 0 | 소멸 | 없음 | **Redis** |

**두 번째 줄과의 비교가 이제야 공정해졌다.** 이전 판은 커밋 2회여서 경합을 아무리 잘 없애도 SKIP LOCKED에 커밋 하나를 그냥 내주고 시작했다. 지금은 같다. 그러면 질문이 이렇게 좁혀진다.

> Redis의 `DECRBY`가 MySQL의 행 단위 작업보다 싼 폭이, **만료 인덱스 하나와 스케줄러 하나**의 값보다 큰가.

설계 취향이 아니라 통제 비교로 정할 문제다([결과 문서 13절](redis-lua-결과.md#13-다음-측정)). 이 설계 쪽 수치는 나왔다 — 커넥션 풀 10에서 **A 1,000 RPS / B 1,300 RPS를 p95 10ms 아래로** 처리한다([결과 문서 3절](redis-lua-결과.md#3-어디까지-쟀나)). 다만 **그 위는 못 쟀다** — 앱에 유입 제한이 없어 사다리를 올리면 OOM으로 죽는다([결과 문서 4절](redis-lua-결과.md#4-왜-더-못-쟀나--측정-장비가-먼저-무너진다)). MySQL 두 전략을 같은 호스트 조건에서 다시 재야 비교가 닫힌다.

마지막 줄을 안 택한 이유는 [9절](#9-폐기한-설계들)에 있다. 지금 설계는 원장이 MySQL이라 그 두 대가가 해당하지 않는다. **Redis는 원장이 아니라 파생이다.** 통째로 잃어도 주문은 남고, 재고는 폐기한 총량 대조 식으로 재구축한다.

```
예약 가능한 재고 = products.stock − Σ(활성 점유) − Σ(구매 확정)
```

### 요약

> 저장소를 나누면 원자성이 공짜로 주던 것을 손으로 다시 만들게 된다. 이전 판은 그 목록이 넷이었고(선기록·마커·판정·유예) 값이 커밋 하나였다. **판정할 이유를 없애서 목록을 둘로, 값을 0으로 줄였다.** 남은 둘은 경계 자체의 값이라 경계를 없애지 않는 한 사라지지 않는다.

## 11. 알려진 한계

- **회수 주체에 전적으로 의존한다.** `reservation:{trxId}`에 TTL이 없으므로, 회수가 돌지 않으면 잡힌 재고도 기록도 무한히 쌓인다. 이 설계에서 스케줄러는 부가 기능이 아니라 구성 요소다.
- **회수의 정확성은 확인됐다.** 부하 하에서 재고 총량과 키 개수가 단위까지 맞았다 — 오버셀·재고 유실·이중 회수·고아 기록이 0이다([결과 문서 8절](redis-lua-결과.md#8-회수는-정확하다)). `ZREM` 가드가 설계대로 작동한다.
- **회수 처리량이 건당 순차 왕복으로 막힌다.** 회수기가 `trxId`마다 스크립트를 따로 보낸다. 건당 0.5ms 중 93%가 왕복 지연이라 빈 결과까지 도는 방식으로 바꿔도 상한이 초당 약 2,000건이다. 측정에서 커밋된 설정(100건 / 10초)은 유입의 1%를 걷었다([결과 문서 10절](redis-lua-결과.md#10-회수의-병목은-배치-크기가-아니라-왕복-횟수다)). 그 위가 필요하면 파이프라이닝이나 한 스크립트가 N건을 처리하는 형태여야 한다.
- **언더셀 창이 점유 시간 전체다.** 판정을 안 하므로 죽은 요청의 재고도 만료를 기다린다. 여기에 스케줄러 주기가 더해진 만큼이 회수 지연의 상한이다.
- **확정·취소가 붙으면 `Reservation`에 종료 상태가 생긴다.** 지금 상태 컬럼이 없는 것은 점유 단계에 표현할 중간 상태가 없어서이지, 예약에 상태가 없어서가 아니다.
- **조회 경로가 stale이다.** 조회는 MySQL을 읽는데 점유는 Redis만 줄인다. `products.stock`은 등록 시점 원본 그대로다.
- **스케줄러 다중 인스턴스는 중복 조회를 낸다.** `ZREM` 가드가 이중 복구는 막지만, 같은 대상을 여러 인스턴스가 동시에 뽑는 낭비는 남는다.
