## 1. 측정 대상

재고 감소는 `RedisStockWriterImpl`이 실행하는 Lua 스크립트 한 번으로 수행된다(측정 당시 이름은 `decrease_stock.lua`, 현재는 `reserve_stock.lua`). Redis는 단일 스레드로 명령을 처리하므로 스크립트 실행 자체가 원자 단위이며, 애플리케이션이 별도로 락을 걸지 않는다.

```lua
-- 전부 검사한 뒤에 차감하므로 부분 차감이 생기지 않는다
for i = 2, #KEYS do
    local current = redis.call('GET', KEYS[i])
    if tonumber(current) < tonumber(ARGV[i]) then
        return {2, i - 1}
    end
end
for i = 2, #KEYS do
    redis.call('DECRBY', KEYS[i], ARGV[i])
end
```

호출 전후로 `StockOpLogger`가 `stock-op` 로그에 pending/done을 남긴다(Redis 타임아웃 시 적용 여부를 알 수 없는 요청을 나중에 식별하기 위한 WAL). 예약 자체(`Reservation` 저장)는 이전과 동일하게 MySQL에 JPA로 쓰인다 — 이 측정에서 MySQL은 재고 경합과는 무관하게 매 요청 1건씩 계속 쓰인다.

측정 당시 `RedisStockWriterImpl`이 `@Primary`라 이 저장소가 실제 예약 경로에서 사용됐다. 지금은 전략을 브랜치로 나눠 `main`에 Redis 구현만 남아 있다.

이 구현은 아직 커밋되지 않은 작업 중 코드다(git sha `c2f314d` 기준 워킹 트리 변경분).

> **이 수치는 현재 코드와 맞지 않는다. 재측정 대상이다.** 측정 이후 설계가 두 번 바뀌었다.
>
> 1. WAL(pending/done)과 op 키가 제거되고 총량 대조로 갔다 — 여기 수치에 포함된 요청당 디스크 append 2회가 사라졌으므로 이 방향으로는 **비관적**이다.
> 2. 총량 대조가 PENDING 선기록 + 완료 마커로 바뀌었다 — 요청당 DB 커밋이 1회에서 2회가 되고 Redis 쓰기가 늘었으므로 이 방향으로는 **낙관적**이다. 그 상태를 진단한 것이 [11절](#11-병목-진단--완료-마커-도입-이후)이다.
> 3. 그 판정 구조가 다시 제거되고 **만료 기준 회수**로 바뀌었다([설계 문서 7절](redis-lua-설계.md#7-판정을-없앤-이유)) — 커밋이 다시 1회로 내려갔다. 즉 11절이 지목한 병목의 절반이 사라졌다.
>
> 변화들이 서로 반대 방향이라 부호조차 추정할 수 없다. 3~8절은 1번 시점의 기록으로만 둔다. **현재 코드(커밋 1회)의 측정은 [12절](#12-만료-기준-회수-측정--커밋-1회)에 있다.**

## 3. 시나리오 A 단일 행 경합

| 도착률 | run1 p95 | run2 p95 | run3 p95 | 중앙값 | 판정(중앙값 기준) |
|---|---|---|---|---|---|
| 500 | 17ms | 6ms | 10ms | **10ms** | PASS |
| 600 | 17ms | 11ms | 6ms | **11ms** | PASS |
| 700 | 7ms | 6ms | 1,130ms (FAIL) | **7ms** | PASS |

요청 수는 500/600 RPS 구간에서 3회 모두 기대치(rate×40s)에 사실상 일치한다(20,000~20,001건, 24,000~24,001건). 700 RPS는 run1·run2가 28,001건(100%)이고, run3만 27,138건(96.9%)로 5.6절 완결성 기준(95%)은 겨우 넘는다.

각 실행에서 나온 `dropped_iterations` 경고(run1 6,236 / run2 1,473 / run3 2,127)는 사다리 최고 rate(700)로 60초 도는 워밍업 구간에서 커넥션을 새로 여는 비용 때문으로 보인다 — 측정 구간(500/600/700) 요청 수 자체는 위처럼 기대치에 도달했으므로, 5.6절 "워밍업 구간 드롭은 유효성 판정에서 제외"에 해당한다.

**3회 사다리 전 구간이 중앙값 기준 PASS다.** 유일한 예외는 run3의 700 RPS에서 나온 1,130ms 단발 저하로, 다른 두 실행(6~7ms)과 두 자릿수 이상 차이 난다. **사다리(500~700 RPS) 안에서 A의 처리 한계를 찾지 못했다** — MySQL 재측정에서는 정확히 이 구간(약 645 RPS)이 한계였던 것과 대조적이다.

## 4. 시나리오 B 기준선

| 도착률 | run1 p95 | run2 p95 | run3 p95 | 중앙값 | 판정(중앙값 기준) |
|---|---|---|---|---|---|
| 500 | 6ms | 1,464ms (FAIL) | 252ms (FAIL) | **252ms** | FAIL |
| 600 | 286ms (FAIL) | 10ms | 10ms | **10ms** | PASS |
| 700 | 42ms | 6ms | 52ms | **42ms** | PASS |
| 1000 | 13ms | 8ms | 204ms (FAIL) | **13ms** | PASS |

**500 RPS(사다리의 첫 측정 구간, 워밍업 직후)에서 3회 중 2회가 큰 폭으로 튀었다.** run2는 1,464ms, run3는 252ms로 SLO(200ms)를 넘겼고, 중앙값도 252ms로 FAIL이다. 나머지 구간(600/700/1,000)은 매번 다른 회차에서 한 번씩만 튀는, 지금까지와 같은 일회성 패턴이다.

500 RPS의 저하가 유독 3회 중 2회 반복된다는 점은 다른 구간의 "무작위한 1회성"과 결이 다르다. 워밍업(최고 rate인 1,000 RPS로 60초)이 끝난 직후 곧바로 시작되는 첫 측정 구간이라, 워밍업 종료 시점의 VU 정리·재할당 비용이 500 RPS 구간 초반에 걸쳐 들어갈 가능성이 있다 — 검증하지 않은 가설이다(9절).

600 RPS부터는 안정적으로 PASS다. **B의 처리 한계는 최소 700 RPS까지 확인되고, 1,000 RPS는 중앙값(13ms)은 PASS지만 3회 중 1회(run3, 204ms)가 SLO 경계에 걸려 완전히 확정하기는 이르다.**

## 5. 경합 비용

공통 도착률 600 RPS를 기준으로 삼는다(양쪽 다 3회 중 다수가 안정적으로 통과).

| 기준 | A 중앙값 | B 중앙값 | 배수 |
|---|---|---|---|
| p95 @ 600 RPS | 11ms | 10ms | **약 1.1배** |
| p95 @ 500 RPS | 10ms | 252ms | 0.04배 (A가 더 빠름 — B의 500 구간 이상치 때문, 6절) |

**단일 행에 요청이 몰려도(A) 상품 100개에 분산돼도(B) 지연에 유의미한 차이가 없다.** MySQL에서 관측된 15~18배의 경합 비용이 Redis 구현에서는 사실상 사라졌다. 500 RPS의 역전(B가 A보다 20배 이상 느림)은 경합 때문이 아니라 4절에서 다룬 B 고유의 워밍업 직후 저하 때문이며, 이 수치를 경합 비용으로 해석하면 안 된다.

## 6. MySQL 대비 관찰

MySQL 구현([MySQL 단일 UPDATE 결과](mysql-case-update-결과.md) 6절)의 병목은 행 락 보유 시간(~1.5ms, 커밋 시 fsync 포함)이었고, 이 값이 A의 처리 한계(~645 RPS)를 그대로 결정했다. Redis 구현은 이 병목의 원인 자체가 없다 — Lua 스크립트는 단일 스레드로 마이크로초 단위에 끝나고, 트랜잭션 커밋에 걸리는 fsync도 재고 변경 경로에는 없다(재고는 인메모리 키 변경이지 디스크 커밋이 아니다). 그 결과가 3절의 관찰이다: 같은 사다리(500~700 RPS) 안에서 A가 한 번도 한계에 부딪히지 않았다.

다만 예약 자체는 여전히 MySQL에 `Reservation` 행을 커밋한다. 이 쓰기는 상품별 경합이 없는 단순 INSERT라 행 락 문제는 없지만, HikariCP 풀(기본값 10)을 A와 B가 공유한다. 1,000 RPS 부근에서 나타나는 B의 불안정(4절)이 이 공유 풀 때문인지, 아니면 아래 7절의 호스트 잡음 때문인지는 이번 측정만으로 구분할 수 없다.

## 7. 미해결 관측

MySQL 재측정([MySQL 단일 UPDATE 결과](mysql-case-update-결과.md) 7절)에서 관측한 "부하 크기와 무관하게 매 실행 정확히 한 구간에서만 나타나는 일회성 저하"가 Redis 구현에서도 그대로 재현됐다: A run3의 700 RPS(1,130ms), B run1의 600 RPS(286ms), B run2의 500 RPS(1,464ms), B run3의 500·1,000 RPS.

**구현을 MySQL 행 락에서 Redis 단일 스레드 연산으로 완전히 바꿨는데도 같은 패턴이 재현됐다는 것은, 이 저하가 재고 경합 로직과 무관하다는 강한 증거다.** 두 구현이 공유하는 것은 호스트/Docker VM, k6, 그리고 MySQL에 남아 있는 Reservation INSERT뿐이다. MySQL 결과 7절의 호스트/VM 스케줄 지연 가설이 이번 결과로 더 힘을 얻는다.

B의 500 RPS에서만 3회 중 2회 반복된 것(4절)은 이 일회성 패턴과 별개로 다뤄야 한다 — 워밍업 종료 직후 첫 구간이라는 위치가 고정돼 있어, 무작위 호스트 잡음보다는 워밍업-측정 전환 시점의 구조적 비용일 가능성이 있다.

## 8. 이 결과의 유효 범위

| 항목 | 상태 |
|---|---|
| 반복 횟수 | 3회. 8.6절 충족 |
| 호스트 전용 사용 | 충족. 모니터링 스택 내리고 측정 |
| 실행 간 편차 | **미충족.** A 700(160배), B 500(244배)·600(29배)·1,000(25배)이 15% 기준을 크게 초과 |
| 표본 완결성 | A 700 구간 run3만 96.9%로 경계. 나머지 전 구간 충족 |

편차가 기준을 크게 넘지만, 6·7절에서 그 성격을 설명했다(A: 처리 한계 미도달 상태에서의 호스트 잡음, B: 워밍업 직후 구간의 반복적 저하 + 산발적 호스트 잡음). 값을 폐기하지 않고 중앙값과 함께 유보 범위를 명시하는 쪽을 mysql 재측정과 동일하게 택했다.

## 10. 처리 한계 탐색 (풀 크기 진단)

3절·4절의 사다리(500~1,000 RPS)로는 Redis 구현의 실제 한계를 찾지 못해(3회 모두 사다리 위에서 한계 미도달), 사다리를 올려 한계를 직접 찾았다. 아래는 모두 **단발 실행**(반복 없음)이라 탐색 목적으로만 쓴다 — 8.6절 반복 기준 대상이 아니다.

### 10.1 1차 시도: 크래시

사다리를 A/B 모두 `[700, 1000, 1500, 2000, 3000]`으로, k6 `maxVUs` 상한을 기존 1,500 → 8,000으로 올려 재실행했다. 결과: **앱 컨테이너가 `OutOfMemoryError: Java heap space`로 죽었다.** 힙 사용량이 컨테이너 메모리 상한(1,465MiB)의 98%까지 찬 뒤 각 스레드에서 연쇄적으로 OOM이 터졌고, `http_req_failed`가 99.82%(대부분 10초 타임아웃)에 달했다.

원인은 백프레셔 부재다. HikariCP 풀(기본 10)이 감당 못 하는 속도로 요청이 들어오면, MySQL 락 대기 타임아웃(2초)으로 빠르게 튕기는 MySQL 구현과 달리 이 구현은 커넥션을 그냥 기다린다 — 대기가 쌓일수록 Tomcat 스레드·Virtual Thread·버퍼가 힙에 계속 누적된다. k6 쪽 `maxVUs`를 넉넉히 열어주면 그 누적을 막을 벽이 없어져 힙이 터진다. **한계를 넘겼을 때 "느려짐"이 아니라 "죽음"으로 나타난다는 것 자체가 관찰 결과다.**

컨테이너를 재기동하고 `maxVUs` 상한을 2,500으로, 사다리를 `[1000, 1300, 1600, 1900]`으로 낮춰 재시도했다(아래 10.2). 시드 재고도 이 사다리의 워밍업 소비량에 맞춰 500,000 → 3,000,000으로 올렸다(`seed.sql`).

### 10.2 풀 기본값(10)에서의 한계

| 도착률 | A p95 | A 판정 | B p95 | B 판정 |
|---|---|---|---|---|
| 1000 | 941ms | FAIL | 101ms | PASS |
| 1300 | 80ms | PASS | 4,657ms | FAIL |
| 1600 | 732ms | FAIL | 3,313ms | FAIL |
| 1900 | 2,367ms | FAIL | 2,761ms | FAIL |

판정이 뒤죽박죽인 것(A는 1000에서 FAIL, 1300에서 PASS) 자체가 신호다 — 1,000~1,300 RPS 부근이 한계 바로 옆이라 튀는 것이지, 사다리를 더 올린 1,600·1,900은 명확히 넘어섰다. **풀 10 기준 실제 처리 한계는 대략 1,000~1,300 RPS**로, 6절에서 "행 락 병목이 없다"고 결론 낸 것과 모순되지 않는다 — 이번에 새로 찾은 벽은 재고 경합이 아니라 **Reservation INSERT가 공유하는 HikariCP 풀**이라는 게 아래 10.3에서 확인된다.

### 10.3 풀을 50으로 올렸을 때

같은 사다리로, `docker-compose.bench.yml`에 `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=50`을 임시로 얹어 재실행했다(측정 후 원복 — 이후 baseline과 섞이지 않게).

| 도착률 | A p95 | A 판정 | B p95 | B 판정 |
|---|---|---|---|---|
| 1000 | 19ms | PASS | 328ms | FAIL (이상치) |
| 1300 | 16ms | PASS | 60ms | PASS |
| 1600 | 543ms | FAIL | 17ms | PASS |
| 1900 | 410ms | FAIL | 90ms | PASS |

**B의 처리 한계가 1,000 → 1,900 RPS 이상으로 밀렸다.** A도 1,000 RPS가 941ms(FAIL)에서 19ms(PASS)로 확 좋아졌다. 풀을 5배 늘렸더니 한계가 그만큼 밀린다는 것은, **6절의 결론에 이어 시스템 전체의 상한이 Redis 재고 로직이 아니라 Reservation을 쓰는 MySQL 커넥션 풀(기본값 10)이라는 뜻이다.** B의 1000 RPS FAIL(328ms)은 다른 구간이 다 PASS인 채로 하나만 튄 것이라 7절의 일회성 저하 패턴과 같은 종류로 보인다.

**결론: 지금 기본 설정(풀 10)에서 Redis 구현의 실질 처리 한계는 약 1,000~1,300 RPS다.** 이 한계는 Redis도 MySQL 행 락도 아닌 커넥션 풀 크기가 만든 것이므로, 재고 로직과 무관하게 `application.yml`에 풀 크기를 명시하고 늘리는 것만으로 쉽게 올릴 수 있는 여지가 있다(9절 4번).

## 11. 병목 진단 — 완료 마커 도입 이후

PENDING 선기록 + 완료 마커로 바꾼 뒤 무엇이 천장을 정하는지 확인한 기록이다. **그 설계는 이후 제거됐다**(`backup/marker-design` 브랜치). 이 절을 남기는 이유는 수치가 아니라, 여기서 나온 진단이 지금 설계를 만들었기 때문이다 — 커밋 횟수가 유일한 직렬 자원이라는 것.

**이 절은 처리량 측정이 아니다.** 실행이 1회고 `dropped_iterations`가 있어 [모델 문서](../02-부하테스트-모델.md)의 유효성 조건을 만족하지 않는다. 여기 적는 것은 "얼마나 빠른가"가 아니라 **"무엇이 막고 있는가"**이며, 아래 근거들은 반복 횟수와 무관하게 성립한다.

### 11.1 병목은 Redis가 아니다

같은 실행에서 A(상품 1개 집중)와 B(100개 분산)의 처리 한계가 **둘 다 700 RPS로 같았다.** 700 RPS 지점의 p95는 A 18ms / B 16ms — 경합 비용 약 **1.1배**다.

MySQL 단일 UPDATE에서 15~18배였던 경합이 완전히 사라진 상태 그대로다. 모든 요청이 한 상품에 몰려도 흩어져도 차이가 없으므로, **남은 천장은 경합이 아니라 요청마다 공통으로 치르는 비용**에 있다.

### 11.2 커넥션 풀 고갈이 먼저 드러났다

풀 크기 10에서 앱이 이렇게 죽었다.

```
HikariPool-1 - Connection is not available, request timed out after 30000ms
(total=10, active=10, idle=0, waiting=2744)
```

커넥션 10개를 2744개가 기다렸다. A의 `http_req_failed`가 13.1%였고 그 전부가 이 500이다.

Virtual Thread라 요청이 앱에 전부 들어온 뒤 풀 큐에 쌓인다. **백프레셔가 없다.** k6의 `maxVUs`를 2배로 올렸더니 드롭이 3317 → 13560으로 오히려 늘었는데, 부하 생성기가 모자란 게 아니라 대기열만 길어졌다는 뜻이다.

### 11.3 풀 10 → 20 통제 실험

코드·사다리·VU 설정을 고정하고 `spring.datasource.hikari.maximum-pool-size`만 바꿨다.

| | rate | 풀 10 | 풀 20 |
|---|---|---|---|
| A | 500 | 125ms | 54ms |
| A | 600 | **828ms FAIL** | 43ms PASS |
| A | 700 | 53ms | 18ms |
| A | 에러율 | **13.1%** | 0.28% |
| B | 700 | 28ms | 16ms |
| B | 1000 | **471ms FAIL** | **1550ms FAIL** |

`Connection is not available` 로그는 8건 → **0건**.

읽는 법이 둘로 갈린다.

- **700 이하**: 풀이 지배했다. 요청당 풀 획득이 2회가 되면서 같은 풀 크기의 동시성 상한이 절반이 됐고, 풀을 2배로 주니 그대로 풀렸다
- **1000**: 풀이 아니다. 풀을 늘렸는데 471ms → 1550ms로 **악화**됐다. 큐 제한을 풀면 용량이 느는 게 아니라 대기열이 길어진다. 이 지점의 벽은 풀 뒤쪽이다

### 11.4 벽의 정체 — 커밋

`performance_schema.events_statements_summary_by_digest`로 분해했다.

| 문장 | 호출 수 | 평균 | 총 시간 | 비중 |
|---|---|---|---|---|
| **COMMIT** | 1,645,991 | **2.586ms** | **4256초** | **92%** |
| UPDATE reservations | 833,073 | 0.141ms | 117초 | 2.5% |
| INSERT reservations | 833,632 | 0.138ms | 115초 | 2.5% |
| SET autocommit | 3,315,991 | 0.034ms | 113초 | 2.5% |

**MySQL 시간의 92%가 COMMIT이다.** 문장 자체는 UPDATE와 INSERT가 사실상 같고(0.141 / 0.138ms), 세컨더리 인덱스 재배치·undo 기록이 전부 그 안에 들어 있다. 즉 **UPDATE 문을 최적화할 여지는 전체의 2.5% 안에 있다.**

그리고 커밋 횟수가 문장 수와 맞아떨어진다.

```
COMMIT 1,645,991 ≈ INSERT 833,632 + UPDATE 833,073 = 1,666,705   → 요청당 2회
```

### 11.5 커밋 2.586ms의 내역

| | 커밋당 | 비중 |
|---|---|---|
| redo fsync (`innodb_log_file`) | 0.52ms | 20% |
| binlog fsync (`sql/binlog`) | 0.49ms | 19% |
| **그 외 (group commit 대기)** | **~1.57ms** | **61%** |

`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`이라 커밋마다 fsync 두 벌이다. 그런데 상태 카운터를 보면 이미 잘 상각되고 있다.

```
Innodb_os_log_fsyncs / Com_commit = 1,266,533 / 1,673,016 = 0.76   ← 커밋당 fsync 1회 미만
Innodb_os_log_written / Com_commit = 984 bytes                      ← 트랜잭션이 작다
Binlog_cache_disk_use = 0                                           ← 캐시가 샌 적 없음
```

group commit이 여러 트랜잭션의 fsync를 묶고 있는데도 커밋이 2.586ms인 이유는, 비용의 다수가 fsync 대기가 아니라 **`FLUSH → SYNC → COMMIT` 3단계 파이프라인에서 리더를 기다리는 줄서기**이기 때문이다. (`wait/synch/*` 계측이 꺼져 있어 직접 관측은 못 했고, 위 산술과 카운터로 추정한 값이다.)

이 구분이 처방을 가른다. **fsync는 여러 트랜잭션이 나눠 쓰지만 줄서기는 상각되지 않는다.** 파이프라인에 들어가는 트랜잭션 수가 곧 큐 길이이므로, 요청당 커밋을 2회 내면 큐가 2배가 된다.

| 손댈 곳 | 닿는 구간 | 내구성 |
|---|---|---|
| **커밋 2회 → 1회** | 92% 전체를 절반으로 | **안 판다** |
| `sync_binlog=0` / `flush_log=2` | 39% 구간만 | 판다 |
| UPDATE 문·인덱스 튜닝 | 2.5% 구간 | — |

### 11.6 결론

> 병목은 Redis가 아니라 **예약 쓰기의 커밋 횟수**다. 그리고 두 번째 커밋은 저장소가 갈렸기 때문에 존재한다 — 차감과 예약이 한 트랜잭션이면 "요청이 어떻게 끝났는가"를 따로 증언할 필요가 없다.
>
> Redis는 맡은 일을 다 했다(경합 1.1배). 다만 그 이득의 대가로 청구한 커밋 1회가, 경합이 사라지고 나서 드러난 유일한 직렬 자원을 두 배로 먹는다.

이 결론이 현재 설계를 만들었다. 두 번째 커밋의 존재 이유가 판별자 하나뿐이었으므로, **판정할 이유를 없애서 그 커밋을 지웠다**([설계 문서 7절](redis-lua-설계.md#7-판정을-없앤-이유)).

그래서 이 절의 수치는 더 이상 현재 코드의 것이 아니다. 다만 진단 자체 — 커밋이 92%, 문장이 5%, 경합은 1.1배 — 는 왜 그 변경을 했는지의 근거로 유효하다.

커밋이 1회로 내려가면서 SKIP LOCKED와 커밋 수가 같아졌다. 그러면 남는 질문은 "Redis의 경합 제거가 만료 인덱스 + 회수 스케줄러의 값보다 큰가"뿐이고, 그건 세 전략을 같은 사다리·같은 풀 크기로 나란히 재야 닫힌다([설계 문서 10절](redis-lua-설계.md#10-값어치를-하는-조건)). 아직 없다.

## 12. 만료 기준 회수 측정 — 커밋 1회

판정을 없애 요청당 커밋이 1회가 된 설계([설계 문서 7절](redis-lua-설계.md#7-판정을-없앤-이유))의 첫 측정이다. 11절이 "두 번째 커밋이 천장을 정한다"고 진단했고, 그 커밋을 지운 뒤 무엇이 달라졌는지를 잰다.

### 12.1 환경 스탬프

```
date                     2026-08-29
git sha                  373ab8c (+ 미커밋 만료 기준 회수 구현)
host                     M1 Pro 8core / 16GB / macOS 26.5.2
docker vm                6 vCPU / 7.75GB
app cpus / mem           2.0 / 1500m   (heap = MaxRAMPercentage 70)
mysql cpus / mem         2.0 / 2g
redis cpus / mem         1.0 / 512m
flush_log_at_trx_commit  1
connection pool max      10
k6                       v0.51.0, 호스트 실행
호스트 상태               측정 중 다른 작업 없음 (2회차 이후)
회수 스케줄러             동작 (delay 10s / batch 100). hold 10분 > 시나리오 길이라 실행 중엔 빈 조회만
반복 횟수                 1회 (탐색 목적, 8.6절 반복 기준 미충족)
```

### 12.2 결과

세 차례 실행했다. **회차마다 사다리를 바꿨으므로 회차 간 반복 측정이 아니라 구간 탐색이다.**

| 회차 | 시나리오 | rate | p95 | p99 | 판정 |
|---|---|---|---|---|---|
| **1** | A | 500 / 600 / 700 | 4 / 5 / 5ms | 11 / 32 / 23ms | 전부 PASS |
| **1** | B | 500 / 600 / 700 / 1000 | 4 / 4 / 4 / 6ms | 10 / 32 / 13 / 25ms | 전부 PASS |
| **2** | A | 700 / 1000 / 1300 | — | — | **무효 (앱 OOM)** |
| **3** | A | 700 / 850 / 1000 | 8 / 7 / 7ms | 43 / 46 / 74ms | 전부 PASS |
| **3** | B | 1000 / 1150 / 1300 | 7 / 7 / 9ms | 42 / 30 / 72ms | 전부 PASS |

`dropped_iterations`: 1회차 A 604건(0.7%), 3회차 A 2,294건(1.9%). **B는 두 회차 모두 0건으로 완전히 유효하다.** A는 엄격히는 무효지만, 같은 rate가 두 회차에서 재현된다(A/700 = 5ms → 8ms).

**처리 한계**

| | 확인된 통과 | 상한 |
|---|---|---|
| A 단일 행 | **1,000 RPS @ 7ms** | 1,300 미만 (2회차 워밍업이 여기서 죽었다) |
| B 분산 | **1,300 RPS @ 9ms** | 미확정, 이 위 |

SLO가 p95 200ms인데 1,000~1,300 RPS에서 7~9ms다 — **예산의 4% 안쪽**이다. 그런데도 그 위에서 무너진다. 지연이 아니라 다른 것이 천장을 정한다는 뜻이고, 12.4가 그것이다.

### 12.3 커밋 1회가 실제로 확인됐다

3회차, 새 컨테이너 기준(누적 통계 없음).

| 문장 | 호출 수 | 평균 | 총 시간 | 비중 |
|---|---|---|---|---|
| **COMMIT** | 373,518 | 2.005ms | **749.1초** | **91.9%** |
| INSERT reservations | 374,922 | 0.108ms | 40.5초 | 5.0% |
| SET autocommit | 747,026 | 0.034ms | 25.2초 | 3.1% |

총 요청 375,711건(A 159,708 + B 216,003)이고, Redis `ZADD` 호출수가 375,711로 정확히 일치한다. **커밋 373,518 ≈ 요청 375,711 = 요청당 1회.** 11절의 `UPDATE reservations` 문장은 아예 사라졌다.

커밋 비중은 92%로 11절과 같다. **커밋이 여전히 지배적이지만 횟수가 절반이다.**

### 12.4 벽이 커넥션 풀에서 앱 힙으로 옮겨 갔다

11절의 벽은 풀이었다 — `total=10, active=10, waiting=2744`. 이번 측정에서 **Hikari 타임아웃은 0건**이다. 1,300 RPS에서도 풀이 마르지 않는다. 요청당 커넥션 획득이 2회에서 1회가 됐으니 같은 풀이 두 배의 도착률을 감당한다.

대신 2회차가 새 벽을 드러냈다.

```
java.lang.OutOfMemoryError: Java heap space
[stock-concurrency] [t-handler-13585]
```

스레드 이름의 13,585가 그 시점의 동시 요청 수다. 도착률이 서비스율을 넘으면 큐가 무한히 자라고, **대기 중인 요청 하나가 가상 스레드와 HTTP 컨텍스트만큼의 힙을 잡는다.** 앱 `mem_limit` 1500m에서 이 큐가 힙을 채웠다.

기전은 워밍업이다. `common.js`가 워밍업을 사다리 **최고 rate**로 돌린다.

```js
const warmupRate = Math.max(...rates);
```

그래서 최고 rung이 용량을 넘으면 **측정이 시작되기 전에** 60초 동안 앱을 죽인다. 2회차 A/700이 10,006ms로 나온 것이 그 증거다 — 1회차·3회차에서 같은 700이 5ms, 8ms였다.

> **사다리 상향 시 마지막 rung이 생사를 정한다.** 중간 단계가 아무리 안전해도 워밍업이 최고점으로 돌기 때문이다. 10.1절이 같은 함정을 기록했다.

### 12.5 커밋 내부 구성이 예측대로 바뀌었다

11.5절은 커밋 2.586ms를 fsync 39% / group commit 줄서기 61%로 갈랐고, **"줄서기는 상각되지 않으므로 커밋 횟수를 줄이는 것이 크게 먹힌다"**고 예측했다.

| | 11절 (커밋 2회) | 12절 (커밋 1회) |
|---|---|---|
| `innodb_log_file` | 857.8초 | 241.9초 (0.231ms) |
| `sql/binlog` | 808.5초 | 225.6초 (0.350ms) |
| IO 합계 | 1,666초 | **467.5초** |
| COMMIT 총 시간 | 4,256초 | **749.1초** |
| **IO 비중** | **39%** | **62%** |
| **줄서기 비중** | **61%** | **38%** |

fsync 1회당 지연은 거의 그대로인데(0.247→0.231ms, 0.397→0.350ms) **줄서기 몫이 61%에서 38%로 줄었다.** 커밋 수를 줄이면 파이프라인 대기열이 짧아진다는 예측이 방향과 크기 모두 맞았다.

### 12.6 Redis는 이번에도 결백하다

```
used_memory      54.38M / 512M
evalsha          375,715회, 평균 24.24µs
zadd             375,711회, 평균 5.18µs
SLOWLOG          2건
```

점유 스크립트가 요청당 1회, 24µs다. 이론상 초당 4만 건이라 1,300 RPS와는 자릿수가 다르다.

**경합은 이번에도 안 보인다.** 1,000 RPS에서 A(한 행 집중) 7ms, B(100행 분산) 7ms로 같다. 다만 12.2가 보여주듯 **A가 1,300에서 먼저 죽고 B는 통과한다** — 경합 비용이 지연에는 안 나타나고 천장의 높이로만 나타난다.

### 12.7 무엇을 말할 수 있고 없나

**말할 수 있는 것**

- 요청당 커밋이 2회에서 1회가 됐다 (12.3, 문장 카운트로 직접 확인)
- 커넥션 풀이 더 이상 벽이 아니다 (Hikari 타임아웃 0건)
- 커밋 시간에서 줄서기 몫이 61%→38%로 줄었다 (12.5)
- A는 1,000 RPS, B는 1,300 RPS를 p95 10ms 아래로 처리한다
- 새 벽은 앱 힙이다 (12.4)

**말할 수 없는 것**

11절 수치와의 격차를 **설계 변경만의 공으로 돌릴 수 없다.** 11절은 자기 문서에서 밝혔듯 `dropped_iterations`가 있는 단발 실행이었고, 그때 **호스트 CPU 상태를 모른다.** 이번 회차에서 그 변수 하나가 얼마나 센지 직접 봤다 — 호스트에 다른 작업이 있던 실행에서 B/700이 3,977ms였고, 호스트를 비우자 같은 구성에서 4ms가 나왔다. **1,000배 차이가 코드가 아니라 측정 환경에서 왔다.**

12.3과 12.5는 MySQL 내부 카운터라 이 오염에 덜 민감하고, 12.2의 지연 수치는 민감하다. 전략 간 비교는 여전히 **같은 회차·같은 호스트 조건에서 나란히 재야** 닫힌다.

### 12.8 회수는 정확하다

12.1~12.7은 `hold-minutes: 10`이라 만기가 시나리오(약 4분) 밖이었다. 회수 스케줄러는 `ZRANGE`를 59회 돌려 **전부 빈 결과**를 받았다 — 한 번도 일하지 않았다. 설계 문서가 "스케줄러는 부가 기능이 아니라 구성 요소"라고 선언했으므로 따로 측정한다.

`HOLD_MINUTES=1`로 낮춰 만기를 측정 구간 안으로 넣고, 회수 설정은 커밋된 값 그대로 뒀다(`batch-size: 100`, `delay-seconds: 10`).

**재고 총량이 단위까지 맞는다.** 실행 종료 후 Redis의 `available_stock:{id}` 100개를 전부 더했다.

```
시드          100개 × 500,000       =  50,000,000
예약          172,004건 × 1         =    -172,004     (MySQL reservations 행 수)
회수          4,200건 × 1           =      +4,200
                                       ────────────
기대                                    49,832,196
실측                                    49,832,196   ✓
```

**키 개수도 맞는다.**

```
reservation:{trxId}   167,804        (= 172,004 예약 − 4,200 회수)
available_stock:{id}      100
reservation_expire          1
                      ─────────
DBSIZE                167,905   ✓
```

이 두 항등식이 한 번에 넷을 증명한다.

| | 어떻게 |
|---|---|
| **오버셀 없음** | 총합이 시드를 한 번도 넘지 않았다 |
| **재고 유실 없음** | 모든 차감이 아직 잡혀 있거나 정확히 되돌아왔다. 고아가 0이다 |
| **이중 회수 없음** | 두 번 되돌렸다면 총합이 기대보다 컸을 것이다. `ZREM` 가드가 실제로 작동했다 |
| **고아 기록 없음** | 잔량이 미회수 예약 수와 정확히 일치한다. 되돌리고 안 지운 기록도, 지우고 안 되돌린 기록도 없다 |

**회수 주기도 전부 완주했다.** 42주기 전부 `대상=100건, 회수=100건`이고, Redis 카운터가 `hgetall` 4,200 / `del` 4,200으로 정확히 일치한다. 부분 실패나 재시도가 한 건도 없었다.

부하가 끝난 뒤에도 스케줄러는 계속 돌아 잔량을 비우는 중이다 — 측정 시점 4,000건에서 관측 시점 4,200건으로 늘었다.

> **회수 경로는 설계대로 동작한다.** 아래 12.9~12.11이 지적하는 것은 정확성이 아니라 **속도**다.

### 12.9 다만 유입을 못 따라간다

**5초 간격 관측 (시나리오 B, 유입 500→1,000 RPS)**

| 시각 | 만료 인덱스 잔량 | 누적 회수 |
|---|---|---|
| 01:08:07 | 0 | 1,700 |
| 01:09:12 | 59,485 | 1,700 |
| 01:10:15 | 79,401 | 2,300 |
| 01:11:19 | 104,277 | 2,900 |
| 01:12:23 | 141,322 | 3,600 |
| 01:13:01 | **169,704** | **4,000** |

B가 만든 예약 172,004건 중 회수는 2,300건. **유입의 1.3%다.** 잔량은 선형으로 자랐고 꺾이는 지점이 없다.

```
회수 처리량 = 100건 / 10.05초 = 초당 9.95건
유입        = 초당 1,000건
```

12.8이 보였듯 실패한 건은 없다. **처리량 자체가 두 자릿수 모자란다.**

### 12.10 배치 크기보다 왕복 횟수가 먼저 막는다

`batch-size`를 키우면 될 것 같지만 그렇지 않다. 회수기는 `ZRANGE`로 100건을 한 번에 받은 뒤 **trxId마다 `EVALSHA`를 따로 보낸다.**

로그 타임스탬프 간격이 10.05초다. `fixedDelay`가 10초이므로 100건 처리에 약 50ms — **건당 0.5ms**다. 그런데 Redis가 실제로 쓴 시간은 건당 36µs다(`evalsha` 28.91 + `hgetall` 4.71 + `del` 2.36).

| | 건당 |
|---|---|
| Redis 실행 시간 | 36µs (7%) |
| **왕복 지연** | **약 464µs (93%)** |

즉 회수 속도는 Redis 성능이 아니라 **순차 왕복 횟수**가 정한다. 빈 결과가 나올 때까지 도는 방식으로 바꿔도 상한이 초당 약 2,000건이다. 그 위로 가려면 파이프라이닝(`RBatch`)이나 한 스크립트가 N건을 처리하는 형태여야 한다.

`ZRANGEBYSCORE` 자체는 잔량 169,605건에서도 74µs다. 조회는 병목이 아니다.

### 12.11 회수가 도는 동안의 요청 경로

같은 사다리, 회수만 동작/무동작으로 갈랐다.

| | 회수 무동작 (hold 10분) | 회수 동작 (hold 1분) |
|---|---|---|
| A 500 / 600 / 700 | 4 / 5 / 5ms | 5 / 24 / 14ms |
| B 500 / 600 / 700 / 1000 | 4 / 4 / 4 / 6ms | 6 / 7 / 5 / 12ms |
| `ZADD` 평균 | 5.18µs | 6.40µs |
| Redis 메모리 | 54.38M | 44.93M |

전 구간 PASS를 유지했고 SLO(200ms) 대비 여전히 예산의 12% 안쪽이다. 다만 A/600에서 p95 5→24ms, p99 32→270ms로 튀었다.

**이 차이를 회수 탓으로 돌리기 어렵다.** 회수가 쓴 Redis 명령은 전 구간 합쳐 4,200건이고 요청 경로는 285,371건이다 — 0.0015%다. 각각 단발 실행이라 회차 간 편차와 구분되지 않는다. `ZADD` 평균이 5.18→6.40µs로 오른 것은 ZSET이 커진 영향으로 보이지만, 마이크로초 단위라 p95 20ms 차이를 설명하지 못한다.

### 12.12 이 절이 확정한 것

- 회수 경로는 **정확하게** 동작한다. 재고 총량과 키 개수가 단위까지 맞아 오버셀·재고 유실·이중 회수·고아 기록이 전부 0임을 확인했다 (12.8)
- 커밋된 설정(`100건 / 10초`)은 **초당 10건**이고, 이는 측정한 유입의 1%다
- 병목은 배치 크기가 아니라 **건당 순차 왕복**이다 (건당 0.5ms 중 93%)
- 잔량이 선형으로 자라며 자정하지 않는다. `reservation:{trxId}`에 TTL이 없으므로 회수가 유일한 배출구다

설정을 어떻게 잡아야 하는지는 정하지 않았다. 유입이 회수를 넘는 구간이 얼마나 지속되는지는 확정 유스케이스가 붙어야 정해진다 — 정상 흐름에서는 대부분 구매 확정으로 빠지고 만기 도달분만 회수 대상이 된다. 지금은 확정 경로가 없어 **전량이 만기로 온다.**
