# Redis 원자적 차감 측정 결과

[부하테스트 모델](../02-부하테스트-모델.md)이 정의한 부하 모델과 판정 기준으로 측정한 결과다. 대상은 [현재 설계](redis-lua-설계.md) — Lua 한 번으로 재고를 차감하고 되돌릴 근거를 같은 원자 단위에 남기며, 요청당 MySQL 커밋이 1회다.

설계가 세 번 바뀌었고 각 시점의 측정이 남아 있다. **본문은 현재 설계만 다루고**, 앞선 두 판의 기록은 부록으로 내렸다. 부록을 남기는 이유는 수치가 아니라 그 진단이 지금 설계를 만들었기 때문이다.

|---|---|

# 현재 설계

## 1. 측정 대상

요청 경로가 이렇다.

```
1. trxId 발급
2. 만료 시각 계산
3. Redis (reserve_stock.lua 1회, 원자)   검사 → 차감 → 본문 기록 → 만료 인덱스 등재
4. MySQL   Reservation INSERT             ← 커밋 1회
```

Redis는 단일 스레드라 스크립트 실행 자체가 원자 단위이고, 애플리케이션이 별도로 락을 걸지 않는다. 예약 기록은 MySQL에 JPA로 쓰인다 — 상품별 경합이 없는 단순 INSERT지만 HikariCP 풀을 모든 요청이 공유한다.

만료된 점유는 `ExpiredReservationScheduler`가 주기적으로 회수한다. 이것도 측정 대상이다([8~11절](#8-회수는-정확하다)) — 설계상 부가 기능이 아니라 구성 요소이기 때문이다.

## 2. 환경 스탬프

```
date                     2026-08-29
git sha                  373ab8c + 만료 기준 회수 구현 (208135a~f7df679)
host                     M1 Pro 8core / 16GB / macOS 26.5.2
docker vm                6 vCPU / 7.75GB
app cpus / mem           2.0 / 1500m   (heap = MaxRAMPercentage 70 ≈ 1,050MB)
mysql cpus / mem         2.0 / 2g
redis cpus / mem         1.0 / 512m
flush_log_at_trx_commit  1
connection pool max      10
hold-minutes             10 (3~7절) / 1 (8~11절, 만기를 측정 구간에 넣으려고 낮춤)
reclaim                  batch 100 / delay 10s
k6                       v0.51.0, 호스트 실행
호스트 상태               측정 중 다른 작업 없음
반복 횟수                 회차마다 사다리를 바꾼 구간 탐색. 8.6절 반복 기준 미충족
```

**호스트 상태가 통제 변수다.** 다른 작업이 돌던 실행에서 B/700이 3,977ms였고, 호스트를 비우자 같은 구성에서 4ms가 나왔다. 1,000배 차이가 코드 밖에서 왔다([12절](#12-이-결과의-유효-범위)).

## 3. 어디까지 쟀나

| 시나리오 | 사다리 | p95 | p99 | 판정 |
|---|---|---|---|---|
| A 단일 행 | 500 / 600 / 700 | 4 / 5 / 5ms | 11 / 32 / 23ms | 전부 PASS |
| A 단일 행 | 700 / 850 / **1,000** | 8 / 7 / **7ms** | 43 / 46 / 74ms | 전부 PASS |
| B 분산 | 500 / 600 / 700 / 1,000 | 4 / 4 / 4 / 6ms | 10 / 32 / 13 / 25ms | 전부 PASS |
| B 분산 | 1,000 / 1,150 / **1,300** | 7 / 7 / **9ms** | 42 / 30 / 72ms | 전부 PASS |

**확인된 처리량**

| | 통과 | 상한 |
|---|---|---|
| A 단일 행 | **1,000 RPS @ p95 7ms** | 1,300 미만 |
| B 분산 | **1,300 RPS @ p95 9ms** | **미확정** |

`dropped_iterations`: A는 604건(0.7%) / 2,294건(1.9%)이 남아 엄격히는 무효다. **B는 두 회차 모두 0건으로 완전히 유효하다.** A는 같은 rate가 두 회차에서 재현되므로(700 = 5ms → 8ms) 값 자체는 신뢰한다.

**경합 비용이 안 보인다.** 1,000 RPS에서 A(한 상품에 집중) 7ms, B(100개 분산) 7ms로 같다. MySQL 단일 UPDATE의 15~18배가 완전히 사라진 상태다. 다만 경합이 없는 게 아니라 **천장의 높이로만 나타난다** — A는 1,300에서 죽고 B는 통과한다.

## 4. 왜 더 못 쟀나 — 측정 장비가 먼저 무너진다

**진짜 한계는 못 찾았다.** 사다리를 올리면 앱이 죽는다.

```
java.lang.OutOfMemoryError: Java heap space
[stock-concurrency] [t-handler-13585]
```

A를 `700 / 1,000 / 1,300`으로 올린 회차에서 나왔다. 스레드 이름의 **13,585가 그 시점의 동시 요청 수**다.

기전은 **백프레셔 부재**다. 도착률이 서비스율을 넘으면 큐가 무한히 자라고, 대기 중인 요청 하나가 가상 스레드와 HTTP 컨텍스트만큼의 힙을 잡는다. 유입 제한도 큐 상한도 없어서 앱 `mem_limit` 1500m(힙 약 1,050MB)를 그대로 채운다.

여기에 워밍업이 증폭한다. `common.js`가 워밍업을 사다리 **최고 rate**로 60초 돌린다.

```js
const warmupRate = Math.max(...rates);
```

그래서 최고 rung이 용량을 넘으면 **측정이 시작되기 전에** 앱이 죽는다. 증거가 있다 — 같은 A/700이 회차별로 이렇게 나왔다.

| 그 앞의 워밍업 rate | A/700 p95 |
|---|---|
| 700 | 5ms |
| 1,000 | 8ms |
| **1,300** | **10,006ms** (전 구간 FAIL, 앱 사망) |

세 번째 회차는 700 자체가 문제가 아니라 앞선 워밍업이 이미 앱을 무너뜨린 것이다.

**두 번째 증폭 경로는 부하 생성기다.** 지연이 늘면 k6의 VU가 수천으로 불어나고(상한 5,000), 호스트에서 도는 k6가 컨테이너의 CPU를 뺏는다. 실제로 그 상태의 Redis SLOWLOG에 단일 `ZADD`가 15.6ms로 찍혔다 — 정상일 때는 5µs다. 앱이 느려질수록 측정 장비가 앱을 더 느리게 만드는 되먹임이다.

**그래서 이 하드웨어에서 잴 수 있는 밴드에 상한이 있다.**

| | |
|---|---|
| 측정 가능 | ~1,300 RPS |
| 그 위 | 앱 OOM 또는 생성기-앱 CPU 경합. 어느 쪽이든 설계가 아니라 장비를 재게 된다 |

**측정한 최고점에서 SLO 예산의 4%만 썼다는 것이 핵심이다.** 지연이 한계에 다가가서 무너진 게 아니라, 지연은 멀쩡한데 메모리가 먼저 마른다. **설계의 실제 처리 한계는 1,300 RPS보다 위이고, 얼마인지는 이 장비로 알 수 없다.**

더 올려서 재려면 셋 중 하나가 필요하다.

- 앱 `mem_limit` 상향 — 다만 이전 측정과 비교 불가가 된다
- 유입 제한(큐 상한, 세마포어) 도입 — 넘치면 죽는 대신 429로 튕긴다
- 부하 생성기를 다른 머신으로 분리 — CPU 경합 되먹임 제거

## 5. 커밋 1회 확인

새 컨테이너 기준(누적 통계 없음).

| 문장 | 호출 수 | 평균 | 총 시간 | 비중 |
|---|---|---|---|---|
| **COMMIT** | 373,518 | 2.005ms | **749.1초** | **91.9%** |
| INSERT reservations | 374,922 | 0.108ms | 40.5초 | 5.0% |
| SET autocommit | 747,026 | 0.034ms | 25.2초 | 3.1% |

총 요청 375,711건(A 159,708 + B 216,003)이고 Redis `ZADD` 호출수가 375,711로 정확히 일치한다.

```
COMMIT 373,518  ≈  요청 375,711     → 요청당 1회
```

이전 판에 있던 `UPDATE reservations` 문장은 아예 사라졌다. **커밋이 여전히 MySQL 시간의 92%를 먹지만 횟수가 절반이다.**

## 6. 커밋 내부 구성이 예측대로 바뀌었다

[부록 B](#부록-b-완료-마커-설계의-병목-진단)는 커밋 2.586ms를 fsync 39% / group commit 줄서기 61%로 갈랐고, **"줄서기는 상각되지 않으므로 커밋 횟수를 줄이는 것이 크게 먹힌다"**고 예측했다.

| | 커밋 2회 (부록 B) | 커밋 1회 (현재) |
|---|---|---|
| `innodb_log_file` | 857.8초 (0.247ms) | 241.9초 (0.231ms) |
| `sql/binlog` | 808.5초 (0.397ms) | 225.6초 (0.350ms) |
| IO 합계 | 1,666초 | **467.5초** |
| COMMIT 총 시간 | 4,256초 | **749.1초** |
| **IO 비중** | **39%** | **62%** |
| **줄서기 비중** | **61%** | **38%** |

fsync 1회당 지연은 거의 그대로인데 **줄서기 몫이 61%에서 38%로 줄었다.** 커밋 수를 줄이면 파이프라인 대기열이 짧아진다는 예측이 방향과 크기 모두 맞았다.

**커넥션 풀도 더 이상 벽이 아니다.** 이전 판에서는 `total=10, active=10, waiting=2744`로 풀이 말랐는데, 이번 측정에서 **Hikari 타임아웃 0건**이다. 요청당 커넥션 획득이 2회에서 1회가 되면서 같은 풀이 두 배의 도착률을 감당한다.

## 7. Redis는 병목이 아니다

```
used_memory      54.38M / 512M
evalsha          375,715회, 평균 24.24µs
zadd             375,711회, 평균 5.18µs
SLOWLOG          2건
```

점유 스크립트가 요청당 1회, 24µs다. 이론상 초당 4만 건이라 측정한 1,300 RPS와 자릿수가 다르다. 메모리도 상한의 10%다.

# 회수

`hold-minutes: 10`이면 만기가 시나리오(약 4분) 밖이라 스케줄러가 `ZRANGE`를 59회 돌려 **전부 빈 결과**를 받는다. 회수를 재려고 `HOLD_MINUTES=1`로 낮춰 만기를 측정 구간 안에 넣었다. 회수 설정은 커밋된 값 그대로다(`batch-size: 100`, `delay-seconds: 10`).

## 8. 회수는 정확하다

**재고 총량이 단위까지 맞는다.** 실행 종료 후 `available_stock:{id}` 100개를 전부 더했다.

```
시드          100개 × 500,000       =  50,000,000
예약          172,004건 × 1         =    -172,004     (MySQL reservations 행 수)
회수          4,200건 × 1           =      +4,200
                                       ────────────
기대                                    49,832,196
실측                                    49,832,196   ✓
```

**키 개수도 맞는다.**

```
reservation:{trxId}   167,804        (= 172,004 예약 − 4,200 회수)
available_stock:{id}      100
reservation_expire          1
                      ─────────
DBSIZE                167,905   ✓
```

이 두 항등식이 한 번에 넷을 증명한다.

| | 어떻게 |
|---|---|
| **오버셀 없음** | 총합이 시드를 한 번도 넘지 않았다 |
| **재고 유실 없음** | 모든 차감이 아직 잡혀 있거나 정확히 되돌아왔다. 고아가 0이다 |
| **이중 회수 없음** | 두 번 되돌렸다면 총합이 기대보다 컸을 것이다. `ZREM` 가드가 실제로 작동했다 |
| **고아 기록 없음** | 잔량이 미회수 예약 수와 정확히 일치한다. 되돌리고 안 지운 기록도, 지우고 안 되돌린 기록도 없다 |

`ZREM` 가드는 단위 테스트로만 검증돼 있었는데, **초당 1,000건 유입 하에서 실제로 작동한 증거**가 이것이다.

**회수 주기도 전부 완주했다.** 42주기 전부 `대상=100건, 회수=100건`이고 Redis 카운터가 `hgetall` 4,200 / `del` 4,200으로 일치한다. 부분 실패나 재시도가 한 건도 없었다. 부하가 끝난 뒤에도 스케줄러는 계속 돌아 잔량을 비웠다.

> **회수 경로는 설계대로 동작한다.** 아래 9~11절이 지적하는 것은 정확성이 아니라 **속도**다.

## 9. 회수는 유입을 못 따라간다

**5초 간격 관측 (시나리오 B, 유입 500→1,000 RPS)**

| 시각 | 만료 인덱스 잔량 | 누적 회수 |
|---|---|---|
| 01:08:07 | 0 | 1,700 |
| 01:09:12 | 59,485 | 1,700 |
| 01:10:15 | 79,401 | 2,300 |
| 01:11:19 | 104,277 | 2,900 |
| 01:12:23 | 141,322 | 3,600 |
| 01:13:01 | **169,704** | **4,000** |

B가 만든 예약 172,004건 중 회수는 2,300건. **유입의 1.3%다.** 잔량이 선형으로 자랐고 꺾이는 지점이 없다.

```
회수 처리량 = 100건 / 10.05초 = 초당 9.95건
유입        = 초당 1,000건
```

8절이 보였듯 실패한 건은 없다. **처리량 자체가 두 자릿수 모자란다.**

## 10. 회수의 병목은 배치 크기가 아니라 왕복 횟수다

`batch-size`를 키우면 될 것 같지만 그렇지 않다. 회수기는 `ZRANGE`로 100건을 한 번에 받은 뒤 **`trxId`마다 `EVALSHA`를 따로 보낸다.**

로그 타임스탬프 간격이 10.05초, `fixedDelay`가 10초이므로 100건 처리에 약 50ms — **건당 0.5ms**다. 그런데 Redis가 실제로 쓴 시간은 건당 36µs다(`evalsha` 28.91 + `hgetall` 4.71 + `del` 2.36).

| | 건당 | 비중 |
|---|---|---|
| Redis 실행 | 36µs | 7% |
| **왕복 지연** | **약 464µs** | **93%** |

즉 회수 속도는 Redis 성능이 아니라 **순차 왕복 횟수**가 정한다. 빈 결과가 나올 때까지 도는 방식으로 바꿔도 상한이 초당 약 2,000건이다. 그 위로 가려면 파이프라이닝(`RBatch`)이나 한 스크립트가 N건을 처리하는 형태여야 한다.

`ZRANGEBYSCORE` 자체는 잔량 169,605건에서도 74µs다. 조회는 병목이 아니다.

## 11. 회수가 도는 동안의 요청 경로

같은 사다리에서 회수만 동작/무동작으로 갈랐다.

| | 회수 무동작 (hold 10분) | 회수 동작 (hold 1분) |
|---|---|---|
| A 500 / 600 / 700 | 4 / 5 / 5ms | 5 / 24 / 14ms |
| B 500 / 600 / 700 / 1000 | 4 / 4 / 4 / 6ms | 6 / 7 / 5 / 12ms |
| `ZADD` 평균 | 5.18µs | 6.40µs |

전 구간 PASS를 유지했고 SLO 대비 예산의 12% 안쪽이다. 다만 A/600에서 p95 5→24ms, p99 32→270ms로 튀었다.

**이 차이를 회수 탓으로 돌리기 어렵다.** 회수가 쓴 Redis 명령은 전 구간 합쳐 4,200건이고 요청 경로는 285,371건이다 — **0.0015%**다. 각각 단발 실행이라 회차 편차와 구분되지 않는다. `ZADD` 평균이 오른 것은 ZSET이 커진 영향으로 보이지만 마이크로초 단위라 p95 20ms 차이를 설명하지 못한다.

## 12. 이 결과의 유효 범위

**말할 수 있는 것**

- 요청당 커밋이 1회다 (5절, 문장 카운트로 직접 확인)
- 커넥션 풀이 벽이 아니다 (Hikari 타임아웃 0건)
- 커밋 시간에서 줄서기 몫이 61%→38%로 줄었다 (6절)
- A는 1,000 RPS, B는 1,300 RPS를 p95 10ms 아래로 처리한다 (3절)
- 회수 경로가 정확하다 — 총량·키 개수 항등식 (8절)
- 회수 처리량이 초당 10건이고 병목은 건당 왕복이다 (9·10절)

**말할 수 없는 것**

- **설계의 진짜 처리 한계.** 1,300 RPS 위는 앱 OOM과 생성기 CPU 경합에 가려 안 보인다(4절). 측정한 최고점에서 SLO 예산의 4%만 썼으므로 실제 한계는 한참 위다
- **이전 판 대비 개선폭.** 부록 B는 `dropped_iterations`가 있는 단발 실행이었고 그때 호스트 CPU 상태를 모른다. 같은 세션에서 그 변수 하나로 B/700이 3,977ms와 4ms로 갈렸다
- **회수가 요청 경로에 준 비용.** 11절 참고 — 회차 편차와 구분되지 않는다
- **전략 간 우열.** MySQL 두 전략은 다른 회차·다른 호스트 조건의 기록이다

5절과 6절은 MySQL 내부 카운터라 호스트 오염에 덜 민감하고, 3절의 지연 수치는 민감하다.

**반복 기준 미충족.** 회차마다 사다리를 바꾼 구간 탐색이라 [모델 문서](../02-부하테스트-모델.md) 8.6절의 3회 반복을 만족하지 않는다.

## 13. 다음 측정

1. **유입 제한을 붙이고 다시 잰다.** 4절의 OOM이 사라져야 진짜 한계가 보인다. 넘치면 죽는 대신 429로 튕기는 쪽이 운영에도 맞다
2. **부하 생성기를 다른 머신으로 뺀다.** 그래야 4절의 두 번째 증폭 경로(생성기-앱 CPU 경합)가 없어진다
3. **A의 무릎을 1,000~1,300 사이에서 가둔다.** 사다리를 올릴 때 4절을 볼 것 — 마지막 rung이 워밍업 rate다
4. **B의 상한을 찾는다.** 1,300까지만 확인됐다
5. **세 전략(단일 UPDATE / SKIP LOCKED / Redis Lua)을 같은 사다리·같은 호스트 조건에서 나란히 잰다.** 커밋 수가 같아졌으므로 이제 비교가 공정하다
6. **회수 설정을 정한다.** 확정 유스케이스가 붙어야 실제 만기 도달률을 알 수 있다. 지금은 확정 경로가 없어 전량이 만기로 온다
7. `wait/synch/%MYSQL_BIN_LOG%` 계측을 켜고 6절의 줄서기 비중을 직접 관측한다 — 지금은 산술 추정이다
8. 워밍업 직후 첫 구간의 반복적 저하([부록 A](#부록-a-초기-설계-측정-기록-wal--총량-대조))가 워밍업-측정 전환 구조 때문인지 확인한다

# 부록

## 부록 A. 초기 설계 측정 기록 (WAL + 총량 대조)

> **현재 코드와 맞지 않는다.** 요청당 디스크 append 2회(WAL pending/done)가 포함돼 있고, 그 뒤 설계가 두 번 더 바뀌었다. 남기는 이유는 **경합 비용과 호스트 잡음 관찰**이 지금도 유효하기 때문이다.

측정일 2026-08-24, git sha `c2f314d`, 3회 반복. 재고 키 이름은 당시 `product_stock:{id}`(현재 `available_stock:{id}`).

**A 단일 행 / B 분산 (p95 중앙값)**

| 도착률 | A | B |
|---|---|---|
| 500 | 10ms PASS | 252ms FAIL |
| 600 | 11ms PASS | 10ms PASS |
| 700 | 7ms PASS | 42ms PASS |
| 1,000 | — | 13ms PASS |

**경합 비용 약 1.1배** (600 RPS 기준 A 11ms / B 10ms). MySQL 단일 UPDATE의 15~18배가 사라진 첫 확인이다. 사다리(500~700) 안에서 A의 한계를 못 찾았다 — MySQL은 정확히 이 구간(약 645 RPS)이 한계였다.

**미해결 관측 두 가지.**

- **일회성 저하.** 부하 크기와 무관하게 매 실행 정확히 한 구간에서만 나타난다(A run3의 700에서 1,130ms 등). 구현을 MySQL 행 락에서 Redis 단일 스레드로 완전히 바꿨는데도 재현됐다 — **재고 경합 로직과 무관하다는 강한 증거**다. 두 구현이 공유하는 것은 호스트/Docker VM, k6, 그리고 MySQL의 Reservation INSERT뿐이다
- **B의 500 RPS에서만 3회 중 2회 반복.** 워밍업(최고 rate 60초) 종료 직후 첫 측정 구간이라는 위치가 고정돼 있어, 무작위 잡음보다 워밍업-측정 전환의 구조적 비용일 가능성이 있다. 미검증 가설이다

**처리 한계 탐색에서 얻은 것.** 사다리를 `[700, 1000, 1500, 2000, 3000]`으로 올리고 `maxVUs`를 8,000으로 열었더니 **앱이 `OutOfMemoryError`로 죽었다**(`http_req_failed` 99.82%). 백프레셔 부재가 원인이고, 이 함정은 현재 설계에서도 그대로다([4절](#4-왜-더-못-쟀나--측정-장비가-먼저-무너진다)).

풀 크기를 10 → 50으로 올리자 B의 한계가 1,000 → 1,900 RPS 이상으로 밀렸다. **당시 시스템 상한은 Redis도 MySQL 행 락도 아닌 커넥션 풀이었다.** 현재 설계에서는 커밋이 1회가 되면서 이 벽이 사라졌다(6절).

## 부록 B. 완료 마커 설계의 병목 진단

> 코드는 `backup/marker-design` 브랜치에 있다. **이 절의 진단이 현재 설계를 만들었다.**

예약을 PENDING으로 선기록하고, 차감 성공 시 Redis에 완료 마커를 남기고, 예약을 HELD로 갱신하던 판이다. 요청당 커밋 2회. 단발 실행이고 `dropped_iterations`가 있어 처리량 측정으로는 무효지만, 아래 근거는 반복 횟수와 무관하게 성립한다.

**병목은 Redis가 아니었다.** A와 B의 처리 한계가 둘 다 700 RPS로 같았고 p95는 18ms / 16ms — 경합 1.1배다. 모든 요청이 한 상품에 몰려도 흩어져도 차이가 없으므로 천장은 **요청마다 공통으로 치르는 비용**에 있었다.

**MySQL 시간의 92%가 COMMIT이었다.**

| 문장 | 호출 수 | 평균 | 총 시간 | 비중 |
|---|---|---|---|---|
| **COMMIT** | 1,645,991 | **2.586ms** | **4,256초** | **92%** |
| UPDATE reservations | 833,073 | 0.141ms | 117초 | 2.5% |
| INSERT reservations | 833,632 | 0.138ms | 115초 | 2.5% |
| SET autocommit | 3,315,991 | 0.034ms | 113초 | 2.5% |

```
COMMIT 1,645,991 ≈ INSERT 833,632 + UPDATE 833,073   → 요청당 2회
```

문장 자체는 UPDATE와 INSERT가 사실상 같고(0.141 / 0.138ms) 인덱스 재배치·undo가 전부 그 2.5% 안에 있다. **문장을 튜닝할 여지가 전체의 2.5%뿐이었다.**

**커밋 2.586ms의 내역.**

| | 커밋당 | 비중 |
|---|---|---|
| redo fsync | 0.52ms | 20% |
| binlog fsync | 0.49ms | 19% |
| **group commit 줄서기** | **~1.57ms** | **61%** |

```
Innodb_os_log_fsyncs / Com_commit = 0.76   ← 커밋당 fsync 1회 미만, group commit이 상각 중
Innodb_os_log_written / Com_commit = 984B  ← 트랜잭션이 작다
Binlog_cache_disk_use = 0
```

fsync는 이미 잘 상각되는데도 커밋이 비싼 이유는 `FLUSH → SYNC → COMMIT` 3단계 파이프라인의 **줄서기**다. 이 구분이 처방을 갈랐다 — **fsync는 여러 트랜잭션이 나눠 쓰지만 줄서기는 상각되지 않는다.**

| 손댈 곳 | 닿는 구간 | 내구성 |
|---|---|---|
| **커밋 2회 → 1회** | 92% 전체를 절반으로 | **안 판다** |
| `sync_binlog=0` / `flush_log=2` | 39% 구간만 | 판다 |
| 문장·인덱스 튜닝 | 2.5% 구간 | — |

> 병목은 Redis가 아니라 **예약 쓰기의 커밋 횟수**다. 그리고 두 번째 커밋은 저장소가 갈렸기 때문에 존재한다 — 차감과 예약이 한 트랜잭션이면 "요청이 어떻게 끝났는가"를 따로 증언할 필요가 없다.

두 번째 커밋의 존재 이유가 판별자 하나뿐이었으므로, **판정할 이유를 없애서 그 커밋을 지웠다**([설계 문서 7절](redis-lua-설계.md#7-판정을-없앤-이유)). 그 결과가 [6절](#6-커밋-내부-구성이-예측대로-바뀌었다)이다.
