## 1. 정의

대량 등록은 한 번의 요청으로 n개의 상품을 **새로 만드는** 것이다. "있으면 고치고 없으면 만든다"가 아니다.

**이 API가 받는 모든 행은 이번에 처음 저장되는 신규 데이터로 간주한다.** 이미 있는 상품코드로 들어온 행은 덮어쓰지 않고 **실패로 돌려준다.** 사용자가 "저장됐다"고 믿은 값이 실제로는 무시되는 상태를 만들지 않기 위해서다. 기존 상품의 값을 바꾸는 것은 이 API의 책임이 아니다.

`product_code`는 상품의 자연키다. 요청 안에서도, DB 안에서도 유일하다. 이 유일성이 결과를 행 단위로 되돌려줄 수 있는 유일한 근거다 — 자세한 것은 [인프라 설계 4장](전략/mysql-insert-ignore-설계.md#4-성공실패-판별)에 있다.

## 2. 처리 흐름

`RegisterProducts`가 순서대로 실행한다.

```
1. 판매자 검증          ownerId가 SELLER인가. 아니면 요청 전체 실패
2. 행 단위 도메인 검증   이름/가격/재고/코드 형식. DB 접근 없음
3. 요청 내 코드 중복 판정 같은 요청 안에서 겹친 코드는 전부 실패로 확정
4. 저장                 신규만 삽입. 이미 있는 코드는 삽입되지 않는다
5. 결과 취합            행 단위 성공/실패 목록
```

2·3번은 DB에 가기 전에 끝난다. 4번에서만 DB 상태에 따른 실패가 새로 생긴다.

**사전 검증 API를 따로 두지 않는다.** check API와 save API를 나누면 그 사이에 다른 요청이 같은 코드를 선점할 수 있어(TOCTOU) check 결과가 보증이 되지 못한다. 결국 save가 같은 검증을 다시 해야 하므로 검증 로직만 두 벌이 되고 사용자는 왕복을 두 번 한다.

## 3. 입력 규칙

| 항목 | 규칙 | 위반 시 |
|---|---|---|
| 요청 건수 | 1 ~ `bulk-insert.max-size`(5,000) | 요청 전체 실패 |
| `ownerId` | 존재하는 SELLER | 요청 전체 실패 |
| `name` | 공백 불가, 20자 이하, 한글·영문·숫자·공백만 | 그 행만 실패 |
| `stock` | 0 이상 | 그 행만 실패 |
| `code` | 공백 불가 | 그 행만 실패 |

앞의 두 줄은 요청 자체가 성립하지 않는 조건이라 행 단위로 나누어 보고할 수 없다. 나머지는 행의 문제이므로 그 행만 죽인다.

### 요청 안에서 코드가 겹치면 둘 다 실패한다

하나를 살리고 나머지를 죽이지 않는다. 어느 쪽이 사용자가 의도한 값인지 **요청만 보고는 알 수 없기 때문이다.** 앞의 것을 임의로 채택하면 사용자는 뒤의 값이 조용히 버려진 것을 모른다. 둘 다 실패로 돌려주면 사용자가 어느 쪽이 맞는지 정하고 다시 보낸다.

부수적으로, 이 규칙이 "요청 안에서 코드는 유일하다"를 보장한다. 저장 결과를 코드로 역조회해 입력 행에 되돌려 붙이는 [판별 방식](전략/mysql-insert-ignore-설계.md#4-성공실패-판별)이 서 있는 전제다.

## 4. 부분 성공

**실패한 행은 성공한 행을 되돌리지 않는다.** 5,000행 중 3행이 중복이라고 나머지 4,997행을 다시 올리게 만들지 않는다.

트랜잭션 경계는 요청 전체가 아니라 [청크](전략/mysql-insert-ignore-설계.md#3-sql-구성)다. 청크 하나의 삽입은 원자적이고, 청크 사이에는 원자성이 없다.

## 5. 실패 분류

실패는 **사용자가 고쳐서 다시 보내면 되는가**로 나눈다.

| 분류 | 사유 | 재시도 |
|---|---|---|
| 검증 실패 | 이름 규칙 위반, 재고 음수 등 | 값을 고쳐야 함 |
| 코드 중복 | 이미 있는 코드, 요청 내 중복 | 코드를 바꿔야 함 |
| 저장 실패 | 일시 장애가 재시도 후에도 안 풀림 | 그대로 다시 보내면 됨 |

응답에는 행별 메시지만 싣는다. 실패 상세 원인(SQL 오류 문자열 등)은 로그 전용이다.

## 6. 위치 규약

**실패 보고의 계약은 위치다.** 응답의 `index`는 요청 `products` 배열에서의 자리를 가리킨다(응답은 1-based, 내부는 0-based).

이 자리가 어긋나면 사용자는 멀쩡한 행을 고치게 된다. 그래서 실패 목록에 코드나 이름이 아니라 위치를 싣고, 청크 경계를 넘어가도 위치가 밀리지 않아야 한다.

```json
{
  "successCount": 4997,
  "failureCount": 3,
  "failedProducts": [
    { "index": 12,  "message": "이미 등록된 상품코드입니다" },
    { "index": 401, "message": "상품명은 특수문자를 포함할 수 없습니다" },
    { "index": 3320, "message": "이미 등록된 상품코드입니다" }
  ]
}
```

## 7. 등록 이후

삽입에 **성공한 행만** Redis에 초기 재고가 심긴다. 예약 경로가 읽는 재고 저장소는 Redis뿐이므로, 여기까지 끝나야 실제로 팔 수 있는 상품이 된다. `products.stock` 컬럼은 등록 시점의 원본일 뿐 예약이 읽지 않는다 — [재고 점유 비즈니스 규칙](../재고점유/01-비즈니스-규칙.md) 참고.

## 8. 범위 밖

- **기존 상품 수정** — 이 API는 UPDATE를 하지 않는다. 필요해지면 별도 API로 분리한다
- **삭제**
- **옵션 등 자식 엔티티** — 현재 상품은 단일 테이블이다. 부모-자식이 생기면 [설계 9장](전략/mysql-insert-ignore-설계.md#9-폐기한-설계들)의 find-or-create를 부모에만 적용한다
- **비동기 처리** — 요청당 5,000건 상한 안에서는 동기 응답으로 끝낸다. 상한을 크게 올려야 하면 작업 큐 + 결과 조회 API로 전환을 검토한다
