# 요구사항

## 1. 요구사항과 제약

### 지켜야 하는 것

- **신규만 삽입** — 이미 있는 코드의 행은 덮어쓰지 않는다. UPDATE는 이 경로에 없다
- **부분 성공** — 실패한 행이 성공한 행을 되돌리지 않는다
- **행 단위 판별** — 5,000행 중 어느 행이 안 들어갔는지 정확히 알아야 한다
- **위치 보존** — 결과가 입력과 같은 길이·같은 순서여야 한다. `saveAll`의 반환 규약이다
- 왕복 최소화 — 행 수만큼 쿼리를 보내지 않는다

### 주어진 제약

- **`product_code`가 unique** — 중복은 DB가 막는다. 애플리케이션이 미리 조회해서 막지 않는다
- **요청 안에서 코드는 유일하다** — 겹친 코드는 저장 전에 이미 전부 실패로 확정된다([비즈니스 규칙 3장](../01-비즈니스-규칙.md#3-입력-규칙))
- **id는 auto-increment** — 값은 DB가 정한다. 애플리케이션이 미리 알 수 없다
- **부모-자식 테이블이 없다** — 상품은 단일 테이블이다. 요청의 모든 행이 신규 삽입 대상이고, 재사용되는 마스터성 행이 없다
- MySQL prepared statement 파라미터 상한 65,535개

### 핵심 문제

멀티밸류 INSERT 한 문장으로 보내면 왕복은 1회로 끝나지만, **어느 행이 스킵됐는지 문장 자체는 알려주지 않는다.** `affected rows`는 몇 개인지만 말하고, auto-increment 값은 스킵된 자리를 건너뛰므로 위치를 역산할 근거가 못 된다.

**이 문서의 설계 전체가 "왕복 1회를 유지하면서 행 단위 판별을 어떻게 얻느냐"에 대한 답이다.**

# 결정된 설계

## 2. 처리 흐름

```
1. 청크 분할              chunk-size(1,000)씩. 각 청크는 원래 입력의 offset을 들고 다닌다
2. 멀티밸류 INSERT IGNORE 청크당 1문장. 이미 있는 코드는 여기서 조용히 스킵된다
3. 생성키 회수            getGeneratedKeys — 실제로 삽입된 행의 id만 돌아온다
4. 코드 역조회            그 id들로 product_code를 읽어 "성공한 코드 집합"을 만든다
5. 차집합                 청크 입력 - 성공 = 중복으로 스킵된 행
6. 제자리에 꽂기          offset + 청크 내 위치로 결과 배열을 채운다
```

3~5번이 이 설계의 전부다. **auto-increment가 어디서 몇 개를 건너뛰었는지에 전혀 의존하지 않고, "최종적으로 실제 존재하는 것"만 확인한다.**

## 3. SQL 구성

`batchUpdate`가 아니라 VALUES 튜플을 손으로 이어붙여 청크당 INSERT 한 문장을 보낸다.

```kotlin
val sql = INSERT_PREFIX +
    List(chunk.size) { VALUES_TUPLE }.joinToString(",")
// INSERT IGNORE INTO products (owner_id, product_code, ...) VALUES (?,?,...),(?,?,...),...
```

- `rewriteBatchedStatements`는 기본값이 `false`다. 켜지 않은 `batchUpdate`는 드라이버가 행마다 서버로 보낸다 — 5,000행이면 왕복 5,000회다
- 그 옵션을 켜는 방식은 택하지 않았다. 커넥션 URL 레벨 설정이라 앱 전체 배치 쿼리에 영향을 주고, `executeBatch()`가 돌려주는 `int[]`가 `SUCCESS_NO_INFO(-2)`로 바뀌는 등 이 기능과 무관한 코드가 조용히 깨질 수 있다
- 배치가 아니라 단일 문장이므로 드라이버의 배치 재작성 로직이 개입할 여지 자체가 없다. 성능은 재작성 방식과 동등하다(왕복 1회)

**청크 크기 제약** — 청크 하나가 `chunk-size × 컬럼 수(8)`개의 파라미터를 쓴다. 파라미터 상한 65,535 때문에 `chunk-size`는 8,191을 넘길 수 없다. 현재 값 1,000은 8,000개를 쓴다. `max_allowed_packet`도 같이 본다.

### `INSERT IGNORE`인 이유

`ON DUPLICATE KEY UPDATE product_code = product_code`도 같은 효과(no-op)를 내지만, **의미가 "충돌하면 덮어쓴다"이다.** 이 API의 계약은 "신규만 허용하고 충돌은 실패로 보고한다"이므로 시맨틱이 맞지 않는다. 나중에 누군가 SET 절에 컬럼을 하나 추가하면 그 순간 이 API는 조용히 UPDATE API가 된다.

## 4. 성공/실패 판별

### 4.1 생성키를 전부 회수한다

```kotlin
val keyHolder = GeneratedKeyHolder()
jdbcTemplate.update({ conn ->
    conn.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS).apply {
        chunk.products.forEachIndexed { i, p -> bind(this, i * COLUMN_COUNT, p) }
    }
}, keyHolder)

// keyList는 삽입된 행마다 한 항목. 스킵된 행은 여기 없다
val insertedIds = keyHolder.keyList.map { (it.values.first() as Number).toLong() }
```

`getGeneratedKeys()`가 돌려주는 행 개수는 **실제 삽입된 행 개수와 항상 일치한다.** 스킵된 행은 write 자체가 일어나지 않으므로 결과에 포함되지 않는다.

키 컬럼 이름은 드라이버 버전에 따라 갈린다(`GENERATED_KEY` / `insert_id`). 이름으로 꺼내지 않고 `values.first()`로 꺼낸다.

### 4.2 id로 코드를 역조회한다

```kotlin
SELECT id, product_code FROM products WHERE id IN (?, ?, ...)
```

id는 방금 우리가 심은 행의 것이므로 다른 요청의 행이 섞일 수 없다. 여기서 나온 `product_code` 집합이 **이번 청크에서 실제로 성공한 코드**다.

### 4.3 차집합이 실패 목록이다

```kotlin
val idByCode = /* 4.2의 결과 */
chunk.products.forEachIndexed { i, product ->
    val id = idByCode[product.code]
    results[chunk.offset + i] =
        if (id != null) Result.success(id)
        else Result.failure(ProductDuplicateCodeException(product.code))
}
```

**왜 안전한가**

- auto-increment 예약/gap의 내부 동작(어디서 스킵이 일어났는지)에 의존하지 않는다. 최종 상태만 확인하므로 드라이버·엔진 구현 디테일과 무관하게 정확하다
- `product_code`가 입력과 조회 결과 양쪽에 공통으로 존재하므로 매핑을 신뢰성 있게 재구성할 수 있다. 이 매개값이 **요청 안에서 유일**해야 성립한다 — [비즈니스 규칙 3장](../01-비즈니스-규칙.md#3-입력-규칙)이 그것을 보장한다
- `offset`이 결과를 입력 순서로 되돌리는 유일한 근거다. 청크가 여럿이어도 위치가 밀리지 않는다

## 5. 진짜 예외

`INSERT IGNORE`가 흡수하지 못한 예외(문법 오류, 못 삼킨 제약 위반)가 던져지면 **그 청크를 통째로 실패로 확정한다.** 범인 행을 좁히지 않는다.

- 청크 INSERT는 원자적이라 예외 시점에 그 청크에서 커밋된 행이 없다. 부분적으로 들어간 상태를 정리할 일이 없다
- 남은 청크는 계속 시도한다. 한 청크가 깨졌다고 다음 청크가 깨진다는 근거가 없다

### 범인 행을 좁히지 않는 이유

행 단위로 좁히는 방법은 있다 — 1행씩 다시 넣거나(O(n) 문장), 절반씩 쪼개 이등분하거나(범인이 k개일 때 O(k log n) 문장). **둘 다 "범인이 소수"라는 전제 위에서만 이득이다.**

이 경로에서는 그 전제가 서지 않는다. 여기까지 오는 예외는 `INSERT IGNORE`가 **못 삼킨** 것뿐인데, IGNORE는 길이 초과·NOT NULL 위반·FK 위반까지 warning으로 낮춰 그 행만 스킵한다([10장](#10-알려진-한계)). 그래서 남는 것은 문법 오류나 스키마 불일치처럼 **전 행이 똑같이 죽는** 종류다. 범인이 1,000개면 이등분은 트리를 잎까지 내려가며 약 2,000개 문장을 쓰고도 살려내는 행이 없다.

값을 못 내는 대신 비용은 확실하다. 재귀 한 벌이 늘고, 그 코드는 **장애 상황에서만 처음 실행된다.** 그래서 두지 않는다.

잃는 것은 "예외를 유발한 행 하나 때문에 같은 청크의 멀쩡한 행까지 실패로 보고된다"는 것이다. 사용자는 [위치 규약](../01-비즈니스-규칙.md#6-위치-규약)으로 실패한 행만 골라 다시 보내면 되고, 재전송은 `INSERT IGNORE`라 안전하다([6.3](#63-부하-조절은-바깥에서-한다)).

다시 좁히고 싶어지는 조건은 **`INSERT IGNORE`를 걷어낼 때**다. 그러면 중복 한 건이 문장 전체를 죽이므로 범인이 진짜 소수가 되고, 그때는 이등분이 값을 한다.

## 6. 실패 분류와 포기 범위

**서버는 실패한 청크를 다시 시도하지 않는다.** 재시도는 공짜가 아니라 부하를 더 만드는 행위다. 이 경로가 실패하는 원인은 대개 서버가 이미 감당하지 못하는 상태라는 신호이므로, 그 상태에서 다시 두드리면 원인 자체를 키운다.

그렇다고 모든 실패를 똑같이 다루지는 않는다. **어디까지 포기할지가 갈래마다 다르기 때문이다.**

### 6.1 실패를 두 갈래로 가른다

| 갈래 | 예 | 처리 |
|---|---|---|
| **이 청크의 문제** | 문법 오류, 못 삼킨 제약 위반, 락 타임아웃, 데드락(1213) | **그 청크만** 실패로 확정한다. 다음 청크는 계속 시도한다 |
| **자원 고갈** | 커넥션 풀 획득 타임아웃 | **남은 청크까지** 포기한다. 뒤 청크도 같은 풀에서 기다릴 뿐이다 |

갈리는 축은 "재시도할까"가 아니라 **"이 실패가 다음 청크에 대해 무엇을 말해주는가"**다. 깨진 문장이나 락 경합은 그 청크가 담은 데이터·키에 대한 이야기라 다음 청크까지 죽일 이유가 없다. 반면 빈 커넥션 풀은 요청 전체에 대한 이야기라 남은 청크를 시도하는 것 자체가 낭비다.

### 6.2 커넥션 획득 실패는 잡는 순서가 곧 분류다

`CannotGetJdbcConnectionException`은 `DataAccessException`의 하위지만 **Transient 가지가 아니다.**

```
CannotGetJdbcConnectionException
  └ DataAccessResourceFailureException
      └ NonTransientDataAccessResourceException   ← Transient 가지가 아니다
```

그래서 catch 순서를 뒤집으면 커넥션 획득 실패가 일반 `DataAccessException` 갈래로 떨어져 **"이 청크만 포기"로 잘못 처리된다.** 풀이 빈 상태에서 남은 청크를 계속 시도하게 되고, 청크마다 HikariCP `connectionTimeout`(기본 30초)만큼 줄을 선다. 5,000행이면 청크 5개 × 30초다.

```kotlin
catch (e: CannotGetJdbcConnectionException) { /* 남은 청크까지 포기 */ }
catch (e: DataAccessException) { /* 이 청크만 실패로 확정 */ }
```

**좁은 것을 먼저 잡는다.** 이 순서가 곧 [6.1의 분류](#61-실패를-두-갈래로-가른다)이고, 코드에는 그 의존이 드러나지 않으므로 순서를 바꾸는 사람이 알아야 한다.

### 6.3 부하 조절은 바깥에서 한다

실패한 청크의 행은 `ProductCreationException`으로 채워 [비즈니스 규칙 5장](../01-비즈니스-규칙.md#5-실패-분류)의 "그대로 다시 보내면 되는" 실패(409)로 돌려준다.

**서버 안에서 붙잡고 재시도하는 것보다 클라이언트가 다시 보내게 하는 것이 낫다.** 서버 내부 재시도는 이미 포화된 자원을 더 쓰지만, 클라이언트 재전송은 그 사이 자원을 놓아준다. 부하 조절이 시스템 바깥에서 일어난다.

재전송이 안전한 근거는 `INSERT IGNORE`다. 첫 시도에서 들어간 행은 재전송 때 스킵되므로 이중 삽입이 없다. 실패한 청크 자체도 커밋된 행을 남기지 않는다([8.1](#81-트랜잭션을-열지-않는다)). [위치 규약](../01-비즈니스-규칙.md#6-위치-규약) 덕분에 실패한 행만 골라 다시 보낼 수도 있다.

서버 내 재시도를 두면 그 대기 동안 [8.3](#83-메모리는-요청-상한이-막는다)의 요청 본문(최대 5,000행)이 힙에 그대로 남고, 커넥션 획득 타임아웃 30초에 걸린 요청이 대기를 더 쓰면 **클라이언트는 이미 끊었는데 서버만 계속 두드리는 상태**가 된다. 아무도 받지 않을 응답을 만드느라 자원을 점유하는 것이라 순수한 폭풍 연료다.

같은 이유로 **풀을 재시도로 뚫으려 하지 않는다. 풀을 입장 제어로 쓴다.** [8.4](#84-커넥션은-요청당-하나로-고정한다)처럼 요청당 커넥션 1개를 잡으면 동시에 처리되는 벌크 요청 수가 풀 크기로 자연히 제한된다. Virtual Threads 아래에서 동시 요청 수는 사실상 무제한이므로, 어딘가에서 막히기는 해야 한다. 커넥션 획득 지점에서 막고 즉시 409를 돌려주는 편이, 전부 받아 놓고 안에서 서로 기다리는 것보다 낫다.

**서버 재시도가 필요해지는 조건**은 실측에서 "재시도 한 번이면 풀렸을 실패"가 유의미하게 잡힐 때다. 그때는 지터(full jitter)와 재시도 예산·서킷 브레이커를 같이 넣는다. 고정 간격만 넣으면 같은 순간에 실패한 요청들이 같은 순간에 다시 몰려 스파이크가 그대로 재현된다.

## 7. 재고 심기

삽입에 성공한 행만 골라 Redis에 초기 재고를 심는다. `saveAll`이 입력과 같은 순서로 결과를 돌려준다는 전제 위에서 입력과 zip한다.

심기는 비동기 executor로 청크 단위로 던진다. **여기서 넘기는 컬렉션은 미리 `Map`으로 떠서 넘긴다** — `chunked`의 transform 오버로드가 넘겨주는 리스트는 윈도로 재사용돼, 비동기 람다가 나중에 읽을 때 내용이 바뀌어 있다.

## 8. 트랜잭션과 리소스

### 8.1 트랜잭션을 열지 않는다

**되돌려야 할 상태가 없다.** 실패 처리를 ROLLBACK이 아니라 [4.3의 차집합 판정](#43-차집합이-실패-목록이다)으로 하기 때문이다. 중복 행은 애초에 써지지 않았고, 성공한 행은 되돌리면 안 된다 — 부분 성공이 계약이다.

그래서 `@Transactional`을 붙이지 않는다. 붙이면 청크 여러 개가 한 트랜잭션에 묶여, 뒤 청크가 실패할 때 앞 청크의 성공까지 되돌아간다. 계약 위반이면서 동시에 락 보유 시간도 요청 전체 길이로 늘어난다. `ReserveProducts`가 `@Transactional`을 안 붙이는 것과 같은 판단이다.

`autocommit=true`에서는 **문장 하나가 곧 트랜잭션**이다. unique 인덱스에 락을 쥐는 시간이 이론적 최소치인 "그 INSERT 문장의 실행 시간"으로 줄고, undo log와 커넥션 점유도 같이 짧아진다.

[5장](#5-진짜-예외)과 [6장](#6-실패-분류와-포기-범위)에서 실패한 청크를 그냥 버려도 되는 근거가 여기 있다. 실패한 문장은 커밋된 행을 남기지 않으므로 정리할 상태가 없고, 클라이언트가 같은 행을 다시 보내도 이중 삽입이 되지 않는다.

명시적 트랜잭션이나 SAVEPOINT가 필요한 경우는 지금 없다. 부모-자식 테이블이 생겨 "부모는 들어갔는데 자식 하나가 진짜 예외로 죽는" 상황이 만들어지면, 그때 아이템 단위 SAVEPOINT를 검토한다.

### 8.2 격리 수준은 바꾸지 않는다

MySQL 기본값 REPEATABLE READ는 phantom read를 막으려고 넓은 범위에 gap lock을 잡는다. READ COMMITTED에서는 gap 잠금이 중복 키 검사와 FK 제약 검사 목적으로만 제한적으로 걸리므로, 서로 다른 코드 구간을 동시에 밀어 넣는 벌크 요청들 사이의 불필요한 대기를 줄일 수 있다.

**그래도 지금은 바꾸지 않는다.** 이 경로가 쓰는 문장이 둘뿐이고 둘 다 범위 스캔이 없기 때문이다 — `INSERT IGNORE`는 unique 인덱스의 중복 키 검사만, 역조회는 PK 등치 조회만 한다. gap lock에 노출되는 표면 자체가 작아서 격리 수준을 낮춰 얻을 것이 크지 않다.

부하 측정에서 동시 벌크 요청 간 락 대기가 실제로 보이면 그때 바꾸되, **이 워크로드가 쓰는 세션에만** 적용한다.

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

전역 설정으로 내리지 않는 이유는 [3장에서 `rewriteBatchedStatements`를 URL에 켜지 않은 것](#3-sql-구성)과 같다. 이 기능을 위한 설정이 무관한 코드의 동작을 조용히 바꾸게 두지 않는다.

### 8.3 메모리는 요청 상한이 막는다

`@RequestBody`로 받으므로 **컨트롤러에 진입하는 시점에 요청 본문 전체가 이미 힙에 있다.** 청크 분할은 DB에 주는 부담만 줄일 뿐 이 문제를 막지 못한다.

지금은 `bulk-insert.max-size`(5,000)가 그대로 메모리 상한 역할을 한다. 행 하나가 200바이트 안팎이라 요청 하나가 수 MB를 넘지 않는다. **상한이 곧 방어선이므로 이 값을 올릴 때는 메모리를 같이 계산해야 한다.**

상한을 크게 올려야 하면 입력을 스트리밍으로 파싱해야 한다(`JsonParser` + `MappingIterator`로 청크만큼만 버퍼링). 다만 공짜가 아니다.

**스트리밍은 요청 내 중복 판정과 충돌한다.** [비즈니스 규칙 3장](../01-비즈니스-규칙.md#3-입력-규칙)의 "요청 안에서 겹친 코드는 둘 다 실패"는 요청 전체를 한 번에 봐야 성립한다. 스트리밍하면 판정 범위가 청크로 줄어들고, 겹친 두 행이 다른 청크에 있으면 하나는 삽입되고 나머지가 DB 중복으로 뒤늦게 잡힌다 — 규칙이 "먼저 온 것이 이긴다"로 바뀐다. **상한을 올릴 때는 이 규칙부터 다시 정한다.**

응답도 같은 문제를 갖는다. 실패 목록의 길이는 요청 길이에 비례한다. 지금은 상한 5,000이 유계로 만들어 주지만, 상한을 올리면 상세는 앞 N건만 싣고 총 건수는 카운터로, 전체 리포트는 별도 저장소 + 조회 링크로 뺀다.

### 8.4 커넥션은 요청당 하나로 고정한다

`JdbcTemplate` 호출마다 커넥션을 빌리고 돌려준다. 트랜잭션이 없으므로 **대여-반납 단위가 문장 단위다.** 5,000건이면 청크 5개 × (INSERT + 역조회) = 10회다.

문장 수에 비례하는 대여는 동시 요청이 많을 때 풀을 압박한다. **Virtual Threads를 쓰기 때문에 더 그렇다** — 스레드는 싸지만 커넥션은 싸지 않다. 동시에 처리 중인 요청 수가 풀 크기를 훨씬 넘길 수 있고, 그때 대여 횟수가 요청당 10회면 대기가 그만큼 곱해진다.

고정하려면 커넥션을 요청당 한 번만 빌려 그 안에서 청크를 순회한다.

```kotlin
jdbcTemplate.execute { conn ->            // 요청당 1회 대여
    chunks.forEach { chunk ->
        writeChunk(conn, chunk, results)  // autocommit 유지 - 문장은 여전히 짧다
    }
}
```

커넥션을 오래 쥐는 것과 트랜잭션을 오래 여는 것은 다른 문제다. autocommit이라 락 보유 시간은 [8.1](#81-트랜잭션을-열지-않는다) 그대로 문장 하나짜리다.

**부하 측정에서 풀 대기가 실제로 보였다.** 동시 요청 16, 풀 10에서 처리량이 65,000행/초에서 531행/초로 무너졌고 `HikariPool-1 - Connection is not available, request timed out after 30001ms`가 찍혔다. 응답 중앙값 30초는 커넥션 타임아웃 1회, p95 60초는 2회 — **요청 하나가 대여를 여러 번 하기 때문**이다([측정 결과 5장](부하테스트-결과.md#5-동시-요청--8이-천장-16에서-붕괴)).

**전환했다.** `jdbcTemplate.execute(ConnectionCallback { … })`로 커넥션을 한 번 빌려 그 안에서 청크를 순회한다. 요청당 대여가 11회(5,000행이면 21회)에서 2회로 줄었다 — 판매자 검증 1회 + `bulkInsert` 1회.

전환 뒤 부하 산정 조합(브랜드 10곳 × 5,000행)의 중앙 응답이 30.9초에서 1.0초로, 실패행이 48.5%에서 6%로 떨어졌다([측정 결과 5장](부하테스트-결과.md#5-동시-요청--천장은-커넥션-풀-크기다)).

**대가**: 대여가 하나뿐이라 못 받으면 요청 전체를 포기한다. 전에는 앞 청크가 이미 성공했을 수 있었지만 이제는 아무것도 안 들어간 상태다 — 부분 성공 보고가 사라지는 대신 사용자가 받는 답은 더 단순해진다("전건 실패, 그대로 다시 보내라").

**이것만으로는 부족했다 — OSIV가 하나를 더 쥐고 있었다.** `spring.jpa.open-in-view`는 명시하지 않으면 `true`이고, 그러면 EntityManager가 응답 끝까지 요청에 묶인다. 유스케이스 첫 줄의 판매자 검증이 잡은 커넥션을 안 놓은 채 `bulkInsert`가 두 번째를 요구하므로, **요청당 커넥션은 여전히 2개**였다. 풀 10이면 동시에 완주 가능한 요청이 5개뿐이라 동시 16에서 교착하고 30초 타임아웃으로만 풀렸다.

풀 크기를 1로 놓고 요청 하나만 보내면 드러난다 — OSIV가 켜져 있으면 경쟁 상대가 없는데도 30초를 기다리다 실패하고, 끄면 391ms에 완주한다. `open-in-view: false`로 끄면 대여가 진짜 요청당 1회가 된다. 이 애플리케이션은 엔티티에 지연 로딩 연관이 없고 `@Transactional`도 쓰지 않아(영속성 컨텍스트가 리포지토리 호출 하나만큼만 산다) OSIV가 덮어 줄 대상이 애초에 없다.

**둘을 다 걷어낸 뒤의 값**: 동시 16이 528 → 50,989행/초, 실패 0. 사다리가 절벽 없이 동시 4의 61,000행/초를 정점으로 완만히 내려온다. 병목은 커넥션 풀이 아니라 MySQL CPU다([측정 결과 4장](부하테스트-결과.md#4-시나리오-b--동시-요청)).

### 8.5 청크 크기는 세 개의 상한이 정한다

청크 크기는 **왕복 효율(클수록 유리)과 서버 부담(클수록 불리)의 트레이드오프**다. 500~1,000은 출발점일 뿐이고, 아래 세 상한을 실측해 환경별로 정한다.

| 상한 | 값 | 현재 여유 |
|---|---|---|
| prepared statement 파라미터 | 65,535 ÷ 컬럼 8 = **8,191행** | 1,000행이 8,000개 사용 |
| `max_allowed_packet` | 문장 하나가 이 값을 넘으면 거부된다. 우리 compose는 지정하지 않아 MySQL 8.0 기본값(64MB)을 쓴다 | 행 200바이트 기준 1,000행 ≈ 200KB |
| 락 보유 시간·binlog 이벤트 크기 | 청크 크기에 비례해 늘어난다. 큰 statement는 binlog 이벤트도 커져 복제 지연에 영향을 준다 | 상한이 아니라 감쇠 — 측정으로만 정한다 |

앞의 두 줄은 넘기면 문장이 깨지고, 마지막 줄은 조용히 느려진다. **상품에 설명 같은 큰 컬럼이 붙으면 행 바이트가 달라지므로 `max_allowed_packet` 기준을 다시 역산해야 한다.**

**실측했고 1,000을 유지한다.** 청크를 250~4,000으로 스윕하면 행당 비용이 52.2µs에서 36.1µs로 줄지만, 500 아래만 뚜렷이 나쁘고 그 위로는 평평하다. p95는 1,000이 최저(394ms)다([측정 결과 6장](부하테스트-결과.md#6-시나리오-d--청크-크기)).

**청크 수에 비례하는 비용의 정체는 커밋 fsync다.** 트랜잭션을 열지 않으므로 INSERT 문장 하나가 곧 커밋 하나이고, `innodb_flush_log_at_trx_commit=1`이면 커밋마다 redo를 flush한다. 회귀가 `177ms + 4.45ms × 커밋수`로 잡힌다. 8.4 전환으로 대여 횟수가 청크와 무관해진 뒤에도 이 기울기가 남아서 대여가 아니라 커밋임이 갈렸다.

단 이 측정은 동시 1이라 **큰 청크가 락을 오래 쥐어 남에게 주는 영향은 안 잡는다.**

## 9. 폐기한 설계들

| 방안 | 기각 사유 |
|---|---|
| **`ON DUPLICATE KEY UPDATE` upsert** | 의미가 "충돌 시 덮어쓰기"라 "신규만 허용, 충돌은 실패로 보고"라는 계약과 어긋난다. SET 절에 컬럼 하나만 늘어도 조용히 UPDATE API가 된다 |
| **`created_at` 값으로 이번에 심은 행 식별** | 앱에서 조립한 타임스탬프를 식별자로 재활용하는 것이라 감사 컬럼의 의미를 오염시킨다. 해상도의 물리적 한계 때문에 동시 요청 간 충돌 가능성도 남는다. DB `NOW()` 기반 range 비교는 다른 요청의 행까지 걸려 더 나쁘다 |
| **INSERT 전 존재 여부 SELECT** | 두 단계 모두 n건 규모라 비용 이점이 없고, SELECT와 INSERT 사이에 TOCTOU가 열린다. 경쟁이 나면 재조회가 붙어 왕복이 2회에서 3회로 늘어난다 |
| **auto-increment gap으로 위치 역산** | simple insert가 행 수만큼 블록을 순서대로 예약하는 것은 맞지만, 블록의 **시작값**을 안전하게 얻을 표준 API가 없다. `LAST_INSERT_ID()`와 `getGeneratedKeys()`는 "실제 성공한 첫 값"만 알려주므로 선두 행이 스킵되면 계산이 어긋난다 |
| **`affected rows` 개수로 판별** | 몇 개인지만 알려주고 어느 것인지 알려주지 않는다. Connector/J 기본값 `useAffectedRows=false`에서는 no-op 업서트가 0이 아니라 1로 오기까지 한다 |
| **`rewriteBatchedStatements=true` 전역 활성화** | 커넥션 URL 레벨 설정이라 앱 전체 배치 쿼리에 영향을 준다. `executeBatch()` 결과 코드가 바뀌어 무관한 코드가 조용히 깨질 수 있다 |
| **행 단위 범인 찾기(1행씩·이등분)** | 예외가 여기까지 오려면 `INSERT IGNORE`가 못 삼킨 것이어야 하는데, 그런 예외는 대개 전 행이 똑같이 죽는 종류다. "범인이 소수"라는 전제가 안 서서 문장만 최대 2n개 쓰고 살리는 행이 없다. IGNORE를 걷어내면 다시 검토한다 — [5장](#5-진짜-예외) |
| **사전 검증 전용 API 분리** | check와 save 사이 TOCTOU. save가 같은 검증을 다시 해야 해서 로직이 두 벌이 되고 사용자 왕복도 2회가 된다 |
| **JPA `saveAll`** | id 전략이 IDENTITY라 Hibernate가 배치를 접는다. 행마다 INSERT가 나가므로 왕복 최소화 요구와 정면으로 충돌한다 |
| **부모 테이블 find-or-create** | 상품이 단일 테이블이라 지금은 적용 대상이 없다. `INSERT IGNORE` 후 스킵된 것만 골라 기존 id로 채우는 방식이며, 상품-옵션 같은 부모-자식이 생기면 **부모에만** 적용한다. 부모는 여러 요청이 공유하는 마스터성 데이터라 "실패"라는 개념이 없기 때문이다 |

## 10. 알려진 한계

- **`INSERT IGNORE`는 중복 말고도 삼킨다.** 데이터 길이 초과, NOT NULL 위반, FK 위반 같은 오류도 warning으로 낮추고 그 행을 스킵한다. 그러면 [5장](#5-진짜-예외)의 예외 경로는 타지 않고, 그 행은 **중복으로 잘못 분류돼 보고된다.** 실무상 도메인 검증([비즈니스 규칙 3장](../01-비즈니스-규칙.md#3-입력-규칙))이 그 전에 대부분 잡고, 사용자 입장에서 결과는 "그 행은 저장되지 않았다"로 같기 때문에 감수한다. 원인 정확도가 필요해지면 `SHOW WARNINGS`를 읽어 분리한다
- **청크 사이에는 원자성이 없다.** 앞 청크가 커밋된 뒤 뒤 청크가 실패할 수 있다. 부분 성공을 계약으로 삼았으므로 의도된 동작이다
- **판별 쿼리가 청크당 1회 더 든다.** 왕복이 청크당 1회가 아니라 2회다. 행 단위 판별의 값으로 지불한 비용이고, 행 수에 비례하지 않는다. 실측에서는 이 비용이 지연에 드러나지 않았다 — 중복이 많을수록(= 역조회가 짧아질수록) 오히려 11% 빨랐다([측정 결과 6장](부하테스트-결과.md#6-중복-비율--중복이-오히려-싸다))
- **요청 전체를 재전송하면 이미 성공한 행이 중복 실패로 보고된다.** 데이터는 안전하지만(이중 삽입 없음) 응답은 사용자를 헷갈리게 한다. 재전송은 실패 목록의 행만 골라 보내는 것이 맞고, [위치 규약](../01-비즈니스-규칙.md#6-위치-규약)이 그것을 가능하게 한다
- **동기 응답 상한은 5,000건이다.** 그 이상은 작업 큐 + 결과 조회 API로 전환해야 한다
- **이 문서의 실패 분류는 `bulkInsert` 안쪽만 덮는다.** 유스케이스 첫 줄의 `validateMemberIsSeller`(JPA)는 분류 밖이라 풀이 마르면 500이 나갔다. 지금은 `ApiControllerAdvice`의 일시 장애 핸들러가 받아 409로 내린다 — 여기 밖의 경로는 그 핸들러가 최후 방어선이라는 뜻이다(동시 16 측정에서 41건 관측)
