- §6.1 실패 분류 밖에서 커넥션 고갈이 500으로 새던 것을 찾아 고쳤다([설계 10](mysql-insert-ignore-설계.md#10-알려진-한계))

- **배경 데이터 1,000만 행의 영향은 측정되지 않는다.** 단조 증가하지 않아 노이즈와 구분되지 않는다([A](#3-시나리오-a--요청-크기와-배경-데이터))
- **`owner_id` 인덱스가 무는 비용은 10%대이거나 그보다 작다.** 이전 환경(1 vCPU / 1GB)에서 기록된 "1.5배"는 재현되지 않는다([A](#3-시나리오-a--요청-크기와-배경-데이터))

## 3. 시나리오 A — 요청 크기와 배경 데이터

### 무엇을 어떻게

동시 1로 고정하고 **클라이언트가 한 요청에 몇 행을 담는지**를 바꾼다. `chunk-size`는 1,000 고정이므로 이 시나리오는 청크 값에 대해 아무 말도 하지 않는다(그건 [D](#6-시나리오-d--청크-크기)).

같은 측정을 배경 데이터(`reset.sh`의 `PRESEED_ROWS`, 접두어 `SEED-`, `owner_id` 100개 분산)만 바꿔 세 번 돌렸다. 그리고 배경 1,000만을 고정한 채 `owner_id` 인덱스만 껐다 켜서 한 번 더 돌렸다([모델 6.1](../02-부하테스트-모델.md#61-변수-하나만-바꿔-비교하기)의 토글 절차 — 같은 바이너리에 스키마만 바꾼다).

### 결과

요청 크기(배경 1,000만):

| 행/요청 | 중앙 소요 | p95 | 행/초 | **행당 비용** |
|---|---|---|---|---|
| 100 | 9ms | 15ms | 10,934 | 91µs |
| 500 | 23ms | 69ms | 21,478 | 47µs |
| 1,000 | 40ms | 113ms | 25,087 | 40µs |
| 5,000 | 182ms | 239ms | 27,401 | **36µs** |

최소제곱 회귀: `소요(ms) = 5.3 + 35.4µs × 행수`

배경 데이터(5,000행 요청):

| 배경 행 수 | 테이블 크기 | 행당 비용 | 행/초 | 회귀 |
|---|---|---|---|---|
| 0 | — | 35.3µs | 28,306 | 13.1ms + 32.4µs × 행 |
| 100만 | 데이터 117MB + 인덱스 72MB | 38.7µs | 25,857 | 5.3ms + 37.5µs × 행 |
| 1,000만 | 데이터 1,147MB + 인덱스 **726MB** | 36.5µs | 27,401 | 5.3ms + 35.4µs × 행 |

`owner_id` 인덱스 유무(배경 1,000만):

| 행/요청 | 있음 (행당) | 없음 (행당) | 차이 |
|---|---|---|---|
| 100 | 167.1µs | 189.2µs | **−11.7%** |
| 500 | 68.1µs | 65.4µs | +4.2% |
| 1,000 | 43.4µs | 47.6µs | **−8.8%** |
| 5,000 | 44.6µs | 40.3µs | +10.7% |

| | 회귀 | 5,000행 처리량 |
|---|---|---|
| 인덱스 있음 | 9.1ms + 42.5µs × 행 | 22,442행/초 |
| 인덱스 없음 | 13.3ms + 37.5µs × 행 | 24,842행/초 |

### 인사이트

**요청 고정비가 작은 요청을 지배한다.** 5.3ms(HTTP 왕복, 도메인 검증, 요청 내 중복 판정, 응답 조립)가 100행 요청에서는 비용의 절반이 넘는다. 배치가 커지면 그 고정비가 행 수로 나뉘어 행당 비용이 2.5배 싸진다. → **튜닝 여지는 서버가 아니라 클라이언트가 몇 행씩 묶어 보내는가에 있다.**

**OSIV를 끄니 고정비만 줄었다.** 같은 측정이 전에는 `8.3ms + 35.8µs × 행`이었다. **고정항이 3ms 빠지고 기울기는 그대로다** — OSIV 비용이 요청당 한 번 붙는 성격이라는 것과 정확히 맞는다([B](#4-시나리오-b--동시-요청)). 그래서 작은 요청일수록 이득이 크다(100행 10 → 9ms, 500행 29 → 23ms).

**청크 분할은 싸다.** 5,000행 요청은 청크 5개로 쪼개져 문장 10개를 보내는데도 행당 비용이 최저다. 분할 오버헤드가 요청 고정비보다 훨씬 작다.

**배경 데이터의 영향은 측정되지 않는다.** 1,000만 행이면 총 1,873MB로 버퍼 풀(1,024MB)을 1.8배 넘기는데, 행당 비용이 **단조 증가하지 않는다** — 100만(38.7µs)이 1,000만(36.5µs)보다 느리게 나왔다. 차이가 노이즈 안이라는 뜻이다.

**`owner_id` 인덱스가 무는 비용은 한 자릿수~10%대다.** 5,000행 구간에서 처리량 22,442 → 24,842행/초(+10.7%), 회귀 기울기 42.5 → 37.5µs/행(12%). 그런데 **네 단계 중 둘은 부호가 뒤집힌다** — 100행과 1,000행에서는 인덱스 있는 쪽이 빨랐다. 인덱스가 삽입을 느리게 만든다면 전 구간이 같은 방향이어야 하므로, **차이가 노이즈와 같은 크기**라는 뜻이다. 지금 말할 수 있는 것은 "10%대이거나 그보다 작다"까지다.

값이 작은 이유는 선택도다. `owner_id`는 값의 종류가 적어 보조 인덱스 항목이 소수의 페이지에 몰려 붙는다. 5,000행마다 전부 새 값이 들어가는 유니크 인덱스(`product_code`)가 무는 비용에 비하면 부수적이다.

> 참고: 같은 스키마로 1 vCPU / 1GB 환경에서 잰 이전 기록은 "인덱스가 INSERT를 1.5배 느리게 한다"였다. 이 환경(버퍼 풀 1GB, MySQL 2 CPU)에서는 재현되지 않는다. **인덱스 비용은 절대값이 아니라 메모리 대비 인덱스 크기의 함수**라 환경에 따라 자릿수가 달라진다.

이 경로가 인덱스에 하는 일은 `INSERT IGNORE`의 unique 키 중복 검사와 PK 등치 역조회뿐이다. B-트리가 깊어져도 건드리는 페이지가 몇 개 늘 뿐, **범위 스캔이 없어 버퍼 풀 미스가 폭증하지 않는다.** [설계 8.2](mysql-insert-ignore-설계.md#82-격리-수준은-바꾸지-않는다)의 "범위 스캔이 없어 gap lock 표면이 작다"가 데이터 접근 측면에서도 성립했다.

## 4. 시나리오 B — 동시 요청

### 무엇을 어떻게

요청 크기를 1,000행으로 고정하고 **동시 요청 수**를 1 → 16으로 올린다. 배경 1,000만, VU를 브랜드 10곳에 분산. 별도로 부하 산정 조합인 **피크(브랜드 10곳 × 5,000행 = 동시 5만 행)**를 따로 돌린다([모델 3.2](../02-부하테스트-모델.md#32-b--동시-요청)).

같은 조건을 **커넥션을 쥐는 방식만 바꿔** 세 번 쟀다.

| 회차 | 요청당 커넥션 |
|---|---|
| 문장 단위 대여 | 청크마다 2회 = 11회(5,000행이면 21회) |
| 요청당 1회 | `bulkInsert`가 1회 — [설계 8.4](mysql-insert-ignore-설계.md#84-커넥션은-요청당-하나로-고정한다) 전환 |
| + OSIV off | 위 + `open-in-view: false` |

### 결과

| 동시 | 총 행/초 (문장 단위) | 총 행/초 (요청당 1회) | **총 행/초 (+OSIV off)** | 중앙 | p95 | 실패행 |
|---|---|---|---|---|---|---|
| 1 | 16,545 | 15,169 | 15,995 | 63ms | 363ms | 0 |
| 2 | 26,553 | 24,810 | 25,399 | 79ms | 138ms | 0 |
| 4 | 47,738 | 42,364 | 39,582 | 101ms | 296ms | 0 |
| 8 | 49,716 | 44,848 | 45,938 | 174ms | 266ms | 0 |
| 16 | 529 | 528 | **48,458** | 330ms | 504ms | **0** |
| 32 | — | — | **54,828** | 584ms | 1,266ms | 0 |
| 64 | — | — | 53,559 | 1,195ms | 3,149ms | 0 |

동시 32·64는 OSIV off 이후에만 쟀다 — 그전에는 16에서 이미 무너져 올릴 이유가 없었다.

피크:

| | 문장 단위 대여 | 요청당 1회 | **+ OSIV off** |
|---|---|---|---|
| 중앙 소요 | 30,946ms | 1,032ms | **964ms** |
| p95 | 316,162ms | 30,458ms | **1,277ms** |
| 성공 / 실패행 | 247,000 / 233,000 | 470,000 / 30,000 | **500,000 / 0** |
| 총 행/초 | 1,620 | 48,470 | **51,842** |
| 실행 시간 | 14분 14초 | 41초 | **약 11초** |

### 인사이트

#### 절벽의 정체는 OSIV였다

전환 전후 모두 동시 16에서 처리량이 3자릿수로 무너졌다. 동시 8이 p95 288ms인데 16이 30,384ms — **170배**다. 부하가 두 배 늘 때 지연이 170배가 되는 곡선은 없다. 절벽이면 원인이 따로 있다.

원인은 `spring.jpa.open-in-view`였다. 명시하지 않으면 기본값이 `true`이고, 그러면 **요청 하나가 커넥션을 동시에 둘 점유한다** — 판매자 검증(JPA)이 잡은 것이 응답 끝까지 반납되지 않은 채 `bulkInsert`가 두 번째를 요구한다. 풀 10이면 동시에 완주 가능한 요청이 5개뿐이라 16개가 서로 물리고, 30초 타임아웃이 유일한 탈출구가 된다.

`open-in-view: false`로 끄니 `pending`이 **6**이 됐다. `16 VU − 커넥션 10 = 6`, 교과서적인 큐잉이다.

→ 진단 과정과 근거 셋은 [부록 A](#부록-a-osiv가-요청당-커넥션을-둘-점유하던-문제).

#### 곡선이 곡선처럼 생겼다

15,995 → 25,399 → 39,582 → 45,938 → 48,458 → **54,828(동시 32)** → 53,559. 32까지 완만히 오르다 64에서 처리량이 안 늘고 지연만 배로 뛴다(584 → 1,195ms). **전형적인 포화 지점이고, 절벽이 없다.**

지연도 동시성에 선형이다 — 63 → 79 → 101 → 174 → 330 → 584 → 1,195ms. 두 배 늘 때마다 두 배 안쪽이다.

**동시 64까지 실패 0건, 비200 0%다.** 커넥션 풀이 10인데 동시 64에서 타임아웃이 하나도 없다. 풀은 이제 입장 제어로만 동작하고 대기는 짧게 흡수된다.

그동안 "천장"이라 부른 동시 8은 시스템의 용량이 아니라 **교착이 시작되는 지점**이었다. 실제 천장은 약 **55,000행/초(동시 32)**이고, 거기서 병목은 커넥션 풀이 아니라 MySQL에 준 2 CPU다.

#### 8.4 전환의 효과는 OSIV에 가려져 있었다

요청당 커넥션 1회로 바꿨을 때 사다리는 거의 안 움직였고 피크만 좋아졌다. **`bulkInsert`의 대여를 10회에서 1회로 줄여도 OSIV가 뒤에서 하나를 더 쥐고 있었으므로 "요청당 2개"라는 조건이 그대로였기 때문**이다. 두 개를 다 걷어낸 뒤에야 사다리가 96배(528 → 50,989행/초) 뛰었다.

둘 다 필요했다는 것도 분명하다. 문장 단위 대여로 되돌리면 요청당 11 + OSIV 1이라 훨씬 일찍 마른다.

#### 실패의 모양은 계약대로였다

교착 구간에서도 500은 0건이었다. 실패는 두 갈래로 나뉘어 나갔다 — 200 + 행 단위 실패(`bulkInsert`가 커넥션을 못 받아 전건 `giveUp`), 그리고 요청 전체 409(`validateMemberIsSeller`가 먼저 말라 `bulkInsert`가 시작도 못 함). 처음 쟀을 때 후자가 500으로 새던 것은 advice 핸들러로 닫았다([설계 10](mysql-insert-ignore-설계.md#10-알려진-한계)).

다만 **계약을 지킨 것과 처리한 것은 다르다.** 교착 구간의 동시 16은 보낸 16만 행 중 45.6%만 들어갔고 나머지는 다시 보내야 했다. 지금은 100%다.

#### `owner_id` 핫스팟 가설은 틀렸다

1차는 전부 `ownerId=1`이라 인덱스 삽입이 한 값에 몰렸다. 실제로는 없을 핫스팟이라 보고 브랜드 10곳에 흩었는데 **같거나 오히려 느렸다**(단일 owner 총 행/초: 동시 4에서 60,644, 8에서 52,856).

값이 하나면 보조 인덱스 삽입이 오른쪽 끝에 순차로 붙지만, 10곳으로 흩으면 삽입 지점이 열 군데라 더 많은 페이지를 더럽힌다. **단일 owner는 핫스팟이 아니라 순차 삽입이라는 최적 조건이었다.** 이후 기준선은 운영에 가까운 분산 쪽이다.

## 5. 시나리오 C — 중복 비율

### 무엇을 어떻게

5,000행 요청 안에서 **이미 존재하는 코드의 비율**을 바꾼다. `setup()`이 5,000개를 미리 심어 두고 그 풀에서 섞는다. 배경 0, 동시 1.

역조회(`SELECT ... WHERE id IN (...)`)가 청크마다 한 번 더 드는 것이 [설계 10](mysql-insert-ignore-설계.md#10-알려진-한계)의 한계로 적혀 있어, 그 비용이 지연에 나타나는지 보는 것이 목적이다.

### 결과

| 신규 비율 | 중앙 소요 | p95 | 행/초 | 100% 대비 |
|---|---|---|---|---|
| 100% | 188ms | 227ms | 26,539 | 1.00x |
| 50% | 177ms | 208ms | 28,172 | 1.06x |
| 0% | 143ms | 295ms | 35,074 | **1.32x** |

### 인사이트

**중복이 많을수록 빠르다.** `INSERT IGNORE`가 스킵한 행은 write가 아예 없고 생성키도 안 돌아와 역조회 IN 절이 짧아진다. 게다가 커밋에 실을 것이 줄어 [D](#6-시나리오-d--청크-크기)가 짚은 fsync 비용도 가벼워진다. 그 이득이 실패 목록 5,000건을 직렬화하는 비용보다 크다.

OSIV를 끄기 전 같은 측정은 1.11x였다. 방향은 같고 격차만 커졌다. 다만 신규 100%의 절대값이 165 → 188ms로 나빠진 것은 설명되지 않는다 — 각 조건 1회 측정이라 회차 노이즈로 본다.

**역조회 비용은 지연에서 관측되지 않는다.** 설계가 한계로 적어 둔 "판별 쿼리 청크당 1회 추가"는 최소한 이 규모에서는 값을 치르지 않는다. 행 단위 판별의 정확성을 싸게 샀다.

## 6. 시나리오 D — 청크 크기

### 무엇을 어떻게

요청을 5,000행으로 **못 박고** 서버의 `bulk-insert.chunk-size`만 250 → 4,000으로 바꾼다. 바뀌는 것은 요청 하나가 보내는 문장 수뿐이다. 청크는 서버 설정이라 값마다 앱을 다시 띄워야 해서 `sweep-chunk.sh`가 회차를 돈다. 동시 1, 배경 1,000만.

[A](#3-시나리오-a--요청-크기와-배경-데이터)는 청크를 1,000으로 고정한 채 요청 크기를 바꿨으므로 청크 값 자체는 이 시나리오만 답할 수 있다.

커넥션 대여 전환 전후로 두 번 돌렸다. **그 둘의 비교가 원인을 가른다** — 아래 참조.

### 결과

| 청크 | 문장 수 | 커밋 수 | 중앙 소요 | 행당 비용 | p95 | 실패 1회당 잃는 행 |
|---|---|---|---|---|---|---|
| 250 | 40 | 20 | 261ms | 52.2µs | 590ms | 250 |
| 500 | 20 | 10 | 233ms | 46.6µs | 673ms | 500 |
| **1,000** | 10 | 5 | 193ms | 38.7µs | **394ms** | 1,000 |
| 2,000 | 6 | 3 | 193ms | 38.6µs | 488ms | 2,000 |
| 4,000 | 4 | 2 | 181ms | 36.1µs | 487ms | 4,000 |

행당 비용은 4,000이 가장 낮은데 p95는 1,000이 가장 낮다. **두 힘이 반대로 걸려 있다.**

### 인사이트

#### 작으면 왜 비싼가 — 커밋 fsync

사슬이 넷이다.

1. 이 경로는 트랜잭션을 열지 않는다([설계 8.1](mysql-insert-ignore-설계.md#81-트랜잭션을-열지-않는다)) → 커넥션이 autocommit
2. autocommit이면 **INSERT 문장 하나 = 트랜잭션 하나 = 커밋 하나**
3. 측정 환경은 `innodb_flush_log_at_trx_commit=1` → **커밋마다 redo 로그 fsync**
4. 따라서 `청크 개수 = INSERT 개수 = 커밋 개수 = fsync 개수`

역조회 `SELECT`는 읽기라 redo flush가 없다 — **문장 40개 중 돈을 무는 것은 INSERT 20개뿐이다.**

커밋 수로 회귀하면 맞아떨어진다.

```
소요(ms) = 177 + 4.45 x 커밋수
```

**500 위로 평평해지는 이유도 여기서 나온다.** 커밋 수가 기하급수로 줄기 때문이다 — 20 → 10은 10회를 아끼지만 3 → 2는 1회다. 청크를 두 배로 키울 때마다 절약분이 반씩 준다.

#### 원인이 fsync라는 것을 어떻게 갈랐나

처음 쟀을 때는 이 회귀가 원인을 특정하지 못했다. **대여 횟수가 커밋 횟수의 2배로 완전 비례**했기 때문이다 — `커밋수 × a`와 `대여수 × a/2`는 같은 직선이라, 데이터는 "청크 개수에 비례하는 무언가"까지만 말했다.

[B의 커넥션 전환](#4-시나리오-b--동시-요청)이 그 결합을 끊었다. 이제 대여는 **청크와 무관하게 요청당 1회**다. 그래서 같은 스윕을 다시 돌리는 것이 곧 대조 실험이 됐다.

| | 회귀 | 대여가 청크에 비례? |
|---|---|---|
| 전환 전 | 192ms + **3.20**ms × 커밋수 | 예 |
| 전환 후 | 177ms + **4.45**ms × 커밋수 | **아니오** |

**기울기가 사라지지 않았다.** 대여가 원인이었다면 청크와 대여의 관계가 끊긴 순간 평평해졌어야 한다. 남았으므로 **원인은 커밋 fsync다.** `flush_log_at_trx_commit`을 건드리지 않고 갈렸다.

#### 크면 무엇을 내주는가 — 문장 하나가 커진다

커밋은 줄지만 **커밋 하나가 무거워진다.** 청크 4,000이면 문장 하나가 파라미터 32,000개(4,000행 × 8컬럼)를 싣는다.

- **락 보유 시간** — INSERT는 문장이 끝날 때까지 삽입한 행과 unique 인덱스 항목에 락을 쥔다. 문장이 길수록 그 시간이 길다
- **binlog 이벤트 크기** — 문장 하나가 만드는 이벤트가 그만큼 커져 복제 지연에 실린다
- **실패 반경** — 청크는 [실패의 단위](mysql-insert-ignore-설계.md#61-실패를-두-갈래로-가른다)다. `giveUp`이 청크째 실패시키므로 4,000 청크는 한 번 튈 때 4,000행을 잃는다. 되돌릴 트랜잭션이 없으니 롤백 비용이 아니라 **클라이언트가 다시 보내야 할 몫**이다

앞의 둘이 p95에 나타난다 — 1,000의 394ms가 최저이고 500은 673ms, 4,000은 487ms다.

넘으면 깨지는 상한도 둘 있다: 파라미터 65,535개(8컬럼이면 청크 8,191행)와 `max_allowed_packet`([설계 8.5](mysql-insert-ignore-설계.md#85-청크-크기는-세-개의-상한이-정한다)).

#### 그래서 1,000

- **위로 갈 이유가 없다.** 1,000 → 4,000의 이득은 행당 2.6µs(7%)인데, 같은 표에서 1,000과 2,000이 사실상 동률(38.7 vs 38.6µs)이다. 실제로 구분되는 사실은 "500 아래는 나쁘다"(250에서 +35%)다
- **아래로 갈 이유도 없다.** 500 아래는 커밋이 배로 늘어 노이즈를 넘는 손해가 난다
- **1,000이 평지에 드는 가장 작은 값**이라 p95(394ms, 최저)와 실패 반경을 같이 가져간다

## 7. 이 결과의 유효 범위

- **각 조건 1회.** [모델 6.3](../02-부하테스트-모델.md#63-반복-규칙)의 3회 중앙값 규칙 미달. 자릿수와 방향만 유효하다
- **단계당 표본 10~20건.** p95는 사실상 상위 1~2건이 정한다. 본문은 중앙값을 인용했다
- **동시 1·2·4는 실행이 1초대다.** JIT 워밍업이 섞여 낮은 동시성의 p95는 실행 순서에 좌우된다. 조건 간 비교는 8과 16만 쓴다
- **B의 세 열은 각각 1회 측정이다.** 앞 두 열 사이의 ±10% 차이는 노이즈일 수 있다. 자릿수가 바뀌는 것은 OSIV off 열뿐이다
- **A·C·D는 OSIV off 이후로 다시 쟀다.** 전 회차는 `before-osiv-fix/`에 있고, 본문 숫자는 전부 현재 구성(요청당 커넥션 1회 + OSIV off)의 것이다
- **교착 구간(OSIV on, 동시 16)은 재현성이 없다.** 같은 조건 재실행에서 성공행이 73,000 ↔ 99,000으로 흔들렸다. 어느 요청이 먼저 물리느냐로 결과가 갈리기 때문이고, 그 구간 숫자는 "무너진다"는 사실 외에는 인용하지 않는다
- **피크와 사다리는 축이 다르다.** 사다리는 동시성만, 피크는 동시성과 요청 크기를 같이 바꾼다. 한 곡선 위의 점으로 읽지 않는다
- **D는 동시 1이다.** 큰 청크가 락을 오래 쥐어 남에게 주는 영향이 빠져 있다 — 그 대가는 과소평가돼 있다
- **배경 1,000만 실행은 B 수준 사이에 재시드하지 않았다.** 코드 소금으로 충돌은 피했고, 수준마다 16만 행(배경의 1.6%)이 더 쌓였다
- **인덱스 비교는 부호가 뒤집히는 구간이 있다.** 네 단계 중 둘에서 인덱스 있는 쪽이 빨랐다 = 노이즈가 신호만큼 크다. "10.7%"를 확정값으로 인용하지 않는다
- **인덱스 비교 외의 모든 숫자는 `owner_id` 인덱스가 있는 상태**의 것이다
- **앱을 재기동하면 `ddl-auto: create`가 테이블을 지운다.** 설정을 바꿔 비교할 때는 재기동마다 `reset.sh`를 다시 돌려야 한다([부록 A](#부록-a-osiv가-요청당-커넥션을-둘-점유하던-문제)의 재현 절차)
- Docker Desktop VM 위라 fsync 지연이 실제 서버와 다르다([재고 점유 결과 10장](../../재고점유/전략/mysql-case-update-결과.md#10-fsync-비용-검증)과 같은 한계)
- **Redis 재고 심기는 이 숫자에 없다.** 비동기 executor로 던지므로 응답 시간 밖이다

## 8. 다음 측정

1. **인용할 숫자만 3회 반복** — [모델 6.3](../02-부하테스트-모델.md#63-반복-규칙)의 규칙 미달이 남은 가장 큰 구멍이다. 특히 동시 32(천장)와 피크
2. **큰 청크의 대가를 동시 8에서 재기** — [D](#6-시나리오-d--청크-크기)는 동시 1이라 락 보유 시간이 남에게 주는 영향이 빠져 있다
3. **`innodb_flush_log_at_trx_commit=2`의 값어치** — D가 커밋 fsync를 원인으로 확정했으므로, 내구성을 얼마 내주고 얼마를 사는지 실측할 근거가 생겼다
4. **MySQL CPU를 늘려 천장 확인** — 동시 32의 55,000행/초에서 병목이 MySQL 2 CPU라고 봤는데, CPU를 4로 올려 천장이 따라 오르는지가 그 판정이다
5. **Redis 재고 심기 지연** — 비동기라 응답 시간 밖이다. 동시 64에서 얼마나 밀리는지 아직 모른다

# 부록

## 부록 A. OSIV가 요청당 커넥션을 둘 점유하던 문제

지금은 `open-in-view: false`라 이 문제가 없다. 기록을 남기는 이유는 수치가 아니라 **진단 방법**이다 — 같은 증상(부하가 두 배인데 지연이 백 배)을 다시 만나면 이 순서로 가른다.

### 증상

동시 8이 p95 288ms인데 16이 30,384ms. 처리량은 48,000행/초에서 528행/초로 무너졌다. 커넥션 풀 크기(10)와 동시 요청(16)의 차이는 6뿐인데 결과가 세 자릿수로 갈린다.

### 근거 1 — 대기자가 요청보다 많다

풀 상태를 1초마다 샘플링했다.

```
active  : 10.0 이 175회 중 171회      ← 전 구간 포화
pending : 17~20 이 대부분 (최대 20)
```

**동시 요청은 16인데 커넥션을 기다리는 스레드가 20이다.** 요청보다 대기자가 많으면 요청 하나가 커넥션을 둘 이상 요구한다는 뜻이다. 여기까지는 정황이다.

### 근거 2 — 풀 1에서 혼자 교착한다

풀 크기를 1로 놓고 요청을 하나만 보내면 이분법으로 갈린다. 요청당 커넥션이 순차 1개면 직렬로 돌고, 동시에 2개가 필요하면 즉시 자기 교착한다.

| 풀 1, 동시 1 | p95 | 성공행 | 실패행 |
|---|---|---|---|
| OSIV on | **30,442ms** | 0 | 5,000 |
| OSIV off | 391ms | 5,000 | 0 |

**경쟁 상대가 없는데 커넥션을 30초 기다린다.** 기다릴 대상은 자기 자신뿐이다.

같은 상태에서 풀을 들여다보면 그대로 보인다. 진행 중인 요청이 하나뿐인데:

```
active = 1    idle = 0    pending = 1
```

두 자리가 어디인지는 스택이 말한다. 한 유스케이스 안이다.

| | 위치 | 하는 일 |
|---|---|---|
| **쥐는 쪽** | `RegisterProducts.kt:23` `validateMemberIsSeller` | JPA 조회. 커넥션이 응답 끝까지 물린다 |
| **기다리는 쪽** | `JdbcProductRepository.kt:46` `jdbcTemplate.execute(ConnectionCallback)` | 벌크 삽입용 두 번째 커넥션을 요구 → 30초 뒤 `CannotGetJdbcConnectionException` |

판매자 검증과 벌크 삽입은 순차 실행이라 **논리적으로는 겹치지 않는데, 앞의 것이 반납을 안 해서 물리적으로 겹친다.**

### 근거 3 — 점유 총합이 요청 시간을 넘는다

겹침은 대여 횟수가 아니라 **점유 시간**으로 나타난다. 동시 1로 20건을 보내 Hikari의 대여 지표를 재면:

| | 요청당 대여 횟수 | 대여 1회당 점유 | 요청 처리 시간 | 점유 총합 |
|---|---|---|---|---|
| OSIV on | 2.00 | 123ms | 169ms | **246ms** |
| OSIV off | 2.00 | 67ms | 125ms | 134ms |

**대여 횟수는 양쪽 다 2회로 같다** — OSIV가 대여를 더 만드는 것이 아니다. 결정적인 것은 마지막 열이다. **점유 총합이 요청 처리 시간을 넘으면 두 대여가 겹친 것**이고, 순차라면 넘을 수 없다. OSIV off는 맞아떨어지고 on은 77ms 초과한다.

### 왜 그런가

반납이 **안 되는** 것이 아니라 **늦게** 된다. JPA 커넥션의 반납 시점이 트랜잭션 종료가 아니라 세션(EntityManager) 종료에 묶여 있고, `OpenEntityManagerInViewInterceptor`가 그 종료를 응답 뒤로 옮긴다. 리포지토리 호출의 트랜잭션은 그 안에서 열렸다 닫히지만 세션은 살아 있다.

```
OSIV on   판매자검증 [커넥션A 잡음]······················ 응답 [A 반납]
                          벌크삽입 [커넥션B 잡음][B 반납]
                          └─ A와 B가 동시에 잡혀 있는 구간

OSIV off  판매자검증 [A 잡음][A 반납]
                          벌크삽입 [B 잡음][B 반납]
```

JDBC 쪽이 JPA가 쥔 커넥션을 재사용하지도 못한다. Spring의 `DataSourceUtils`는 **트랜잭션에 묶인** 커넥션만 재사용하는데, OSIV가 묶는 것은 트랜잭션이 아니라 EntityManager다.

> Hibernate 문서상 기본 반납 모드는 `RELEASE_AFTER_TRANSACTION`이라 트랜잭션 종료 시 놓는 것이 맞다. **왜 이 설정에서 그렇지 않은지 내부 분기는 못 짚었다** — Hibernate 6에서는 해당 TRACE 로그가 나오지 않는다. 위 근거 셋으로 동작만 확정했다.

### 끈 근거

이 애플리케이션에서 OSIV가 주는 이득은 0이다.

| 끄면 바뀌는 것 | 이 코드에 미치는 영향 |
|---|---|
| 지연 로딩이 뷰에서 실패 | 없음. `@OneToMany`/`@ManyToOne`/`FetchType`이 하나도 없고 엔티티 4개가 모두 평면이다 |
| 엔티티가 리포지토리 호출 직후 준영속 | 없음. 이후 하는 일은 이미 로딩된 필드를 DTO로 옮기는 것뿐 |
| 1차 캐시 범위가 요청 → 호출로 좁아짐 | 없음. 유스케이스 셋 다 리포지토리를 정확히 1회 호출한다 |
| `ui`가 엔티티를 만지면 깨짐 | 없음. `ui`가 `domain`에서 가져오는 것은 `BusinessException`/`ErrorCode`뿐 |

전체 테스트 스위트가 통과한다.
