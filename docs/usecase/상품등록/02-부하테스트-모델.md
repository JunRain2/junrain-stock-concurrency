## 1. 측정 목표와 범위

### 1.1 목표

설계 문서가 **실측으로 미룬 세 가지**에 숫자를 붙이는 것이 목적이다.

| 질문 | 답해야 할 것 | 근거 |
|---|---|---|
| 청크 크기 1,000이 맞는가 | 배치가 커질 때 행당 비용이 어떻게 변하는가 | [설계 8.5](전략/mysql-insert-ignore-설계.md#85-청크-크기는-세-개의-상한이-정한다) |
| 문장 단위 커넥션 대여를 고쳐야 하는가 | 동시 요청이 늘 때 처리량이 꺾이는 지점 | [설계 8.4](전략/mysql-insert-ignore-설계.md#84-커넥션은-요청당-하나로-고정한다) |
| 행 단위 판별의 비용은 얼마인가 | 중복 비율이 오를 때 지연·처리량 변화 | [설계 10](전략/mysql-insert-ignore-설계.md#10-알려진-한계) |

### 1.2 범위 밖

- **행 단위 실패 경로의 성능** — 도메인 검증 실패는 DB에 가기 전에 끝나서 잴 것이 없다
- **재시도·서킷 브레이커** — 서버 내 재시도를 두지 않기로 했다([설계 6](전략/mysql-insert-ignore-설계.md#6-실패-분류와-포기-범위))
- **Redis 재고 심기의 지연** — 비동기 executor로 넘기므로 응답 시간에 안 들어간다. 심기가 밀리는지는 별도 측정이 필요하다
- **5,000행 초과** — 동기 응답 상한이 계약이다

## 2. 부하 모델

### 2.1 처리량 단위는 행/초다

요청 하나가 100행일 수도 5,000행일 수도 있다. 요청/초로는 시나리오 간 비교가 성립하지 않으므로 **행/초**를 1차 지표로 쓴다.

```
행/초 = 요청 행 수 ÷ 응답 시간
```

### 2.2 도착률 고정을 쓰지 않는다

[재고 점유 부하테스트](../재고점유/02-부하테스트-모델.md#31-도착률-고정-방식)는 `constant-arrival-rate`로 초당 요청 수를 고정한다. 요청 하나가 밀리초 단위라 그게 맞다.

여기서는 요청 하나가 **초 단위**다. 도착률을 고정하면 지연이 늘 때 VU가 순식간에 마르고, 재는 대상이 서버가 아니라 k6의 VU 수급이 된다. 그래서 **동시 요청 수(VU)를 고정**하고 각 VU가 순차로 다음 요청을 보내는 폐루프 모델을 쓴다. 동시성이 곧 부하 파라미터다.

### 2.3 단계는 이터레이션 번호로 가른다

한 실행 안의 단계(배치 크기·중복 비율)를 `startTime`으로 배치하지 않는다. 요청 하나의 소요를 미리 모르는데 시각으로 자르면, 앞 단계가 넘칠 때 구간이 겹쳐 측정이 조용히 오염된다. 이터레이션 번호로 나누면 앞 단계가 끝나야 다음 단계가 시작한다.

동시성 수준만은 VU 수가 달라 한 실행에 못 담는다. **수준마다 k6 실행을 새로 띄우고 사이에 리셋한다.**

### 2.4 실행 사이 리셋이 필수다

한 실행이 수십만 행을 남긴다. 리셋 없이 이어 돌리면 unique 인덱스가 계속 커져 **뒤 실행이 다른 조건을 잰다.** `reset.sh`가 `products`를 비우고 Redis를 flush한다.

## 3. 시나리오

| | 부하 축 | 배치 | 역할 |
|---|---|---|---|
| **A** | 배치 크기 100 / 500 / 1,000 / 5,000 | 동시 1 | 분모. 경합 없는 행당 비용 |
| **B** | 동시 요청 1 / 2 / 4 / 8 / 16 (+ 피크 10×5,000) | 1,000행 | 커넥션 풀이 마르는 지점, 그리고 실제 피크 |
| **C** | 신규 비율 100% / 50% / 0% | 5,000행 | 중복 판별 경로의 비용 |
| **D** | `chunk-size` 250 / 500 / 1,000 / 2,000 / 4,000 | 5,000행 | 청크 값 자체. 설계 8.5를 닫는다 |

### 3.1 A — 배치 크기

같은 총 행 수를 큰 요청 하나로 보낼 때와 작은 요청 여럿으로 보낼 때의 차이를 본다. 행/초가 배치 크기에 따라 **평평하면** 행당 비용이 지배적이고, **커질수록 올라가면** 요청 고정비(왕복·검증·응답 조립)가 크다는 뜻이다.

청크 크기(1,000)를 넘어서는 5,000행 요청은 청크 5개 + 역조회 5개 = 문장 10개다. 100행 요청은 2개다. 이 비율이 행/초에 어떻게 나타나는지가 [설계 8.5](전략/mysql-insert-ignore-설계.md#85-청크-크기는-세-개의-상한이-정한다)의 입력이다.

### 3.2 B — 동시 요청

브랜드 여럿이 같은 시간에 대량 등록을 하는 상황이다. 배치를 1,000행(청크 1개)으로 고정해 **요청당 문장 수를 최소로** 만든 뒤 동시성만 올린다. 그래야 꺾이는 지점이 커넥션 때문인지 문장 수 때문인지 갈린다.

HikariCP 기본 풀이 10이므로 8 → 16 사이에서 대기가 보일 것으로 예상한다. 예상이 맞으면 [설계 8.4](전략/mysql-insert-ignore-설계.md#84-커넥션은-요청당-하나로-고정한다)의 "요청당 커넥션 1회" 전환이 근거를 얻는다. 안 보이면 지금 방식을 유지한다.

#### VU는 브랜드에 나눠 준다

전부 한 `ownerId`로 보내면 `owner_id` 인덱스 삽입이 한 값에 몰려 **실제로는 없을 핫스팟**이 생긴다. VU를 `seed.sql`이 심는 판매자 10명에게 돌려 붙인다(`((__VU - 1) % 10) + 1`). 동시 16이면 브랜드 6곳이 요청 2개씩을 띄우는 모양인데, 한 브랜드가 두 개를 겹쳐 올리는 것도 현실이라 그대로 둔다.

#### 부하 산정 근거

사다리 값과 피크 조합은 임의로 고른 것이 아니다. 쿠팡 입점 판매자 증가에서 왔다.

| | |
|---|---|
| 2015년 입점 중소상공인 | 12,161명 |
| 2023년 | 230,000명 |
| 8년간 증가 | 217,839명 = **일평균 약 75명** |

일 75명이면 시간당 3명꼴이지만, 신규 입점은 업무 시작 시간대에 몰린다. 판매자 하나가 한 번에 수천 개를 올리므로 **피크에 브랜드 5~10곳의 대량 등록이 겹치는 상황**을 상한으로 잡는다.

#### 피크는 사다리와 따로 잰다

배치 1,000은 **원인을 가르기 위한** 값이지 최대 부하가 아니다. 사다리 최고점에서도 동시에 떠 있는 행이 16,000행뿐이다. 실제 피크 상한은 이렇다.

```
브랜드 10곳 x 5,000행 = 동시 50,000행
```

```bash
bash k6-tests/registration/reset.sh
k6 run --env VUS=10 --env BATCH=5000 k6-tests/registration/scenario-b-concurrent.js
```

사다리에 섞지 않는 이유는 **축이 둘이 되면 꺾인 원인을 못 가리기 때문**이다. 사다리는 동시성만, 피크는 그 위에서 크기만 바꾼다. `run.sh`는 사다리를 다 돈 뒤 피크를 한 번 더 돌린다.

피크에서 볼 것은 처리량이 아니라 **실패의 모양**이다. 사다리가 이미 동시 16에서 무너졌으므로 5만 행 동시는 한계 밖이고, 확인할 것은:

- **응답 형태** — 200 + 행 단위 실패로 오는가, 500이 섞이는가. 한 번 섞인 적이 있고([설계 10](전략/mysql-insert-ignore-설계.md#10-알려진-한계)) advice 핸들러로 닫았으므로, 다시 섞이면 회귀다
- **앱 힙** — 요청 하나가 5,000행을 통째로 힙에 올린다([설계 8.3](전략/mysql-insert-ignore-설계.md#83-메모리는-요청-상한이-막는다)). `mem_limit` 1500m의 70%가 힙이다
- **k6 쪽 CPU** — 5,000행 JSON(약 500KB)을 이터레이션마다 만든다. 생성기가 먼저 마르면 재는 대상이 서버가 아니다

### 3.3 C — 중복 비율

신규 100%가 A의 5,000행 단계와 같은 조건이라 기준선이 된다. 중복이 늘면:

- INSERT는 write가 줄어 빨라진다
- 생성키가 줄어 역조회 IN 절이 짧아진다
- 응답의 `failedProducts`가 길어져 직렬화가 커진다

어느 쪽이 이기는지가 결과다. 신규 0%는 5,000행 전부가 실패 목록에 실리는 최악의 응답 크기이기도 하다.

`setup()`이 중복으로 쓸 5,000개 코드를 미리 심는다. 이 요청의 지연은 측정에 안 들어간다.

### 3.4 D — 청크 크기

**A와 헷갈리기 쉽다.** A는 요청 하나에 담은 행 수를 바꾸고, `chunk-size`는 전 구간 1,000 고정이다. D는 반대로 **요청을 5,000행으로 못 박고 청크만** 바꾼다. 그래야 바뀌는 것이 문장 수 하나로 좁혀진다.

| 청크 | 5,000행 요청이 보내는 문장 |
|---|---|
| 250 | INSERT 20 + 역조회 20 = 40 |
| 1,000 | INSERT 5 + 역조회 5 = **10** |
| 4,000 | INSERT 2 + 역조회 2 = 4 |

문장이 적을수록 왕복이 준다. 대신 문장 하나가 커져 락 보유 시간과 binlog 이벤트가 커지고, 파라미터 상한(65,535 ÷ 8컬럼 = 8,191행)에 가까워진다. **이 둘이 만나는 지점이 청크 값**이고, [설계 8.5](전략/mysql-insert-ignore-설계.md#85-청크-크기는-세-개의-상한이-정한다)가 실측으로 미뤄둔 것이다.

청크는 서버 설정이라 k6 실행 하나가 값 하나만 잡는다. 값마다 앱을 다시 띄우므로 `sweep-chunk.sh`가 따로 있다([6.2](#62-chunk-size-스윕)).

### 3.5 코드 유일성

요청 안에서 코드가 겹치면 **DB 중복이 아니라 "요청 내 중복"으로 분류돼 다른 경로를 재게 된다**([비즈니스 규칙 3](01-비즈니스-규칙.md#3-입력-규칙)). 그래서 코드에 시나리오·이터레이션·행 번호를 모두 넣는다. C의 의도된 중복만 예외다.

## 4. 판정 기준

### 4.1 이 API에는 지연 SLO가 없다

`p95 < 200ms`는 재고 점유의 SLO다. 5,000행을 넣는 요청에는 적용할 수 없다. 대신 **행/초의 변화**로 판정한다.

| 시나리오 | 읽는 것 |
|---|---|
| A | 배치 크기별 행/초. 평평한가, 우상향인가 |
| B | 동시성별 총 행/초(= 행/초 × 동시 수). 꺾이는 지점 |
| C | 신규 비율별 행/초. 100% 대비 몇 배인가 |
| D | 청크별 행/초. 최고점이 어디인가, 평평하면 이 축은 안 중요하다 |

### 4.2 무효 조건

아래가 뜨면 그 실행은 버린다.

- **`http_req_failed > 0`** — 이 시나리오들은 전부 200을 기대한다. 400/409/5xx가 섞였으면 시드나 코드 생성이 틀렸다
- **`checks` 실패** — 응답의 `successCount + failureCount`가 보낸 행 수와 다르다. 위치 규약이 깨진 것이므로 성능이 아니라 정합성 문제다
- **의도하지 않은 실패 행** — A·B에서 `rejected_rows`가 보인다면 코드가 겹쳤다. 신규 삽입이 아니라 중복 스킵을 잰 것이다

### 4.3 행/초는 중앙값을 쓴다

요청 하나가 초 단위라 단계당 표본이 수십 건뿐이다. 평균은 첫 요청의 커넥션 수립·JIT 워밍업에 끌려간다. p95는 표에 같이 싣되 인용은 중앙값으로 한다.

## 5. 측정 환경

[재고 점유 부하테스트 6장](../재고점유/02-부하테스트-모델.md#6-측정-환경)과 같은 환경·같은 제약을 쓴다. `docker-compose.bench.yml`이 자원 배분을 고정한다.

**스크립트가 도는지 보는 실행과 측정을 섞지 않는다.** 스모크는 로컬 `bootRun` + 기본 compose로 해도 되지만, 그 환경은 앱 CPU가 무제한이고 MySQL buffer pool이 기본값(128MB)이라 bench 오버레이(1GB)와 완전히 다른 숫자가 나온다. 스모크에서 나온 값을 기준선으로 재활용하지 않는다.

추가로 이 경로에만 걸리는 것:

- **요청 본문이 크다.** 5,000행이면 약 500KB다. k6가 매 이터레이션 JSON을 새로 만들므로 **부하 생성기 CPU가 먼저 마를 수 있다.** 동시 16 이상으로 올릴 때는 k6 쪽 CPU를 같이 본다
- **디스크가 는다.** A 한 번이 약 13만 행, B 전체가 약 31만 행을 쓴다. 리셋이 `TRUNCATE`라 공간은 회수되지만 실행 중 최대치는 그만큼이다
- **환경 스탬프**를 결과 옆에 남긴다. 스탬프 형식은 [재고 점유 6.4](../재고점유/02-부하테스트-모델.md#64-환경-스탬프)와 같다

## 6. 실행 방법

```bash
# 전체 (A → B 5수준 → C)
bash k6-tests/registration/run.sh
```

`run.sh`가 이미지 빌드·기동부터 리셋·실행까지 전부 한다. 시나리오마다, B는 동시성 수준마다 `reset.sh`를 부른다.

개별 실행:

```bash
bash k6-tests/registration/reset.sh
k6 run --env BASE_URL=http://localhost:8080 --env OWNER_ID=1 k6-tests/registration/scenario-a-batch-size.js
k6 run --env VUS=8 k6-tests/registration/scenario-b-concurrent.js
k6 run k6-tests/registration/scenario-c-duplicate-ratio.js
```

**앱 기동이 시드보다 먼저다.** `ddl-auto=create`라 기동이 테이블을 다시 만든다. `reset.sh`가 헬스체크로 이 순서를 강제한다.

### 6.1 변수 하나만 바꿔 비교하기

인덱스 유무처럼 **스키마만 다른 두 조건**을 비교할 때는 앱을 다시 빌드하지 않는다. 같은 바이너리에 스키마만 토글해야 변수가 하나로 고정된다.

```bash
# 인덱스 있는 상태
bash k6-tests/registration/reset.sh
```

### 6.2 chunk-size 스윕

```bash
bash k6-tests/registration/sweep-chunk.sh
PRESEED_ROWS=1000000 bash k6-tests/registration/sweep-chunk.sh   # 배경 데이터까지
CHUNKS="500 1000" BATCH=3000 bash k6-tests/registration/sweep-chunk.sh
```

값마다 앱을 다시 띄우고([`docker-compose.bench.yml`](../../../docker-compose.bench.yml)의 `BULK_INSERT_CHUNK_SIZE`), 리셋하고, [시나리오 D](#34-d--청크-크기)를 돌린 뒤 마지막에 청크별 요약을 모아 찍는다. 스윕이 끝나면 앱을 기본값으로 되돌린다 — 안 그러면 다음 측정이 마지막 청크 값으로 돈다.

주의할 것:

- **`ddl-auto=create`라 앱 재기동이 테이블을 새로 만든다.** 배경 데이터를 쓰는 스윕은 회차마다 재시드되고, 1,000만 행이면 그 시간이 회차마다 붙는다
- **k6에 주는 `CHUNK`와 서버의 `CHUNK_SIZE`가 같아야 한다.** k6는 서버 설정을 읽을 방법이 없어서 라벨이 어긋나도 조용히 돈다. `sweep-chunk.sh`가 같은 변수로 양쪽을 채우는 이유다
- 바인딩이 먹었는지 의심되면 `CHUNK_SIZE=0`으로 띄우고 요청 하나를 보낸다. `"Step must be positive, was: 0."`이 오면 값이 전달된 것이다

### 6.3 반복 규칙

숫자를 문서에 인용하려면 **같은 조건으로 3회 반복해 중앙값**을 쓴다. 1회 실행은 배경 잡음(다른 빌드, 브라우저)과 구분되지 않는다.

## 7. 결과 해석

터미널 출력:

```
=== A: 배치 크기 ===

   행/요청   요청수      p95      행/초     성공행     실패행
       100       20     41ms       2439       2000          0
       500       20     92ms       5434      10000          0
      1000       20    158ms       6329      20000          0
      5000       20    703ms       7112     100000          0
```

읽는 순서:

1. **경고 블록이 있으면 거기서 멈춘다.** 무효 조건에 걸린 실행의 숫자는 인용하지 않는다
2. **실패행이 0인지 확인한다.** A·B에서 0이 아니면 재려던 것을 안 재고 있다
3. **행/초의 기울기를 본다.** A가 우상향이면 요청 고정비가 크다는 뜻이고, 그 크기가 청크 크기 조정의 근거다
4. **B의 총 행/초가 꺾이는 동시성**을 찾는다. 그 지점이 커넥션 대여 방식을 바꿀지 판단하는 값이다

원본 JSON은 `k6-tests/results/registration/`에 남는다. 측정치를 문서로 옮길 때는 `전략/` 아래에 결과 문서를 새로 만들고, 이 문서는 방법만 유지한다 — [재고 점유의 결과 문서들](../재고점유/전략/)과 같은 구조다.
