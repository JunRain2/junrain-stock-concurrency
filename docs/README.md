# docs 구조

## 분류 축

1차 축은 **유스케이스**다. 문서는 애그리거트가 아니라 유스케이스 단위로 묶는다 — 비즈니스 규칙·인프라 전략·측정 결과가 전부 "이 유스케이스가 어떻게 동작하는가"에 매달려 있기 때문이다.

```
docs/
├── README.md              이 문서
└── usecase/
    └── <유스케이스>/       예: 재고점유 (= ReserveProducts)
        ├── 01-비즈니스-규칙.md      무엇을·왜 (전략 무관)
        ├── 02-부하테스트-모델.md    어떻게 잰다 (전략 무관)
        └── 전략/
            ├── <전략>-설계.md       어떻게 구현한다
            └── <전략>-결과.md       얼마나 나온다
```

유스케이스 폴더 이름은 한글 업무 용어로 짓고, 대응하는 유스케이스 클래스를 문서 헤더 표에 적는다.

## 문서 종류

문서는 답하는 질문으로 나뉜다. 한 문서가 두 질문에 답하면 쪼갠다.

| 종류 | 질문 | 위치 | 전략 의존 |
|---|---|---|---|
| 비즈니스 규칙 | 무엇을 하는가, 왜 그렇게 정했는가 | `<유스케이스>/01-*.md` | 없음 |
| 부하테스트 모델 | 무엇을 어떤 기준으로 재는가 | `<유스케이스>/02-*.md` | 없음 |
| 전략 설계 | 이 인프라에서 어떻게 구현했는가 | `전략/<전략>-설계.md` | 전략당 1개 |
| 측정 결과 | 그래서 얼마나 나오는가 | `전략/<전략>-결과.md` | 전략당 1개 |

전략 무관 문서는 번호를 붙여 읽는 순서를 고정한다. 전략 문서는 순서가 없으므로 번호를 붙이지 않는다.

## 전략 slug

설계와 결과가 같은 slug를 쓴다. slug 하나 = 구현체 하나. 이름이 갈리면 설계와 결과가 짝이라는 게 안 보인다.

| slug | 구현체 |
|---|---|
| `mysql-case-update` | `MySqlStockWriterImpl` |
| `mysql-skip-locked` | `SkipLockedStockWriterImpl` |
| `redis-lua` | `RedisStockWriterImpl` |

## 규칙

- 새 전략을 추가할 때 기존 전략 문서를 고쳐 쓰지 않는다. 같은 slug로 설계·결과 2개를 새로 만든다.
- 측정 결과는 `02-부하테스트-모델.md`가 정의한 시나리오·판정 기준을 그대로 쓴다. 기준을 바꾸면 기존 결과와 비교 불가이므로 모델 문서를 먼저 고친다.
- 문서 첫머리에 대상·구현체·관련 문서를 표로 남긴다.
- 유스케이스에 매이지 않는 문서(아키텍처 결정, 운영 런북 등)는 `usecase/` 밖에 종류별 폴더를 만들어 둔다.
